# 审查 docs 文档与需求讨论上下文的一致性

## 概述

prd/proto/arch 文档族命令产出的每份 docs 文档（PRD/原型/技术方案）是需求讨论结果的固化，提交 docs PR 前必须加载本 skill 做一次完整审查。

**核心原则**：docs 文档是下游一切的标准来源。如果文档偏离了讨论上下文，后续 apply 阶段的全部实现都会跑偏——越早发现代价越小。

## 触发时机

- **docs PR 提交前**（强制）：每个阶段文档完成时审查该份；技术方案完成后三份联审
- **独立使用**：用户对文档内容有疑虑时手动调用

## 审查方法：逐字符对比

不是粗略浏览，是**逐字逐句**把文档内容与需求讨论上下文对比。

### 审查输入

1. **需求讨论上下文**：对话历史与 Issue 评论时间线中讨论的所有内容（需求、约束、决策、取舍、风险）
2. **docs 文档**：
   - `docs/prd/<模块>.md` — 业务规则 + 验收标准（逐条可勾选）
   - `docs/design/<功能>.html` — 交互原型（结构 + 字段 + 四态枚举）
   - `docs/architecture/<功能>.md` — 技术方案（八章节，写决策不抄代码）

### 审查维度

#### 1. 需求覆盖完整性

逐条检查需求讨论（对话 + Issue 时间线）中提到的每个需求点：

| 检查项 | 方法 |
|--------|------|
| 用户明确要求的功能 | 在 PRD 功能清单中是否都有对应 |
| 用户提到的约束条件 | 在技术方案或 PRD 业务规则中是否体现 |
| 用户关注的边界场景 | 在 PRD 异常流程/验收标准中是否覆盖 |
| 用户提到的非目标（明确不做的） | 在技术方案「目标与非目标」章节是否声明 |

**发现问题**：列出遗漏的需求点，标注严重程度（必须补 vs 可选补）。

#### 2. 方向一致性

逐段检查文档是否偏离了讨论确定的方向：

| 检查项 | 方法 |
|--------|------|
| 技术选型方向 | 技术方案的决策是否与讨论的技术倾向一致 |
| 范围边界 | PRD/技术方案的范围是否与讨论一致（没有偷偷扩大或缩小） |
| 三阶段咬合 | 原型字段/操作与 PRD 验收标准、技术方案契约是否互相一致 |

**发现问题**：列出偏离点，标注讨论中的原始位置和文档中的偏离位置。

#### 3. 内部自洽性

检查三份文档之间的交叉引用是否一致：

| 检查项 | 方法 |
|--------|------|
| PRD → 原型/方案 | PRD 的每条验收标准在原型（字段/操作）与技术方案（契约）中是否都有对应 |
| 方案 → 验收 | 技术方案测试策略规划的每个用例在验收 checklist 中是否都有对应条目 |
| design → tasks | design 中的每个技术决策在 tasks 中是否都有对应落地任务 |
| tasks 内部 | 依赖顺序是否合理（前置任务排在前面） |

**发现问题**：列出断裂的引用链。

#### 4. 表述精确性

逐句检查是否有模糊、歧义或自相矛盾的表述：

| 检查项 | 方法 |
|--------|------|
| 模糊措辞 | "等"、"可能"、"如果需要"、"后续考虑" — 是否需要现在明确 |
| 自相矛盾 | 同一文档内或跨文档的矛盾描述 |
| 缺失定义 | 提到但未定义的概念、术语 |

#### 5. 测试分层硬禁（无豁免，一票否决）——**每轮审查的重点检查项**

每一轮审查，**首先**逐条扫描本项再进入其他维度——历史上重型层验证混入日常实现规划是最高频、代价最大的违规。逐条扫描技术方案与验收 checklist 中的验证类条目：

| 检查项 | 判定 |
|--------|------|
| 重型层任务 | tasks 中出现 E2E 端到端/VRT 视觉回归/截图对比/性能/全量集成测试的编写、修改、运行条目 → 🔴 |
| 重型层验证命令 | task 的验证命令是重型层命令 → 🔴 |
| 重型层落地 | 方案或 checklist 把重型层测试落成日常待执行验证动作 → 🔴（归口 PR CI 门禁） |

**重型层纪律**：技术方案"测试策略"章节规划测试用例是正常内容；但日常实现验证的规划只做编译级确认（build/typecheck）——lint 与一切测试（含单元）的运行都在 PR CI，agent 本地零测试。

## 审查报告格式

```
## 审查报告：Issue #<N> <功能名>

### 审查范围
- 需求讨论上下文：澄清对话（/shw-issue）与文档族起草/审查会话 + Issue 评论时间线
- 文档：docs/prd/<模块>.md / docs/design/<功能>.html / docs/architecture/<功能>.md

### 🔴 必须修复（<N> 项）
1. [需求遗漏] 需求讨论中提到的「XXX」在 PRD 中没有体现
   - 讨论原文："..."
   - 当前状态：缺失
   - 建议：在 PRD 功能清单中补充

2. [方向偏离] 技术方案选择了 Redis 但讨论确定用 PostgreSQL
   - 讨论原文："用 PostgreSQL，不要 Redis"
   - design 原文："使用 Redis 做缓存"
   - 建议：改为 PostgreSQL

### 🟡 建议修复（<N> 项）
1. [表述模糊] tasks.md 的 task 3.1 "完善测试"过于笼统
   - 建议：明确测试哪些场景

### ✅ 通过项
- 需求覆盖：X/Y 项覆盖
- 方向一致：技术选型/范围/优先级均与讨论一致
- 内部自洽：三份文档交叉引用完整
- 表述精确：无模糊/矛盾
```

## 审查后的行动

- **有 🔴 项**：必须修复后才能提交 docs PR。文档族起草流程内由本审查直接修复文档并复审（连续 5 轮不收敛才停下交用户决策）；独立使用时列出修复建议交用户决定。
- **只有 🟡 项**：同样不放过——逐条经用户裁决处置（修复，或豁免并记录理由）；处置完毕才可进入 apply。
- **全部 ✅**：宣布审查通过，提示下一步进入 `/shw-milestone` 排期（大活链）或按当前流程继续；不直接提示 `/shw-apply`——排期与 test 族是 docs 合入到 apply 之间的必经闸。

## 约束

- **逐字符审查，不是粗略浏览**。每份文档都要从头到尾读完。
- **必须有讨论上下文可对比**。小活无 docs 文档时本 skill 不适用（小活三五句话直跳开发，见 shw-gitea-flow）。
- **审查报告必须包含具体引用**（讨论原文 + 文档原文），不能只说"有问题"。
- **独立使用时不修改文档**——只报告问题，修复交用户决定；文档族起草流程内由审查循环直接修复文档并复审。
