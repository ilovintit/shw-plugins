# 端口分配与登记

## 概述

端口冲突的本质是不查表就乱分配。两个项目抢同一端口、dev server 启动即占用、联调时端口互踩——根因永远是"凭感觉选了个端口"。

**核心原则**：每个端口都要先查全局登记表确认空闲，登记后才写进项目配置。

**登记表是唯一事实来源，不是项目内的随手配置。** 凭项目历史记忆、凭默认值直接用，就是在埋雷。

## 铁律

```
分配端口前不查表 = 失职
分配端口后不登记 = 埋雷
```

凭"应该没人用"、"这个端口很冷门"、"沿用上个项目"的直觉选端口——全部是失职。
选完端口不登记就写进配置——下次冲突由你造成。

## 端口登记表

**位置**：`~/Documents/Workspace/.port-registry/ports.yaml`

这个位置是跨项目的全局位置，**不在任何单项目内**。端口冲突发生在项目之间，所以登记表必须独立于所有项目存在。

**YAML 结构：**

```yaml
ports:
  - port: 9501              # 端口号（整数）
    project: project-a      # 所属项目名
    service: api            # 服务名（api/web/admin/db/redis 等）
    usage: HTTP API server  # 用途说明
    protocol: tcp           # 协议（tcp/udp/http）
```

每条记录五个字段缺一不可。`usage` 写清楚这个端口跑的是什么，后来人查表才知道能不能让、能不能改。

## 门禁函数

```
需要分配端口（新项目初始化 / 新服务 / dev server 配置）时：

1. 查表：读取 ~/Documents/Workspace/.port-registry/ports.yaml
   - 提取已占用端口集合（所有项目的所有端口）
   - 若文件不存在 → 首次使用：创建 `~/Documents/Workspace/.port-registry/` 目录与初始 ports.yaml（空列表或现有端口快照），然后继续查表流程

2. 选端口：从项目历史约定或合理范围选候选端口
   - 排除已占用集合
   - 候选端口在合理范围内（见下"端口范围建议"）
   - 选定后再次确认不在已占用集合里

3. 登记：追加一条完整记录到 ports.yaml
   - 五个字段填齐（port/project/service/usage/protocol）
   - 先写文件，再做下一步——顺序不能反

4. 使用：将分配的端口写入项目配置
   - .env、docker-compose、框架配置等
   - 端口必须与登记表里那一条完全一致

跳过查表 = 失职；跳过登记 = 埋雷。
```

## 端口范围建议

按服务类型约定建议范围，新分配优先落在这几个段内：

| 服务类型 | 建议范围 | 说明 |
|---------|---------|------|
| 后端 API server | 19501+ / 9501+ | 内部约定 Hyperf 服务用 19501 段、GoFrame 服务用 9501 段（是内部约定，不是框架默认端口） |
| 前端 dev server | 15175+ / 5173+ | Taro H5 用 15175；Vite 默认 5173 |
| 基础设施 | 3000+ / 7500+ | frp 等内网工具 |
| 数据库 / Redis | 标准端口 / 自选段 | 共享实例（标准端口）不登记；项目自建独立实例（如 docker 起的非标准端口 db/redis）MUST 查表登记 |

共享实例（PostgreSQL 5432、Redis 6379 等标准端口，多项目共用一个实例）不属于"某项目的端口"，不登记；但项目自建的独立实例（如 docker 起的 db/redis 用非标准端口、仅本项目使用）是项目专属端口，MUST 查表登记——多个项目各起各的容器照样会撞端口。

后端默认端口（9501、19501）只在单项目独占机器时直接用；多项目并存时一律从建议范围里挑新号。

## 典型冲突场景（血的教训）

| 冲突类型 | 后果 |
|---------|------|
| 两个项目 dev server 抢同一端口 | 启动即占用，互相挤掉 |
| 前端 dev server 与内网工具（如 frp）抢默认端口 | Vite 默认 5173 被工具占了，dev server 起不来 |
| 两套 Taro H5 撞同一端口（都用 15175） | 同时开发时只能起一个 |

每一次冲突都源于"没查表就用了默认/熟记的端口"。登记表存在就是为了终结这种各自为政。

## 红旗 - 停下重新评估

- 准备直接写 9501 / 19501 / 5173 / 15175 进配置，没查过表
- 准备"沿用上个项目的端口"（上个项目的端口不一定空闲）
- 准备选个"看起来没人用"的端口号
- 改了端口却没更新 ports.yaml
- ports.yaml 不存在 → 初始化创建，不是跳过登记的理由
- 端口登记了，但 project / service / usage 字段留空或瞎填
- 共享实例的标准端口往 ports.yaml 里塞（共享服务不登记；自建独立实例仍要登记）

## 防止合理化

| 借口 | 现实 |
|--------|---------|
| "这个端口很冷门，没人用" | 查表才能证明 |
| "沿用上个项目应该没事" | 上个项目可能还在跑 |
| "默认端口最省事" | 默认端口是冲突重灾区 |
| "ports.yaml 不存在就跳过登记" | 文件不存在 → 初始化创建，不是跳过登记的理由 |
| "先写配置，回头再登记" | 回头 = 永远不会，先登记再用 |
| "数据库端口也要登记吧" | 共享实例不登记；自建独立实例（非标准端口）必须登记 |
| "就这一个服务，不会冲突" | 下一个项目也会这么想 |
| "改一次端口而已" | 改了就要同步登记表 |

## 何时触发

**以下场景必须走查表→登记流程：**

- 新项目初始化，需要分配第一个端口
- 项目新增服务（加 admin、加 websocket、加 worker 等）
- 配置 dev server（前端 H5、Vite、webpack-dev-server）
- 配置基础设施（frp、nginx、内网穿透端口映射）
- 变更已有服务的端口

**不触发：**

- 只读代码、查资料、看现有端口配置（没在分配端口）
- 共享实例的数据库 / Redis 等标准端口服务（走共享实例，不登记；项目自建独立实例仍要登记）

## 底线

**端口不是凭直觉选的，是从登记表里确认出来的。**

先查表，再选号，先登记，再用。顺序错了，冲突就是你埋的。

这是不可协商的。
