# 行政区划采集库设计规范

## 概述

本 skill 是行政区划（省/市/区县/街道）采集库的**设计规范**，语言无关。组件的定位是**采集工具**，不是数据系统：它把任意数据源（高德、民政部、腾讯……）的区划数据拉下来、标准化成统一的 `Region[]` 输出，仅此而已。至于存到哪、怎么查、怎么管版本——那是业务方的事，组件不碰存储、不碰缓存、不碰查询层。

**铁律的反面就是最常见的错误**：把采集和存储揉在一起。一旦组件自己存数据，就会卷入"数据要不要更新"、"新旧版本怎么管"、"缓存怎么失效"这一堆跟采集本身无关的问题，从一个工具退化成一个带状态的系统，难测试、难迁移、难切换数据源。

下文的接口、算法均用伪代码描述，任意后端语言按同一套契约落地即可。

**适用判断**：设计或实现行政区划采集、地区级联选择器数据源、地址库、多厂商区划数据统一接入时。纯业务侧的"用户填地址"表单交互（不涉及数据采集标准化）不适用本 skill。

---

## 铁律

```
组件只采集，不存储、不缓存
adcode 统一 9 位（6 位国标右侧补 000，街道天然 9 位不动）
Region 是不可变值对象（readonly），算完不再变
path 必须是根到自身的完整 adcode 链（用于子树 LIKE 查询）
数据源差异在 Adapter 内部消化，Collector 只认统一层级的 Region
```

凭"顺手存一份到数据库省得每次采"、"缓存一下采集结果省点流量"、"街道的 6 位和区县的 6 位格式不一样分开存"的直觉做事——全部是在把采集库拖进它不该管的领域。

---

## 1. 核心理念：只采集不存储

这是整个设计的地基。组件提供的是**采集工具**，不提供数据；职责到"输出标准化的 `Region[]`"为止，**一字节都不往持久层写**。

```
错误定位：采集 + 存储 + 缓存 + 版本管理 一把抓
   组件自己往 DB/Redis 写数据
   → 数据要不要定时更新？多久更新？
   → 多版本怎么共存？新旧切换谁负责？
   → 缓存失效策略谁定？
   → 切换数据源要清哪些表/键？
   一个采集库背上了一整套数据生命周期管理的包袱。

正确定位：采集 + 标准化 → 输出 Region[]，结束
   存储在哪：业务方决定（MySQL / 文件 / 内存）
   查询怎么做：业务方决定（建表 + path LIKE / 塞进搜索引擎 / 直接树形）
   版本怎么管：业务方决定（快照表 / 时间戳 / 全量覆盖）
   组件无状态、无副作用、可反复调用、可独立测试。
```

**只采集不存储的四大好处**：

| 好处 | 说明 |
|------|------|
| 无依赖 | 不依赖 Redis、不依赖 DB。任何环境随时调，环境挂了采集逻辑不受牵连 |
| 可复跑 | 同一份输入永远产出同一份输出，没有"上次跑过了这次行为不一样"的状态残留 |
| 易测试 | 调一次 Collector 拿到 `Region[]`，断言即可。不需要起容器、不需要造数据 |
| 业务自治 | 业务方最清楚自己要存全量还是只存某省、要每日刷还是手动刷——这不该由组件替它决定 |

## 2. Region 值对象（不可变 / readonly）

采集产出的基本单元。**readonly / 不可变**：一旦构造完成，任何字段都不再修改。需要"算 path"这种派生操作时，构造时就算好塞进去，而不是事后改对象。

| 字段 | 类型 | 说明 |
|------|------|------|
| `adcode` | string(9) | 9 位行政区划代码（详见第 3 节）。统一长度，便于 path 拼接和前缀匹配 |
| `name` | string | 简称（如"北京"、"朝阳"） |
| `fullname` | string | 全称（如"北京市"、"朝阳区"） |
| `level` | int | 层级：`1` 省 / `2` 市 / `3` 区县或街道（详见第 5 节层级拉平） |
| `path` | string | 路径枚举，从根到自身的 adcode 链（详见第 4 节） |
| `parentCode` | string(9) \| null | 9 位父级 adcode；省级为 `null`（根节点无父） |
| `lat` / `lng` | float | 坐标，统一 **GCJ-02**（火星坐标系），不要混入 WGS-84 或 BD-09 |
| `pinyin` | string | 拼音，空格分隔（如 `"bei jing"`），用于字母索引/排序/首字母分组 |

```
readonly value object Region:
    adcode:      string       # 9 位，构造时归一
    name:        string
    fullname:    string
    level:       int          # 1 | 2 | 3
    path:        string       # 构造时算好塞入
    parentCode:  string|null  # 省级为 null
    lat:         float
    lng:         float
    pinyin:      string

    # 构造后无任何 setter / mutate 方法
```

**为什么强制不可变**：Region 会在 path 计算、子树查询、前端渲染多处流转。可变对象在任何一处被意外修改，后续所有持有者都受污染，排查极难。值对象 + 构造时算全 = 用过即丢、谁拿到都是一致的快照。

**坐标为什么统一 GCJ-02**：国内地图展示（高德/腾讯）用 GCJ-02，国测局要求境内展示必须经过偏移。采集时就把坐标归一到 GCJ-02，业务方拿来即用，不用每处再判"这个坐标是哪套"。如果数据源给的是 WGS-84（如部分 GPS 原始数据），Adapter 内部做一次转换，对外仍只吐 GCJ-02。

## 3. 9 位 adcode 统一编码

国标行政区划代码（GB/T 2260）省/市/区县级是 **6 位**（省 2 位 + 市 2 位 + 县 2 位），街道/乡镇级是 **9 位**。本规范对外**一律 9 位**，规则如下：

| 来源 | 原始 | 归一规则 | 9 位结果 |
|------|------|---------|---------|
| 省/市/区县（6 位国标） | `110000`、`110100`、`110105` | 右侧补 `000` | `110000000`、`110100000`、`110105000` |
| 街道/乡镇（9 位国标） | `110105026` | 天然 9 位，不动 | `110105026` |

```
function normalizeAdcode(raw: string) → string:
    if length(raw) == 9:
        return raw                      # 街道级，原样返回
    if length(raw) == 6:
        return raw + "000"              # 省/市/区县级，右侧补 3 个 0
    throw InvalidAdcode
```

**还原国标**：9 位 adcode 取前 6 位 `substr(0, 6)` 即得省/市/区县级的国标码。注意街道级（天然 9 位）的前 6 位是其**所属区县**的国标码，不是街道自身的 6 位（街道本身没有 6 位国标码），所以"还原国标"只对 L1/L2/L3 区县这档有意义。

**为什么非 9 位不可**：
- path 用 `/` 分隔 adcode 拼接，长度统一才能稳定切分、稳定做前缀 LIKE。6 位和 9 位混用会让 path 解析变成猜谜。
- 子树查询、排序、编码比对都建立在"同长度可比较"的前提上。补齐是补齐到一个能被所有层级共用的定长，不是拍脑袋选的数字。

## 4. path 路径枚举：子树 LIKE 查询的根基

`path` 是从**根（省级）到自身**的完整 adcode 链，两端和分隔符用 `/` 包裹。例：

```
北京市（省级）       path = /110000000/
北京市市辖区（市级） path = /110000000/110100000/
朝阳区（区县级）     path = /110000000/110100000/110105000/
朝外街道（街道级）   path = /110000000/110100000/110105000/110105026/
```

### 计算方式：递归回溯父链

path 不能靠数据源直接给（多数数据源只给 parentCode），必须**采集完成后自己算**。算法是从当前节点出发，顺着 `parentCode` 往上找父级，直到 `parentCode == null`（省级根），然后把这条链**反转**（根在前、自身在后）拼成路径。

```
function buildPath(region: Region, regionMapByCode: Map<string, Region>) → string:
    chain = []
    cursor = region
    while cursor is not null:
        chain.prepend(cursor.adcode)                       # 自身及各级祖先，从头插入
        cursor = regionMapByCode.get(cursor.parentCode)    # 顺父链上溯
    return "/" + chain.join("/") + "/"
```

`regionMapByCode` 是采集结果按 adcode 建的索引（`Map<adcode, Region>`），保证回溯每一步 O(1)。整批采集完后一次性算所有节点的 path，复杂度 O(N × 平均深度) ≈ O(N)。

**为什么不在采集时增量算**：增量算 path 要求父节点先于子节点出现并已算好，但多数数据源的返回顺序不保证。统一"采完 → 建索引 → 批量回溯算 path"，跟数据顺序解耦，逻辑更简单、更不易错。

### 用途：子树 LIKE 查询

path 的全部意义就是让"查某个节点及其所有后代"退化成一条 SQL 的前缀 LIKE：

```
# 查北京市下所有后代（市/区/街道全部）
WHERE path LIKE '/110000000/%'

# 查朝阳区下所有街道
WHERE path LIKE '/110000000/110100000/110105000/%'

# 查某节点精确自身
WHERE path = '/110000000/110100000/110105000/'
```

不用 path 就得递归 CTE 或 N+1 查询逐层展开子树（不同数据库递归语法不一、性能差）。path 把树形子查询压成一次索引扫描，`path` 字段建普通索引即可高效命中。

**注意 path 包含自身**：例子里"朝阳区"自己的 path 是 `/110000000/110100000/110105000/`，它会被 `LIKE '/110000000/%'` 命中。若要"严格后代不含自身"，用父级 path 拼自身 adcode 做 LIKE 前缀即可。

## 5. 层级拉平：三种区域形态归一到 L1/L2/L3

中国行政区划有三种"不规整"形态，原始数据里层级深浅不一。组件的责任是在 Adapter 内部把它们**全部拉平到统一的 3 档 level**，对外只暴露干净的三层，Collector 和业务方完全不感知这些差异。

`level` 三档：`1` 省 / `2` 市 / `3` 区县或街道。

| 区域形态 | 原始结构 | Adapter 拉平后 | 说明 |
|---------|---------|--------------|------|
| 普通省 | 省(L1) → 地级市 → 区县 → 街道 | 省=1 / 地级市=2 / 区县=3 / 街道=3 | 标准形态，区县和街道都落 L3 |
| 直辖市 | 直辖市 → 区县 → 街道 | 直辖市=1 / 虚拟"市辖区"=2 / 区=3 / 街道=3 | 直辖市没有地级市这层，补一个虚拟的"市辖区/市本级"作 L2（如北京 `110100000`），让区落到 L3，path 凑齐三层 |
| 直筒子市 | 直筒子市 → 街道/乡镇 | （省=1） / 直筒子市=2 / 街道乡镇=3 | 东莞、中山、儋州等没有区县，街道乡镇直接挂市下，作为 L3 |

```
Adapter 内部要做的事：
  1. 识别区域形态（是不是直辖市？是不是直筒子市？）
  2. 决定每个区域的 level（1/2/3）
  3. 直辖市缺的"市辖区"层 → 虚拟补一个 L2 节点（adcode 用市辖区国标补 000）
  4. 补全每个节点的 parentCode，保证链完整可回溯
  → 对外输出：level 只有 1/2/3，path 永远是根到自身的完整链

Collector 拿到的永远是规整的三层 Region，不需要任何 if 判断区域类型。
```

**为什么必须拉平**：
- 业务侧的级联选择器几乎都是"省→市→区/街道"三级。如果吐出来的层级有的两级、有的四级，前端就得为每种区域形态写特判。
- path 子树查询依赖"祖先链完整"。直辖市若不补虚拟市辖区层，北京下区的 path 就会缺一层，前缀匹配的语义就对不齐。
- 拉平是一次性成本（Adapter 里处理），不拉平是处处成本（每个下游都要判形态）。把复杂度收口在 Adapter 是 ROI 最高的取舍。

## 6. 多源 Adapter 抽象：RegionSourceInterface

行政区划数据来源多（高德、民政部、腾讯、统计局……），各家字段名、层级组织、坐标体系、更新频率都不一样。用一个接口**屏蔽厂商差异**，组件只跟接口对话，不跟任何具体数据源耦合。

```
interface RegionSourceInterface:
    # 拉取并产出中性的 Region[]（已做层级拉平、adcode 归一）
    fetch() → Region[]

    # 进度回调（可选）：每完成一个层级通知一次
    # level: 当前完成的层级（1/2/3）
    # completed: 该层级已采集条数（供调用方展示进度条）
    onProgress(callback: (level: int, completed: int) → void)
```

**接口只产出中性 Region**：`fetch()` 返回的是组件定义的 `Region`，不是高德的 `districts` JSON、不是民政部的 XML。数据源私有结构（如高德的 `adcode`/`name`/`center`/`level` 字段、民政部的层级编码）全部在 Adapter 内部翻译成 Region，绝不外泄。

### 切换数据源 = 实现新 Adapter + 改 config

```
# 配置指定用哪个 source
source: amap        # 换成 minzhengbu 只改这一行

# 组件启动时按 config 实例化对应 Adapter
RegionCollector(source: RegionSourceFactory.create(config.source))
```

切数据源不用改一行业码——只要新数据源实现了 `RegionSourceInterface`，把它注册进 Factory，配置切过去就行。这是接口抽象的全部回报：**数据源可替换、可并存、可灰度**。

### onProgress 回调：采集是慢操作

完整采集一次全国到街道级是几千到几万个节点、要拉几十页数据，可能几十秒到几分钟。`onProgress(level, completed)` 让调用方能挂进度条，不是干等到 `fetch()` 返回才知道结果。回调签名固定 `(level, completed)`：
- `level`：当前刚采集完的层级（`1` 省级完成、`2` 市级完成、`3` 区县/街道完成）
- `completed`：该层级累计已采集条数

Adapter 在自己内部的分页/分批循环里按档位触发回调，调用方据此更新 UI 进度。

## 7. RegionCollector：透明管道（无 Redis/DB 依赖）

Collector 是组件的对外总入口，把 source 和 path 计算串成一条**透明管道**——无 Redis、无 DB、无缓存，调一次就是一次完整的采集。

```
function RegionCollector.collect() → Region[]:
    regions = source.fetch()              # 1. 从数据源拉（Adapter 已做层级拉平 + adcode 归一）
    index  = buildIndexByAdcode(regions)  # 2. 建 adcode → Region 索引
    for r in regions:
        r.path = buildPath(r, index)      # 3. 批量回溯算 path
    return regions                        # 4. 返回，结束。不存、不缓存
```

> 注意 Region 是 readonly 值对象。path 的写入不能在原对象上做，要么在构造阶段一次性带 path，要么用值拷贝产出新切片，保持"构造后不可变"语义。

**透明**的含义：输入完全决定输出，Collector 自身不持有任何跨调用的状态。同样的 source + 同样的数据，今天跑和明天跑结果一致；进程重启行为不变。

**为什么无 Redis 依赖**：常见的反模式是"采集结果顺手写 Redis，下次直接读缓存"。一旦这么干：缓存什么时候失效？多个数据源版本怎么隔离？Redis 挂了采集还能不能跑？——采集库被迫去回答一堆存储层的问题。本规范明确：Collector 不碰任何缓存层，缓存是业务方的事（要缓存自己在 Collector 外面包一层）。

**采集 → 存储的边界**：

```
组件边界内（无状态）：        组件边界外（业务方自治）：
  source.fetch()                存储（DB/文件/搜索引擎）
  adcode 归一                   查询（path LIKE / 树形组装）
  层级拉平                      缓存（Redis/进程内）
  path 计算                     版本管理（快照/时间戳/全量覆盖）
  return Region[]               定时刷新策略
```

Collector 把 `Region[]` 交到边界外，任务完成。后面怎么落盘、怎么查、多久刷一次，组件一概不关心。

## 8. 通用场景举例

| 场景 | 用法 | 设计要点 |
|------|------|---------|
| 初始化地址库 | Collector 采全量 → 业务方落 DB（path 建索引） | 一次性导入，后续按需重采覆盖 |
| 省市区街道四级级联选择器 | 前端按 level + parentCode 拉子节点，或后端按 path LIKE 查子树 | path LIKE 一条 SQL 搞定子树，不用递归 |
| 行政区划搜索（按拼音/名称） | 存 `name`/`fullname`/`pinyin`，按 pinyin 前缀或 name 模糊查 | pinyin 空格分隔便于做首字母分组 |
| 地图标注（按坐标展示） | 直接用 `lat`/`lng`（GCJ-02）打点 | 坐标已归一，不用再判坐标系 |
| 多数据源灰度切换 | 新 Adapter 实现 + config 切换 source | 接口隔离，切源不改业务代码 |
| 子树统计（某省下所有区域数） | `WHERE path LIKE '/110000000/%'` 计数 | 前缀 LIKE 走索引，无需逐层展开 |

## Good / Bad

| Good | Bad |
|------|-----|
| 组件只采集输出 `Region[]`，存储由业务方决定 | 组件自己往 DB/Redis 写采集结果 |
| adcode 统一 9 位（6 位补 000，街道天然 9 位） | 6 位和 9 位混用，path 切分靠猜 |
| Region 不可变值对象，构造时算全 path | 可变对象，事后改 path 污染所有持有者 |
| path 是根到自身的完整链，子树用前缀 LIKE | 只存 parentCode，查子树用递归 CTE 或 N+1 |
| 数据源差异在 Adapter 内部拉平层级 | Collector 里写一堆 `if 直辖市`/`if 直筒子市` |
| RegionSourceInterface 屏蔽厂商，切源改 config | 业务代码直接调高德 API、硬编码字段名 |
| Collector 无缓存无存储，纯透明管道 | Collector 顺手写 Redis，引入一堆失效问题 |
| 坐标统一 GCJ-02，Adapter 内部转换 | 各数据源坐标系混存，业务方每处判坐标 |
| onProgress 回调暴露采集进度 | 干等 fetch() 返回，用户以为卡死 |

---

## 红旗 - 停下重新评估

- 准备在组件里写 DB / Redis 调用（违反"只采集不存储"）
- 准备缓存采集结果"省点流量"（缓存是业务方的事）
- 准备让 6 位和 9 位 adcode 共存（path 解析会崩）
- path 不含完整根到自身链，只存直系 parentCode（子树查询退化成递归）
- 在 Collector 里写区域形态特判（层级拉平是 Adapter 的职责）
- 业务代码直接耦合某厂商 API 字段（没法切数据源）
- 坐标不归一，混存 WGS-84 / GCJ-02 / BD-09（地图打点会偏移）
- Region 设计成可变对象、path 事后填（多持有者被意外修改）
- 放宽 readonly 约束用可导出字段 + 外部赋值（破坏不可变语义）

## 防止合理化

| 借口 | 现实 |
|--------|---------|
| "顺手存一份到 DB，省得每次采" | 存了就要管更新、管版本、管失效，组件从工具退化成状态系统 |
| "缓存一下采集结果省流量" | 缓存策略是业务决策，带缓存就是越界。要缓自己在组件外面包 |
| "6 位够用了，补 000 多此一举" | 6 位和 9 位混用，path 拼接和子树 LIKE 全乱套 |
| "path 只存 parentCode，查的时候递归" | 递归 CTE 方言不一、N+1 慢，path 前缀 LIKE 一条搞定 |
| "层级差异让 Collector 判断更灵活" | 灵活 = 每个下游都要判形态。拉平收口在 Adapter 才是省事 |
| "业务直接调高德 API 省一层抽象" | 换数据源时业务全改一遍。抽象一层接口切源只改 config |
| "坐标系差异调用方自己转" | 每个调用方都判一次坐标系，不如采集时归一一次 |
| "Region 先建对象再慢慢填字段" | 可变对象流转后排查污染是噩梦。构造时算全值对象 |
| "readonly 太麻烦，先放开" | 放开不可变语义 = 自带 bug，后续排查无底洞 |

## 何时触发

**以下场景按本规范设计：**

- 新项目需要行政区划（省/市/区县/街道）采集或地址库
- 实现地区级联选择器的数据源、地址搜索、拼音索引
- 接入多个行政区划数据源（高德/民政部/腾讯），需要统一抽象
- 设计 Region 数据模型、adcode 编码规则、path 子树查询
- 排查子树查询慢、坐标系打点偏移、数据源切换困难等问题

**不触发：**

- 只读现有区划代码、查资料（没在设计/实现）
- 纯前端的地址选择交互/动画（不涉及后端采集标准化）
- 业务侧一次性的静态地址字典硬编码（不是系统化的采集库）

## 底线

**组件只采集不存储，adcode 统一 9 位，path 是根到自身的完整链，层级在 Adapter 拉平。**

采集归采集，存储归存储——混在一起，组件就背上了一整套数据生命周期的包袱。9 位定长 adcode 是 path 和子树查询的地基。path 让树形子查询退化成一次 LIKE。层级拉平把区域形态的复杂度收口在 Adapter，下游永远只看干净的三层。

这四条是采集库的地基，任何一条让步都会在数据源一多、区域一杂、查询一深时塌方。

这是不可协商的。
