# 系统化调试

## 概述

随机修复浪费时间还制造新 bug。快速补丁掩盖底层问题。

**核心原则**：尝试修复之前，始终先找根因。修复症状就是失败。

**违反流程的字面意义就是违反调试的精神。**

## 铁律

```
没有先调查根因，不尝试任何修复
```

若你还没完成 Phase 1，你不能提出修复。

## 何时使用

用于任何技术问题：
- 测试失败
- 生产 bug
- 异常行为
- 性能问题
- 构建失败
- 集成问题

**特别在以下时候用：**
- 时间压力下（紧急让猜测变得诱人）
- "就一个快速修复"看起来很明显
- 你已经尝试了多次修复
- 上次修复没工作
- 你不完全理解问题

**不要在以下时候跳过：**
- 问题看起来简单（简单 bug 也有根因）
- 你在赶时间（赶时间保证返工）
- 老板要现在就修（系统化比来回折腾快）

## 四个阶段

必须完成每个阶段才能进入下一个。

### Phase 1：根因调查

**尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过 error 或 warning
   - 它们经常包含确切解决方案
   - 完整读 stack trace
   - 记下行号、文件路径、错误码

2. **稳定复现**
   - 你能可靠触发吗？
   - 确切步骤是什么？
   - 每次都发生吗？
   - 不能复现 → 收集更多数据，不要猜

3. **检查最近变更**
   - 什么改动可能导致了这个？
   - git diff、最近 commit
   - 新依赖、配置变更
   - 环境差异

4. **在多组件系统里收集证据**

   **当系统有多个组件时（CI → build → signing，API → service → database）：**

   **提出修复前，加诊断仪表：**
   ```
   对每个组件边界：
     - 记录什么数据进入组件
     - 记录什么数据离开组件
     - 验证环境/配置传播
     - 检查每一层的状态

   跑一次收集证据，展示在哪里断
   然后分析证据识别失败的组件
   然后调查那个具体组件
   ```

   **示例（多层系统）：**
   ```bash
   # 第一层：Workflow
   echo "=== Workflow 里的 secrets： ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # 第二层：Build 脚本
   echo "=== Build 脚本里的 env 变量： ==="
   env | grep IDENTITY || echo "IDENTITY 不在环境里"

   # 第三层：Signing 脚本
   echo "=== Keychain 状态： ==="
   security list-keychains
   security find-identity -v

   # 第四层：实际签名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这揭示：** 哪层失败（secrets → workflow ✓，workflow → build ✗）

5. **追踪数据流**

   **当错误在调用栈深处时：**

   见本目录的 `root-cause-tracing.md` 完整的反向追踪技术。

   **快速版：**
   - 错误的值从哪里起源？
   - 谁用错误值调了这个？
   - 一直往上追直到找到源头
   - 在源头修复，不在症状处

### Phase 2：模式分析

**修复前找模式：**

1. **找工作的例子**
   - 在同一代码库定位类似的能工作的代码
   - 什么类似且工作的东西，对比坏掉的？

2. **对比参考**
   - 若在实现某个模式，完整读参考实现
   - 不要浏览——读每一行
   - 应用前完全理解模式

3. **识别差异**
   - 工作和不工作的有什么不同？
   - 列出每个差异，无论多小
   - 不要假设"那个不可能有影响"

4. **理解依赖**
   - 它还需要其他什么组件？
   - 什么设置、配置、环境？
   - 它做了什么假设？

### Phase 3：假设与测试

**科学方法：**

1. **形成单一假设**
   - 清楚陈述："我认为 X 是根因，因为 Y"
   - 写下来
   - 要具体，不要模糊

2. **最小化测试**
   - 做最小可能改动来测试假设
   - 一次一个变量
   - 不要一次修多个

3. **继续前验证**
   - 工作了？是 → Phase 4
   - 没工作？形成新假设
   - 不要在上面叠加更多修复

4. **当你不知道时**
   - 说"我不理解 X"
   - 不要假装知道
   - 寻求帮助
   - 多研究

### Phase 4：实现

**修复根因，不修复症状：**

1. **创建失败测试用例**
   - 最简单的可能复现
   - 可能的话用自动化测试
   - 没框架就用一次性测试脚本
   - 修复前必须有
   - 用 `shw-tdd` skill 写规范的失败测试

2. **实现单一修复**
   - 解决已识别的根因
   - 一次一个改动
   - 不"顺手"改进
   - 不捆绑重构

3. **验证修复**
   - 测试现在通过？
   - 没破坏其他测试？
   - 问题真的解决了？

4. **若修复不工作**
   - 停下
   - 数：你尝试了几次修复？
   - 若 < 3：回 Phase 1，用新信息重新分析
   - **若 ≥ 3：停下并质疑架构（下方步骤 5）**
   - 不要在没有架构讨论前尝试第 4 次修复

5. **若 3+ 次修复失败：质疑架构**

   **指示架构问题的模式：**
   - 每次修复暴露新的共享状态/耦合/在不同地方的问题
   - 修复需要"大规模重构"才能实现
   - 每次修复在别处制造新症状

   **停下并质疑根本性的东西：**
   - 这个模式根本合理吗？
   - 我们是不是"凭惯性硬撑"？
   - 该重构架构还是继续修症状？

   **尝试更多修复前和你的用户讨论**

   这不是失败的假设——这是错误的架构。

## 红旗 - 停下并走流程

若你发现自己在想：
- "先临时修一下，以后再调查"
- "就改 X 试试看能不能用"
- "加多个改动，跑测试"
- "跳过测试，我手动验证"
- "大概是 X，让我修那个"
- "我不完全理解但可能行"
- "模式说 X 但我换个方式改"
- "主要问题是这些：[没调查就列修复]"
- 在追踪数据流前提出方案
- **"再试一次修复"（已经试过 2+ 次）**
- **每次修复在不同地方暴露新问题**

**这些全意味着：停下。回 Phase 1。**

**若 3+ 次修复失败：** 质疑架构（见 Phase 4.5）

## 用户提示你做错了的信号

**留意这些纠正：**
- "那个不是没发生吗？" - 你假设而没验证
- "它会告诉我们吗？" - 你应该加证据收集
- "别猜了" - 你没理解就提修复
- "深入想这个" - 质疑根本性问题，不只是症状
- "我们卡住了？"（沮丧） - 你的方法不工作

**看到这些时：** 停下。回 Phase 1。

## 常见合理化借口

| 借口 | 现实 |
|--------|---------|
| "问题简单，不需要流程" | 简单问题也有根因。流程对简单 bug 很快。 |
| "紧急，没时间走流程" | 系统化调试比猜-检查的折腾快。 |
| "先试这个，再调查" | 第一次修复定下基调。从一开始就做对。 |
| "确认修复有效后再写测试" | 未测的修复不会持久。先测试证明它。 |
| "一次多个修复省时间" | 无法隔离哪个起作用。还制造新 bug。 |
| "参考太长，我改一改模式" | 部分理解保证出 bug。完整读它。 |
| "我看到问题了，让我修" | 看到症状 ≠ 理解根因。 |
| "再试一次修复"（失败 2+ 次后） | 3+ 次失败 = 架构问题。质疑模式，别再修。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 读错误、复现、查变更、收集证据 | 理解了什么和为什么 |
| **2. 模式** | 找工作的例子、对比 | 识别差异 |
| **3. 假设** | 形成理论、最小测试 | 确认或新假设 |
| **4. 实现** | 建测试、修、验证 | Bug 解决、测试通过 |

## 当流程揭示"无根因"

若系统化调查揭示问题真的是环境的、时序相关的、或外部的：

1. 你完成了流程
2. 文档化你调查了什么
3. 实施适当处理（重试、超时、错误信息）
4. 加监控/日志为未来调查

**但是：** 95% 的"无根因"案例是调查不完整。

## 辅助技术

这些技术是系统化调试的一部分，在本目录可用：

- **`root-cause-tracing.md`** - 通过调用栈反向追踪 bug 找原始触发点
- **`defense-in-depth.md`** - 找到根因后在多层加验证
- **`condition-based-waiting.md`** - 用条件轮询替代任意超时

**相关 skill（shw-plugins 内）：**
- **shw-tdd** - 用于创建失败测试用例（Phase 4 步骤 1）
- **shw-verify** - 声称成功前验证修复有效

## 现实影响

来自调试会话：
- 系统化方法：15-30 分钟修复
- 随机修复方法：2-3 小时折腾
- 一次修复成功率：95% vs 40%
- 引入新 bug：近乎零 vs 常见
