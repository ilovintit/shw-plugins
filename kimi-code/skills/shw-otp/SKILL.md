# 验证码设计范式

## 概述

本 skill 是验证码（短信码 / 邮箱码）的**设计范式**。

**核心原则**：四键协同 + 验证与消费分离 + 防爆破兜底。一串 6 位验证码只有 100 万种可能，没有频率限制和失败锁定，爆破只是一个脚本几秒钟的事。

**违反这个原则就是把验证码当成"发出去就安全"**：攻击者 60 秒内刷你 1 万次生成把短信费打爆、或者 100 万次暴力试出其中一条、又或者用户验证通过了但业务提交失败后码已经没了无法重试——所有这些根因都是"只存了码本体，没有协同键，没有分离验证和消费"。

**跨端协同**：验证码系统经常跨端——同一份 Redis 上有发码端和校验端（可能是不同语言实现，也可能是生成服务与校验服务两个独立服务）。**两端 Redis key 命名必须逐字相同**，否则发码端写的码校验端读不到、防爆破计数各算各的。

## 铁律

```
验证码用 Redis 四键协同，绝不只存一个码本体
生成用密码学安全随机（crypto/rand），绝不 rand()
频率限制用 SET NX EX，绝不"查再写"
防爆破靠失败计数 + 锁定，绝不"无限次比对"
验证（Verify）不删码，消费（Consume）才删码
fail 的 TTL 只在首次失败设置，绝不每次失败重设
关键失败必须告警，绝不静默吞掉
两端 Redis key 命名逐字相同
```

凭"存一个 key 加 TTL 够用了"、"验证对了顺手删掉就行"、"用系统随机数差不多"的直觉做事——全部是在给爆破留后门。

## Redis 四键协同

验证码系统用四个 Redis key 协同工作，**不要只存码本体**。默认前缀 `vc`（verify-code），四个键的命名约定**逐字固定**。

### key 命名约定（逐字固定）

```
码本体    vc:{scene}:{key}          ← {prefix} 默认 vc
频率限制  vc:rl:{scene}:{key}       ← rl = rate limit
失败计数  vc:fail:{scene}:{key}     ← fail = fail count
锁定标记  vc:lock:{scene}:{key}     ← lock = lock
```

**两端必须逐字相同**：前缀 `vc`、冒号分隔、`rl`/`fail`/`lock` 段名、`{scene}:{key}` 段顺序——全部固定字面量。换语言、换服务端时只改"如何调用 Redis"，不改 key 字面量。否则生成端写 `vc:LOGIN:13800000000`、校验端读 `verify_code:login:138...`，码发出去却校验不到，防爆破计数也各算各的。

### 键 1：码本体 `vc:{scene}:{key}`

| 项 | 值 |
|----|----|
| 内容 | 验证码本体（6 位数字） |
| TTL | 300s（5 分钟） |
| 操作 | Generate 写入（`SET ... EX 300`），Consume 删除 |

存的就是那串 6 位数字。TTL 5 分钟是用户体验和安全的平衡：太短用户来不及输，太长爆破窗口大。

### 键 2：频率限制 `vc:rl:{scene}:{key}`

| 项 | 值 |
|----|----|
| 内容 | 频率限制标记（存在即代表在冷却期内） |
| TTL | 60s（rateInterval，默认 60s） |
| 操作 | Generate 用 `SET ... NX EX 60` |

**`rl` = rate limit**。用 `SET key value NX EX 60` 原子操作：同一 `key + scene` 在 60 秒内只能生成一次。这是防短信轰炸的第一道闸——攻击者拿同一个手机号刷 1 万次生成，只有第一次成功，剩下 9999 次被 NX 挡掉。

**必须用 SET NX EX，不是"先 GET 判断再 SET"**：后者是两步操作，并发下两个请求都读到"不存在"然后都写入，频率限制形同虚设。SET NX EX 是原子的，Redis 单线程保证只有一个请求写入成功。

### 键 3：失败计数 `vc:fail:{scene}:{key}`

| 项 | 值 |
|----|----|
| 内容 | 验证失败次数 |
| TTL | 3600s（**首次 INCR 时才设置**） |
| 操作 | Verify 失败时 `INCR`（首次再 `EXPIRE 3600`）；Consume 时删除 |

**`fail` = fail count**。每次校验失败 `INCR +1`。**只在首次 INCR 时设置 TTL 3600s**（INCR 本身不带 TTL，要 INCR 完判断返回值是 1 再 EXPIRE）。这个计数窗口 1 小时：1 小时内累计失败达上限就锁定。

**为什么 TTL 只设在首次而不每次**：TTL 是"计数窗口"，第一次失败开始计时 1 小时，后续失败只累加**不改 TTL**。如果每次失败都重设 TTL，攻击者只要持续试错就能无限延长窗口，永远到不了上限——计数器形同虚设。

### 键 4：锁定标记 `vc:lock:{scene}:{key}`

| 项 | 值 |
|----|----|
| 内容 | 锁定标记（存在即代表已被锁定） |
| TTL | 3600s（1 小时） |
| 操作 | 失败达上限（默认 5 次）时 `SET ... EX 3600`；Verify 入口 `EXISTS` 检查 |

**`lock` = lock**。失败计数达上限（默认 5 次）时写入，锁定 1 小时。锁定期间 Verify 直接返回 false（连比对都不做），Generate 通常也应拒绝（已被锁定的号不应再发新码）。这是防爆破的最后一道闸。

### 四键如何协同

四个键分别卡在三流程的不同节点上：

```
Generate（生成）：
  rl key ──SET NX EX──→ 写入成功?
     否 → 拒绝（冷却期内，防轰炸）
     是 → 写码本体（SET EX 300）

Verify（校验）：
  lock key ──EXISTS──→ 存在? → 直接返回 false（锁定中，不比对）
     不存在 → 比对码本体
                相等   → 返回 true（不删码！）
                不等   → fail key INCR（仅首次 EXPIRE 3600）
                          fail ≥ 上限 → 写 lock key（EX 3600）
                          返回 false

Consume（消费）：
  DEL 码本体 + DEL fail key
```

**rl 卡生成、lock/fail 卡校验**：码本体本身是中性的，安全全靠另外三个键把守住入口和出口。

## Generate 流程

生成一串新验证码，三步：

```
function generate(scene, key, codeLength = 6):
    # 1. 频率限制（SET NX EX 原子操作）
    ok = redis.set("vc:rl:" + scene + ":" + key, 1, NX, EX 60)
    if ok == nil:                          # key 已存在 = 冷却期内
        return error("RATE_LIMITED")       # 拒绝生成，防轰炸

    # 2. 密码学安全随机生成 6 位数字
    code = secureRandomDigits(codeLength)  # 底层 crypto/rand，禁止 math/rand
    #    ❌ math/rand / 时间戳取模 / 未播种伪随机  → 可预测，可爆破
    #    ✅ crypto/rand  → 操作系统级熵源，不可预测

    # 3. 存入码本体（TTL 300s）
    redis.set("vc:" + scene + ":" + key, code, EX 300)

    return code
```

**密码学安全随机不可妥协**：6 位验证码空间本就只有 100 万，如果随机数可预测（用时间戳、用未播种的伪随机），攻击者能推算出生成的码，频率限制和锁定都拦不住——因为他根本不需要试错。

## Verify 流程（防爆破）

校验用户输入的验证码，五步，**Verify 不删码**：

```
function verify(scene, key, userInput):
    # 1. 检查锁定（锁定中直接拒绝，不比对、不消费）
    if redis.exists("vc:lock:" + scene + ":" + key):
        return false                       # 已锁定

    # 2. 比对码本体
    stored = redis.get("vc:" + scene + ":" + key)
    if stored == userInput:
        return true                        # 验证通过，但不删码！

    # 3. 比对失败：失败计数 +1
    count = redis.incr("vc:fail:" + scene + ":" + key)
    if count == 1:                         # 仅首次失败设计数窗口
        redis.expire("vc:fail:" + scene + ":" + key, 3600)
        # ⚠ 此处 EXPIRE 写入失败必须告警（见"关键失败告警"）

    # 4. 达上限写锁定（默认 5 次）
    if count >= 5:
        redis.set("vc:lock:" + scene + ":" + key, 1, EX 3600)
        # ⚠ 此处 lock 写入失败必须告警（见"关键失败告警"）

    # 5. 返回失败
    return false
```

**为什么 Verify 不删码**：验证（Verify）和消费（Consume）是两个独立操作。Verify 通过只代表"用户确实收到了码"，删码时机推迟到 Consume（业务真正成功之后）。详见下文。

## Consume 流程（验证与消费分离）

**验证（Verify）和消费（Consume）是两个独立操作**。验证通过后，业务侧显式调用 Consume 才真正删码：

```
function consume(scene, key):
    # 验证通过后由业务侧显式调用，才真正删码
    redis.del("vc:" + scene + ":" + key)        # 删码本体
    redis.del("vc:fail:" + scene + ":" + key)   # 清失败计数
    # 注意：不碰 rl（频率限制是生成侧的事）和 lock（已验证通过说明未锁定）
```

### 为什么不验证成功就删码

```
❌ 错误做法：Verify 成功 → 立刻删码 → 业务提交
   风险：删码后业务提交失败（网络抖动、数据库冲突），
        用户重试时码已失效，必须重新获取短信，体验差且浪费短信费

✅ 正确做法：Verify 成功 → 业务提交 → 提交成功后 Consume 删码
   安全：业务失败可重试（码还在），业务成功才删码
```

把删码时机推迟到业务真正成功之后，避免"验证成功但业务失败后码已失效"的死锁。

### 典型调用顺序

```
前端：用户输入码 → 调业务接口
后端业务接口：
   1. verify(scene, key, userInput) → false 直接返回"验证码错误"
   2. 执行业务逻辑（改密码 / 注册 / 登录...）
   3. 业务成功 → consume(scene, key) 删码
   4. 业务失败 → 不调 consume，码还在，用户可重试
```

## 场景隔离

验证码的 key 由 `{scene}:{key}` 两段组成。**`scene` 是场景维度**，保证同一手机号在不同业务场景的验证码互不干扰。

### 内置场景枚举

| scene 枚举 | 含义 |
|-----------|------|
| `LOGIN` | 登录 |
| `REGISTER` | 注册 |
| `RESET_PASSWORD` | 重置密码 |
| `CHANGE_PHONE` | 换绑手机号 |
| `GENERIC` | 通用（兜底） |

**同一手机号，LOGIN 的码不能用于 RESET_PASSWORD**。否则攻击者拿到登录码就能重置密码——场景隔离是安全边界，不是多此一举。

四键都带 `scene`，所以频率限制、失败计数、锁定也按场景独立计算：LOGIN 场景被锁定了，不影响 REGISTER 场景继续发码。

## 关键失败必须告警

四键协同里有两处"防爆破关键写入"，**失败必须告警**，不能静默吞：

| 关键写入 | 失败后果 | 处置 |
|---------|---------|------|
| 失败达上限写 lock key（`SET vc:lock:... EX 3600`） | 攻击者继续试错直到猜中，锁定形同虚设 | 告警 + 记日志 |
| fail 首次 `EXPIRE` 设 TTL | 计数窗口失效（要么永远不到上限、要么 TTL 漂移） | 告警 + 记日志 |

**这两处失败会导致防爆破机制失效**：lock 写不进去 = 攻击者无限试错；fail TTL 没设上 = 计数窗口错乱。系统看起来还在跑（验证码还能发、还能校验），但安全防线已经穿了，只有告警能让人发现。

静默吞掉这两类错误 = 默认接受被爆破的风险。宁可误报，不可漏报。

## 通用场景举例

| 场景 | scene | 说明 |
|------|-------|------|
| 手机号登录 | `LOGIN` | 短信码，5 分钟有效，失败 5 次锁 1 小时 |
| 新用户注册 | `REGISTER` | 短信码，与登录码隔离，互不影响 |
| 忘记密码 | `RESET_PASSWORD` | 短信码，高安全场景，锁定阈值可调低（如 3 次） |
| 换绑手机 | `CHANGE_PHONE` | 短信码，新旧手机号各发各的，scene 同但 key 不同 |
| 邮箱验证 | `GENERIC` | 邮箱码，key 用邮箱地址，机制完全相同 |

## Good / Bad

| Good | Bad |
|------|-----|
| 四键协同（码 + rl + fail + lock） | 只存一个码本体加 TTL |
| 生成用 crypto/rand 密码学随机 | 用 math/rand / 时间戳 / 伪随机 |
| 频率限制用 SET NX EX 原子操作 | 先 GET 判断再 SET（并发穿透） |
| 失败计数 + 锁定防爆破 | 无限次允许比对 |
| Verify 不删码，Consume 才删码 | Verify 成功立刻删码 |
| fail 仅首次设 TTL 3600s 定窗口 | 每次失败都重设 TTL（窗口可被无限延长） |
| 场景隔离（scene 维度） | 所有业务共用一个码 |
| 两端 key 命名逐字相同 | 各端各起一套 key 命名 |
| lock 写失败 / fail TTL 失败告警 | 静默吞掉错误 |

## 红旗 - 停下重新评估

- 准备只存一个 Redis key 存验证码（违反四键协同）
- 准备用系统伪随机数生成验证码（违反密码学随机）
- 准备"先查频率限制标记再写入"（违反 SET NX EX 原子性）
- 准备 Verify 成功后立刻删码（违反验证与消费分离）
- 准备每次失败都重设 fail 的 TTL（违反计数窗口固定）
- 准备所有业务共用一个 scene（违反场景隔离）
- 准备让另一端用不同的 key 命名（违反两端逐字相同）
- lock key 写失败或 fail TTL 设置失败后静默继续（违反关键失败告警）
- 准备把"验证通过"等同于"业务成功"直接删码

## 防止合理化

| 借口 | 现实 |
|--------|---------|
| "存一个 key 够用了，四个太麻烦" | 一个 key 没有频率限制 = 短信被打爆，没有锁定 = 被爆破 |
| "math/rand 也是随机的，差不多" | 可预测的随机 = 不用试错就能猜中，频率和锁定全废 |
| "先查再写逻辑清楚" | 并发下两步之间会穿透，频率限制失效 |
| "验证对了顺手删掉，省一次调用" | 业务失败后码没了，用户重新获取短信，体验差还费钱 |
| "失败次数每次重设 TTL 更严格" | 攻击者持续试错就能无限延长窗口，永远到不了上限 |
| "都是给同一个手机号发的，scene 合并吧" | 登录码能重置密码，安全边界没了 |
| "另一端 key 我自己起个更顺眼的命名" | 两端 key 不一致，发码端写的码校验端读不到，防爆破各算各的 |
| "告警太吵，这两处错误忽略就行" | 忽略 = 防爆破静默失效，被爆破了你都不知道 |

## 何时触发

**以下场景必须按本范式设计：**

- 新项目需要短信验证码、邮箱验证码功能
- 现有验证码功能要加防爆破、频率限制
- 设计跨端统一的验证码 key 命名（发码端与校验端共享同一套 Redis 命名）
- 从一种语言迁移验证码模块到另一种语言
- 生成端与校验端分属不同服务、需要共享 Redis 协同
- 排查短信被盗刷、验证码被爆破、用户验证后码失效、两端码对不上等问题

**不触发：**

- 只读现有验证码代码、查资料（没在设计 / 实现）
- 纯图形验证码（滑块 / 点选 / 字符图片，那是另一种机制）
- 静态密码 / API Token（不是一次性验证码）

## 底线

**验证码用四键协同，验证不消费、消费才删码，两端 key 命名逐字相同，关键失败必须告警。**

四键协同防爆破和防盗刷，SET NX EX 保证频率限制原子性，验证与消费分离防"验证成功业务失败"的死锁，密码学随机防预测，fail 仅首次设 TTL 防窗口被无限延长。这五条是验证码系统的地基，任何一条让步都会在攻击者上门时塌方。

key 命名约定逐字固定——换语言改的是"怎么调 Redis"，不是"key 长什么样"。

这是不可协商的。
