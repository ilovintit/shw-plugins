# spec 为锚的无状态全量审计

治"specs 随时间变质"：代码持续演进而 spec 停留在旧口径，或多次 patch 合并后 specs 内部自相矛盾。本 skill 以 spec 为锚做**无状态全量审计**——每轮全量、幂等，修复方向唯一（spec 对齐代码现实）。既供 agent 定时任务无人值守调用，也供用户手动调用。

## 触发场景

- agent 定时任务（cron / 闲时 / 凌晨定时）做 specs 审计核对
- 用户手动要求"全面审查 / 核对 specs"
- 需要 specs 一致性 / 完备性检查

## 工作区纪律：选择性暂存

**不做工作区前置检查**——roadmap 等合法流程跑完可能留下未提交改动，审计照常执行。安全性由选择性暂存承接：

- 每类修复分组本地 commit（**绝不 push**）时，只 `git add <本轮修复实际触碰的文件显式路径>`
- **禁止 `git add -A` / `git add .`**——确保用户未提交改动不被卷入审计 commit

**同名文件卷入风险**：若审计修复的文件恰与用户未提交改动同文件，按路径暂存会把用户改动一并卷入该 commit。报告须注明这种情况，并提示该 commit 可定向 revert。

## 审计工作流程

### 1. 全量读取：建立审计基线

**无状态纪律：每一轮都是全量。** 禁止依赖"上次审计时间""审计状态文件""变更窗口"来缩小范围——审计的检测能力不锚定在任何时间基点上；specs 的变质来自任意一次 change 归档，只有全量对账才能兜住。操作本身幂等：跑两遍结果一样。

读取范围：

- `specs/` 下**全部** capability 主 spec（`specs/<capability>/spec.md`）
- 项目元文档：AGENTS.md（以及 README.md 等描述架构/口径的部分）
- 结构单元清单（供第 4 阶段覆盖检查用）：
  - 插件类项目：分发单元名单——skills/、commands/、MCP、adapters 各目录下的单元
  - 一般项目：源码顶层模块（src/ 一级目录）、API 路由组等有限结构单元

### 2. 断言提取与逐条对账：spec 断言 → 代码证据

从每份 spec / 元文档提取**可验证断言**，逐条处理：

- 存在性断言（"存在 X""有 X 功能"）
- 数量口径断言（"共 18 个""2 个 MCP"）
- 路径引用断言（"位于 src/plugin/adapters/""命令文件在 commands/ 下"）
- SHALL / MUST 行为断言（"X 发生时系统 SHALL 做 Y"）

取证方式按断言类型分档：

- **机械层优先**：存在性 / 数量 / 路径断言用 ls、grep、文件内容比对直接取证
- **行为断言定点读码**：定位实现该行为的代码文件精读，确认行为与断言一致（不全文通读代码，只读断言指向的位置）

对账结果二选一：

- **相符** → 通过，进下一条
- **不符** → 立即修复。**修复方向唯一：spec 对齐代码现实**（代码是事实源）。禁止"顺手改代码让代码对齐 spec"

写权限硬边界：**只写 specs/ 与元文档（AGENTS.md 等），绝不修改任何代码文件。** 若对账后发现是代码本身有误（如某变更没有 change 记录、代码行为疑似 bug），只在报告标注，不代为裁决、不动代码。

**证据不足的断言**（矛盾且代码现实与 git 历史都判不了方向的）：列入报告"待人工判断"区并附双方证据——不瞎修、不静默跳过。

### 3. specs 内部互检：矛盾 / 重复 / 术语漂移

全量读完后做 specs 内部三方互检（专治"每份各自正确、合起来出错"的问题）：

- **capability 间矛盾**：同一事实在不同 capability 里口径不一致（数量不同、机制描述相反、路径不同）
- **语义级重复**：同一件事用不同措辞写了两遍（跨 capability 或同一份 spec 内）
- **术语漂移**：同一机制多名并存（新旧叫法混用，通常来自多次 patch 合并）

发现即修（修复同样只动 specs / 元文档）。判不了方向的进"待人工判断"。

### 4. 模块级覆盖检查：完备性哨兵

以第 1 阶段的结构单元清单为锚，逐单元在**全部 specs + 元文档**中 grep 其名称：

- **有提及** → 覆盖通过
- **零提及** → **只报告、不修复**。进报告"完备性缺口"区，附零命中证据（grep 命令与零命中结果），并给两条处置建议：
  1. 确认该单元需要 spec 覆盖 → 开一个 change 走 propose 流程补 delta spec（补需求超出审计的修复权限）
  2. 确认该单元不该存在 → 代码侧处理（同样超出审计权限，只指出不代做）

**断言级完备性明确不检查**（不逐函数 / 逐行为反查 spec 是否写到）——那是噪音区，机械检查几乎必然海量误报。覆盖哨兵只锚定**模块级**有限结构单元。

### 5. 修复落盘：分组 commit + 证据前置 + 重写覆盖核验

**证据前置**：每项修复在进 commit 前必须已附证据——grep 命中位置 / ls 计数对比 / 文件内容比对结果。无证据的修复不落盘。

**分组 commit**：按问题组分别本地 commit（**绝不 push**），消息前缀统一 `chore(spec-audit): …`（如 `chore(spec-audit): 修正分发数量口径 14→18`）。暂存严格按"工作区纪律：选择性暂存"执行：只 `git add <本轮修复实际触碰的文件显式路径>`，禁止 `git add -A` / `git add .`，确保用户未提交改动不被卷入。报告必须含 commit → 修复内容映射，让每类修复可定向 revert；若修复文件与用户未提交改动同文件，须在报告注明（见"同名文件卷入风险"）。

**整篇重写的覆盖核验**：当某 capability 的补丁层过厚时，逐条修补不如整篇重写。触发判据（满足其一即可考虑重写）：

- 同一 Requirement 段内出现多处互不融合的补丁表述（连续"另外 / 注意 / 不再"式修正语，通读已无法连贯理解原意）
- 同一机制的描述散落在多个 Requirement 中且口径已分叉
- 该 capability 在近期多轮归档中反复被 MODIFIED，补丁明显堆积

重写纪律：

1. 重写前先摘出该 spec 的**原 Requirement 清单**（全部标题行）
2. 重写稿完成后**逐条对照原清单**：每条原 Requirement 在新稿中要么保留、要么合并（指明合并进哪条）、要么删除
3. 任何被丢弃 / 合并的 Requirement 必须有明确理由列入报告——**不得静默丢需求**
4. **覆盖核验不过，该重写不许 commit 落盘**——放弃整篇重写，回到逐条修

### 6. 复验收敛：重新对账确认闭环

全部修复落盘后**必须复验**：重新执行第 2 阶段的断言对账循环，确认全部断言收敛——复验用的是本轮修复之后的重新对账结果，不是修复前的旧证据。

- 修复引入了新问题（改 A 引爆 B）→ 必须继续处理，直至收敛
- 收敛结果写入报告"一致性核验结果"区

未通过复验收敛，MUST NOT 宣布审计完成。

## 报告形态

报告**只在会话内展示**：不形成文件、不进 git、无任何持久化产物（禁止把报告写成 md 文件落盘）。五区结构：

1. **自动修复明细**：每类修复 + 对应 commit + 修复内容 + 证据；若有同名文件卷入风险（修复文件与用户未提交改动同文件），在此注明并提示该 commit 可定向 revert
2. **完备性缺口（待裁决）**：零提及结构单元清单 + 零命中证据 + 两条处置建议
3. **待人工判断项**：无法裁决的问题 + 双方证据（或"无"）
4. **一致性核验结果**：复验收敛确认 + 修复引入新问题的处理记录
5. **审计健康度概览**：本轮整体画像——断言总数 / 通过 / 修复 / 零提及单元数 / 待人工项数 / commit 数，供人工跨轮比对趋势

## 定时任务 prompt 示例

本 skill 支持无人值守定时执行。配置方式：**用户在自己 agent 工具的定时任务功能中手动粘贴以下 prompt 文案**——插件侧不做任何自动注册。锚点建议选"早上 / 闲时"而非精确凌晨：宿主机凌晨可能处于休眠状态，定时任务跑不起来。

```
加载 shw-spec-audit skill，对本仓库执行一次 spec 全量审计：按 skill 工作流程完整执行
（全量读取 → 断言对账 → 内部互检 → 覆盖检查 → 修复落盘 → 复验收敛），
最后输出五区报告。全程无人值守：不问问题、不等确认。
```

## 约束

- **无状态全量**：每轮全量、幂等；禁止创建或依赖审计状态文件 / 上次审计时间 / 变更窗口
- **只写 specs/ 与元文档**：绝不修改任何代码文件；代码本身有误只在报告标注，不代为裁决
- **修复方向唯一**：spec 对齐代码现实（代码是事实源）
- **零提及单元只报告不修复**；断言级完备性明确不检查
- **本地 commit 绝不 push**：分组 commit 前缀 `chore(spec-audit): …`，只显式 `git add` 本轮修复触碰的文件（禁止 `git add -A` / `git add .`），报告含 commit → 修复映射；同名文件卷入风险须在报告注明
- **证据前置**：无证据（grep / ls / 内容比对）的修复不进 commit
- **整篇重写必须过覆盖核验**：核验不过不落盘；被丢弃 / 合并的 Requirement 必须列理由进报告
- **复验收敛才算完成**
- **报告只在会话内**：不落文件、不进 git、无持久化产物
- **无人值守自包含**：不问问题、不等确认、不等任何用户输入
- **工具无关**：不绑定任何单一 agent 工具；定时任务由用户在自己工具的定时任务功能中手动配置
