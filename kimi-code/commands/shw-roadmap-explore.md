大任务深度探索与 roadmap 生产：先做深度调查，再把大任务固化为 roadmap（北极星 / 方向解法 / 终态描述原料 / 执行轨迹）——产出的是方向锚与路径判断，不是 change 清单。

与 /shw-propose 的边界：propose 管单个 change 的小循环；本命令管需要拆成多个 change 编排的大任务的方向锚定。

---

**输入**：`/shw-roadmap-explore` 后的参数是 roadmap 名（kebab-case），或描述用户想做的大任务。

**步骤**

1. **若未提供输入，问用户想做什么**

   用向用户提问（开放性问题，不要预设选项）问：
   > "你想做什么大任务？描述你想构建或改造的东西。"

   从描述中推导出 kebab-case roadmap 名（如 "重构权限系统" → `refactor-auth`）。

   **重要**：理解用户想做什么之前不要继续。

2. **深度调查**

   产出 roadmap 前必须先调查项目现状：
   - 读项目代码结构——模块划分、目录组织
   - 读与任务相关的现有实现——集成点、已有模式、隐藏复杂度
   - 读项目 AGENTS.md 等约定文档——仓库规范、技术栈约束

   调查完成后向用户复述理解：现状是什么、任务触及哪些模块、有什么约束与风险。**用户确认后才继续**。

   **不调查不产出**：禁止跳过调查直接产出方向解法。

3. **校准方向解法**

   基于调查结论，与用户校准出 roadmap 的三项产出：

   - **北极星**：一句话终态表述——这个 roadmap 达成时世界是什么样。它是执行期所有判断的方向锚，写定后稳定不动；若执行中发现北极星本身不再正确（意图层偏离），编排者停下向用户陈述、用户裁决（见 shw-goal-drive skill）
   - **方向解法**：初始路径判断——大致怎么走，可以有"先打通 X，再做 Y"的阶段感。这是**初始判断而非承诺清单**：执行期认知提升后允许修正，change 怎么拆是执行期的事，探索期不预拆
   - **终态描述原料**：意图达成时系统具备什么的自然语言逐条描述——/shw-roadmap-verify 转写终态描述句集的原材料

   向用户逐项展示并说明，**用户确认后才落盘**；有异议先调整再确认。

   **禁止产出 change 名单表**：方向解法是文字性的路径判断，不是带状态的 change 清单——change 的存在与状态以 `.changes/` 目录为准，roadmap 不替 change 记账。

4. **写 roadmap.md**

   创建 `.roadmaps/<name>/roadmap.md`（仓库顶层 `.roadmaps/` 目录，不进 `.changes/`——shw-spec 的 change 扫描会把它误认为 change）。按下方模板写入，执行轨迹初始为空：

   ````markdown
   # Roadmap: <name>

   ## 北极星

   <一句话终态表述：这个 roadmap 达成时世界是什么样。写定后稳定不动——执行期所有判断的方向锚>

   ## 方向解法

   <!-- 初始判断，可被执行轨迹修正 -->

   <初始路径判断：大致怎么走，可以有"先打通 X，再做 Y"的阶段感。这是判断参考，不是承诺清单>

   ## 终态描述原料

   <!-- /shw-roadmap-verify 转写终态描述句集的原材料 -->

   - <意图达成时系统具备什么——自然语言逐条描述 1>
   - <意图达成时系统具备什么——自然语言逐条描述 2>

   ## 执行轨迹

   <!-- 初始为空。执行期由编排者每轮追加：拆了什么 change / 学到什么 / 方向解法是否修正 -->
   ````

5. **提示下一步**

   roadmap 落盘后，向用户输出：

   ```
   roadmap 已创建：.roadmaps/<name>/roadmap.md
   下一步：运行 /shw-roadmap-verify <name> 把终态描述原料转写为终态描述句集
   ```

**约束**

- 若大任务实际单个 change 就能承载，不硬拆——建议直接 /shw-propose
- 本命令只负责 roadmap 的初始落盘；执行轨迹的追加由编排者在执行期完成，不在本命令范围
