发布前的**双模型对抗终审**：milestone 交付完成要发布时、版本要发布时、或想对任意范围做一次全面体检时使用。机制——**两个不同的大模型独立做同题对抗审查**（同题独立防串供），本命令负责任务包组装、审查 prompt 生成、报告回收对账。

**审查范围不做预设，由用户输入确定**——输入什么就审什么：一个 milestone、一段版本区间（`<refA>..<refB>`）、整个仓库、某次变更集、某个模块，都行；本命令把输入翻译成具体的 git 范围 + 变更清单。输入含糊到无法确定范围时问清楚再动，不猜。

---

**阶段一：组装审查任务包**（本命令 agent 做）

1. **从输入解析范围**：
   - 输入提到 milestone → 经 gitea-mcp 读该 Milestone 全部 Issue（checklist 状态）+ 已合并 PR 清单（含 CI run 链接）+ git 基线（上个发布 tag 或该 Milestone 首个 PR 的 base → HEAD）
   - 输入是 git 范围/其他形式 → `git diff --stat` 对应区间（全仓则取整体现状）
   - 解析结果（范围实参：ref 区间、Issue/PR 数）向用户复述确认后组包
2. **组包**：变更 diff（按模块分组、超长时分片）+ 验收证据（checklist × CI 绿记录）+ 关键上下文（AGENTS.md、涉及的 docs/prd、docs/architecture 章节）
3. **生成审查 prompt ×2**：两份**完全相同**（同题独立），文本按下述模板填充范围实参（`<...>` 占位）：

   > 现在 <范围声明> 即将发布，请你深入阅读、理解并对抗性 review 本项目<范围基线>的所有修改（<refA>..<refB>，N 个 Issue、M 个已合并 PR）：
   > 1. 对它可能覆盖到的范围和影响面做一个全面深入的评估与总结，对产生的不兼容性（接口契约 / 数据结构 / 行为变更 / 依赖）做一个彻底全面的梳理。
   > 2. 发起一遍深度的 review 与测试验证，从各种角度和维度去测试（包括单元测试、集成测试、验收测试、冒烟测试等的真实覆盖与 CI 证据核查），确保这次的修改合理、有效、正确，且没有引入新的问题。
   > 这是一个很大的工程。深入思考后自己生成一个计划再执行，最终输出结构化报告（发现清单：问题 / 依据 / 严重级 / 建议位置）。

   任务包与 prompt 一起输出（或落临时文件），交用户分发。

**阶段二：双模型分发**（用户做）

分别贴给**两个不同的大模型**（各自独立执行，不互通信息、不给对方报告）。

**阶段三：回收对账合并**（本命令 agent 做）

用户把两份报告贴回后：

1. **逐条对账**：
   - **重合发现**（两模型都报）→ 互证，直接采信进修复清单
   - **单方发现**（只一方报）→ **逐条亲自取证核实**（读代码/diff/CI 记录——防幻觉，不盲信任何模型的结论）
   - **冲突结论**（同一问题两模型判断相反）→ 生成交叉质证 prompt（把 A 的结论与依据给 B 驳、反之亦然），用户可选跑；不跑则由本命令按证据裁决并标注存疑
2. **分级**：🔴 发布阻断（必须修）/ 🟡 建议改进（同样必须处置——逐条经用户裁决：修复，或豁免并记录理由；豁免不等于消灭，如实进放行结论遗留区）/ ♻ 误报（取证后驳回，说明依据）
3. **🔴/🟡 处置**：🔴 与裁决采纳修复的 🟡 走 change 族（explore → propose → apply → archive，涉及基准问题的先走 docs 修订）→ 修复后复审（回归原发现点取证）→ 视改动量决定是否再跑一轮双模型；裁决豁免的 🟡 记录理由进放行结论遗留区（豁免不等于消灭）
4. **放行结论**：

   ```
   ## ✅ 对抗终审放行

   **范围：** <范围声明 + ref 区间>
   **双报告：** 模型 A <N> 项、模型 B <M> 项；重合互证 <X>、单方核实成立 <Y>、误报驳回 <Z>、冲突质证 <W>
   **🔴：** 全部修复并复审通过（<清单摘要>）
   **🟡：** 全部处置完毕（修复 <X> 项；豁免 <Y> 项，逐条附理由）
   可发布。
   ```

5. **放行动作（仅发布粒度范围）**：审查对象是 Milestone / 版本区间时，放行结论得出后建 **dev→main 放行 PR**——描述列 Milestone 内 Issue 清单 + 终审结论摘要，建好交**用户确认合并**（agent 只建不合，main 合并永远用户）；用户合并后在 main 合并 commit 上打 tag 发版。范围是全仓体检等非发布场景则止步于放行结论，不放行。

---

**约束**

- **范围由输入确定，命令不预设**——输入是唯一的范围来源；无法确定范围时问，不猜、不擅自扩大或收窄
- **同题独立**——两份 prompt 完全相同；分发阶段两模型不互通，对账在本命令做
- **取证不盲信**——单方发现必须亲自核实后才进清单；两模型都是 LLM，都可能幻觉
- **红黄清零才放行**——🔴 全部修复并复审；🟡 逐条经用户裁决处置（修复，或豁免并记录理由）。完成定义是**没有任何红和黄被默认略过**——只清 🔴 不处理 🟡 不算做完
- 本命令不替代 pr-gate（每个 PR 的 CI 门禁）与 shw-pr-review（代码审查）——终审是发布粒度的最后一道，不是日常门禁
- 审查 prompt 中的范围实参必须真实（Issue/PR 数、ref 区间），不编造
