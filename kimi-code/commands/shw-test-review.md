测试用例的**对齐审查**：在执行开始前，对抗性核对"测试写对了吗"——测试和实现一起歪时 CI 会全绿漏网，所以这道闸必须在任何代码写之前。审的是**测试 ↔ 验收基准**的转写保真度。

**修正内嵌**：审出的问题经用户裁决后**直接修改用例**，复审到红黄清零——review 本身就是修正的意图，没有独立修正命令。

---

**输入**：Milestone 名或 Issue 编号（与 /shw-test-draft 同口径，审对应起稿批次）。

**步骤**

1. **收集输入**

   - test-draft 起稿的用例集（e2e/、tests/vrt/、单元测试——工作区未提交状态）
   - 验收基准：Issue checklist（TC: 名字）、PRD 验收标准原文、arch"测试策略"章节
   - test-draft 的输出清单（用例 × TC 映射；无此清单则先重建映射再审）

2. **正向核对：AC → 测试**

   逐 Issue 逐条 AC：找到 `TC:` 对应的用例并逐断言读——

   - 找不到对应用例 → 🔴 **未覆盖**
   - 用例在但断言与 AC 语义不符（测了别的/只测了表面）→ 🔴 **转写失真**

3. **反向核对：测试 → 基准**

   逐用例逐断言回指：

   - 断言的内容在 AC/PRD/技术方案里**找不到出处** → 🔴 **擅自扩需求**（最毒的一类：把 agent 的私货变成"合法门禁"）
   - 用例名与 TC 名不一致 / 边界断言与 PRD 业务规则矛盾 → 🔴

4. **质量核对**

   - 断言自审复核：功能缺失时会失败吗？失败原因正确吗？测真实行为不是 mock？
   - 四态与边界覆盖：AC 涉及的状态/边界在用例里有交代
   - 🟡 级：命名不规范、重复断言、可合并用例——逐条列入，与 🔴 同批经用户裁决处置（修复，或豁免并记录理由）

5. **裁决与修正（内嵌）**

   - 🔴 清单展示（每条含：问题描述 / 判定依据【基准原文 + 用例位置】/ 建议修正），请用户逐条裁决：**采纳**（修正用例）或**不采纳**（说明理由，记录在案）
   - 采纳的直接修改用例 → **复审修正涉及的用例**（正反向核对重跑）→ 循环到红黄清零
   - 🔴 修正属于测试文件改动，随各自 Issue 的 feat 分支提交（与 test-draft 同纪律）

6. **放行**

   ```
   ## ✅ 测试对齐审查放行

   **范围：** milestone sprint-3 / Issue #12
   **核对：** 正向 18/18 条 AC 有对应用例；反向 42 条断言全部可回溯基准
   **修正：** 3 处 🔴（2 未覆盖 + 1 擅自扩需求）已裁决修正，复审通过
   **🟡：** 全部处置（修复 <X> / 豁免 <Y> 附理由；无则"无"）

   下一步：进入执行——/shw-roadmap（milestone 驱动）或 /shw-apply（单 change）。
   ```

---

**约束**

- **修正内嵌**——审出即修（经用户裁决），不转交任何其他命令；🔴 修复 + 🟡 全部处置（修复或豁免附理由）才放行——只清红不清黄不算完成
- **双向映射是核心动作**——正向防漏、反向防私货；只读用例不复盘映射不算审过
- **基准是唯一裁据**——AC/PRD/技术方案原文；实现现状不影响基准（实现还没写）
- **只写测试文件**——不动实现代码、不动 docs、不跑任何测试
- 问题清单只在对话展示，不落盘报告文件
