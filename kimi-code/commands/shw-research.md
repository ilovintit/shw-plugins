纯读侧调研的入口：读代码、查文档、做对比、给结论——**零变更零承诺**。回答"这是怎么回事、该选哪个、能不能做"这类问题，不动仓库一行内容。本命令是全工作流唯一不需要 Issue 就能跑的命令：探索永远合法，动手必须过闸，本命令承载的是前半句。

**产出**：结论 + 选项（若涉及取舍）+ 建议路径（若被问）。产出**只在会话上下文，默认不落盘任何文件**。

**research 不写生产代码，也不写 docs 文件。** 思考、读代码、画图、对比选项都可以。

---

## 与 /shw-explore 的边界

两者都是只读探索，差别在**绑定物**：

| | /shw-research | /shw-explore |
|---|---|---|
| Issue | **不需要**，自由入口 | 必须，Issue 绑定的执行方案调查 |
| 问题 | 用户抛来的任意问题（机制/对比/可行性） | 要做的任务与代码之间差多少、缺口在哪 |
| 产出 | 结论 + 选项 + 建议路径（若被问） | 差距清单 + 具体执行方案（change 族强制前置） |
| 去向 | 留在会话上下文，或经闸门交接进 Issue | 同会话 /shw-propose 固化成三件套 |

**research 发现要动手 ≠ explore 的产出**：调研中得出的"建议怎么改"只是结论的一部分，不是可执行的 change 方案；真要动手必须建 Issue、走 explore 重新做差距调查。research 的结论给 explore 当输入素材，不替代它。

## 步骤

### 1. 明确问题

- 输入是具体问题：复述确认理解后直接进步骤 2
- 输入只是方向（"帮我看看这个模块"）：先快速扫一眼相关代码，抛出 2~3 个可能的研究方向让用户挑，不挤牙膏也不替用户定题

### 2. 读码接地（调研主体）

- **一切结论必须基于代码现实**：引用读过的文件/模块/接口作为依据，不凭印象和常识泛泛而谈
- 涉及外部技术选型时查官方文档核实版本与能力，不凭训练记忆断言；外部结论与项目代码现状分开标注（一个是文档说的，一个是仓库里实际有的）
- 有助于澄清时大量用 ASCII 图（系统图、调用链、状态机、依赖图）
- 中途发现前提不成立（问的问题代码里已有答案/问题本身问错了方向）：停下告诉用户，不硬着头皮跑完

### 3. 给结论

- 先给直接答案，再给依据（文件路径 + 关键事实），最后给未尽事项
- 涉及取舍时给对比表；用户没问"该怎么改"就不主动铺执行方案——那是 explore 的地盘
- 结论说完进入留痕裁决（见下）

## 转交咬合

调研中发现**需要动手改仓库**（有 bug 要修、有缺口要补、用户当场拍板要做）：

- 触发 `shw-issue-gate` skill 建 Issue——本命令不自己建单，建单的门禁逻辑归 gate，这里只做交接
- **把 research 的结论摘要写进 Issue 正文**（背景/现状事实/调研结论），对齐 /shw-issue 的"初步整理写回"语义——结论活在会话上下文里，不落盘就会随会话蒸发，交接是它唯一的持久化通道
- 建单后提示后续链路：后续的差距调查走 `/shw-explore <N>`，不在本命令里顺手做

## 留痕裁决

默认不落盘。但 agent 若自己判断结论值得留（踩坑与 Why 适合 `docs/journal/`、结论对某个 Issue 有补充价值适合评论），**主动问用户**："这个结论要不要记到 X？"——不擅自写，也不擅自丢弃；用户说不用就让结论随会话去。

## 调研姿态

- **好奇，不强加** - 自然涌现的问题就问，不照本宣科
- **抛出线索，不是审讯** - 提出方向让用户跟有共鸣的走
- **可视化** - 有助于澄清时大量用 ASCII 图
- **接地气** - 一切结论建立在读过的代码上，不空谈
- **耐心** - 不急于结论，让答案形状自然浮现

---

## 约束

- **免 Issue**——本命令不需要也不创建 Issue；调研中发现要动手，转交 `shw-issue-gate` 处理，本命令不替 gate 做门禁判断
- **不写生产代码、不写 docs 文件、不建 Issue**——产出是调研结论本身；建单是 gate 的事，research 只把结论交接过去
- **默认不落盘**——结论只活在会话上下文；落盘与否必须经用户裁决，agent 不擅自写也不擅自丢
- **结论必须接地**——基于读过的代码与核实过的文档，不凭印象断言
- **不越界做执行方案**——"建议怎么改"一句话可以说，差距清单与执行路径归 /shw-explore
