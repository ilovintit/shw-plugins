用**并行 Agent 调度**实现一个 change 的任务。

你是 **协调者**（主 Agent）。你负责高强度的协调推理——读 context、拆解依赖关系、识别并行机会，实际实现通过子智能体调度委派给隔离子智能体并行执行。这保留你自己的上下文用于协调工作，让每个实现任务获得聚焦的执行环境。

**输入**：可选地指定 change 名（如 `/shw-apply add-auth`）。若省略，检查能否从对话上下文推断。若模糊或歧义，你**必须**询问用户可选的 change。

---

## 步骤

### 1. 选择 change

若提供了名字，直接用。否则：
- 若用户在对话中提到过 change，从上下文推断
- 若只有一个活跃 change，自动选
- 若歧义，调用 **shw-spec** 的 `list_changes` 工具（传入 projectRoot）获取可选 change，用向用户提问让用户选

始终声明："使用 change：<name>"，以及如何覆盖（如 `/shw-apply <other>`）。

### 2. 检查 status 以理解 schema

调用 **shw-spec** 的 `get_status` 工具（传入 projectRoot + changeName），返回：
- `schemaName`：使用的工作流（如 "spec-driven"）
- `changeRoot`：change 目录路径
- `artifacts`：各 artifact 的状态（done/ready/blocked）+ 文件路径
- 哪个 artifact 包含任务（spec-driven 通常是 "tasks"）

### 3. 获取 apply 指令

调用 **shw-spec** 的 `get_apply_instructions` 工具（传入 projectRoot + changeName），返回：
- `contextFiles`：artifact ID → 具体文件路径数组（proposal/specs/design/tasks）
- `progress`：进度（总数、已完成、剩余）
- `tasks`：任务列表及完成状态
- `state`：blocked / ready / all_done
- `instruction`：基于当前状态的动态指令

**处理状态：**
- 若 `state: "blocked"`（缺 artifact）：显示提示，建议先用 `/shw-propose` 补全 artifact
- 若 `state: "all_done"`：祝贺，建议 `/shw-archive`
- 其他：进入实现

### 4. 读取 context 文件

读取 apply 指令输出里 `contextFiles` 下列出的每个文件路径。通常包括：
- `proposal.md` — 为什么 + 做什么
- `specs/` — 需求（scenario 即测试用例）
- `design.md` — 技术方案
- `tasks.md` — 实现清单

**同时读取仓库根目录的项目级 `AGENTS.md`**（若存在），获取项目约定和反模式。

### 5. 显示当前进度

显示：
- 使用的 schema
- 进度："N/M 任务已完成"
- 剩余任务概览
- 动态指令

### 6. 【核心】通过并行 Agent 调度实现任务

这是重写的步骤。**你（主 Agent）是协调者——你自己不写生产代码。** 你识别独立任务组，对每个任务用子智能体调度委派执行。

#### 6.1 加载 shw-change-parallel skill

**派发前**，调用 skill 加载机制加载 `shw-change-parallel`，获取并行调度决策框架。该 skill 告诉你如何识别独立任务组，以及如何决定并行还是串行。

#### 6.2 对每一批待处理任务

**a. 识别独立任务组**（用 shw-change-parallel skill）：

- 触及不同模块/文件且无依赖的任务 → **并行**
- 一个任务的输出是另一个的输入 → **串行**
- 编辑同一文件的任务 → **串行**（冲突风险）

**b. 并行派发**，使用子智能体调度。对一个并行组里的每个任务，构造 **6 段式 prompt** 并调用：

```
对每个任务，构造 6 段式 prompt 并通过子智能体调度委派执行
```

**把所有独立的派发放到同一条消息里**（一条响应里多个子智能体调用），让它们真正并行执行。

#### 6.3 6 段式派发 prompt

每次派发**必须**包含全部 6 段：

```markdown
## 1. TASK
[精确引用 tasks.md 里的某个 checkbox。要极其具体。]

## 2. EXPECTED OUTCOME
- 创建/修改的文件：[精确路径]
- 功能：[精确行为]
- 验证：`[命令]` 通过

## 3. REQUIRED CONTEXT
[从 proposal/specs/design 提取该任务需要的相关片段。
 不要一股脑全贴——只贴和这个任务相关的。]

## 4. MUST DO
[AGENTS.md 里适用于该任务的项目约定。例如：
 - 遵循项目命名规范
 - 遵循 <参考文件:行号> 的模式
 - 使用项目约定的测试框架]

## 5. MUST NOT DO
[AGENTS.md 里适用于该任务的反模式。例如：
 - 禁止使用 any / as any
 - 禁止创建 feature 分支
 - 不要修改其他模块的代码
 - 不要添加未要求的依赖]

## 6. VERIFY
[子智能体如何验证完成。例如：
 - 运行项目的测试命令
 - 运行构建命令确认编译通过
 - 运行 lint / typecheck]
```

#### 6.4 收集结果并审查

子智能体返回后：

**a. spec 合规检查**（你做）：
- 每个子智能体的输出是否符合对应 task 的 EXPECTED OUTCOME？
- 是否满足相关的 spec scenario？
- 是否有 MUST NOT DO 违规？

**b. 独立验证声称**（用 shw-verify 的思维）：
- 子智能体应该附上真实命令输出
- 若子智能体声称"测试通过"但没输出，要求它重新验证或拒绝

**c. 集成检查**（针对并行任务）：
- 并行任务是否编辑了同一文件？（不应该，但要验证）
- 运行完整测试套件确认一切协同工作

#### 6.5 更新 tasks.md 并继续

每个完成的 task：
- 在 tasks.md 标记：`- [ ]` → `- [x]`
- 记录任何偏离或后续工作

然后回到 6.2 处理下一批（下一组独立任务，可能是刚解除阻塞的）。

#### 6.6 暂停条件

**暂停并问用户当：**
- 任务真的不清晰（不是单纯难）
- 实现暴露了需要更新 spec/proposal 的设计问题
- 子智能体报告 BLOCKED 且你无法解决
- 用户中断

**不要暂停当：**
- "我应该继续下一个任务吗？"——继续做
- 任务之间的进度汇报——没必要
- 单个任务失败但有明显的重试路径——重试或换路径

### 7. 自我审查与修复

所有任务完成后，**进入自我审查阶段**——这是 apply 的责任，不是用户的事。**不要把审查工作推给用户。**

#### 7.1 加载审查 skill

加载 `shw-change-review-code` skill，对本次 apply 的全部代码变更做逐字符审查。审查维度（由 skill 定义）：

- 把 specs 的每个 scenario 与代码实现逐行对比
- 把 design 的每个决策与代码落地逐个对比
- 检查 AGENTS.md 项目约定的遵守情况
- 检查反模式（硬编码/资源泄漏/安全漏洞等）
- 检查边界场景完整性

#### 7.2 循环：审查 → 修复 → 复审，直到收敛

apply 交付的不是"审查过一次"，而是"**收敛到零偏差**"。所以审查和修复是循环进行的：

```
loop:
  1. 加载/复用 shw-change-review-code skill，对本次 apply 的全部代码变更做逐字符审查
     （首次审查范围 = 本次 apply 全部变更；后续复审范围 = 上次遗留问题 + 本次修复涉及的变更）
  2. 收集审查结果
     - 🔴 项（必须修复）：进入 step 3
     - 🟡 项（建议改进）：累积起来，最终汇报时列出，让用户决定
     - ✅ 无 🔴：跳出循环，进入第 8 步汇报
  3. 对每个 🔴 项，委派子智能体修复
     - 修复 prompt 同样用 6 段式（步骤 6.3），EXPECTED OUTCOME 写明"消除该审查问题"
     - MUST NOT DO 加上"不要引入新的反模式"
  4. 修复完成后，回到 step 1 重新审查（只复审"上次遗留 🔴 + 本次修复涉及的变更"即可，不必从头全审）
end loop
```

**循环退出条件**：一次完整审查后**零 🔴 项**。

**循环保护**：
- 实务上绝大多数情况 1-3 轮即可收敛。若修复反复引入新问题（例如连续 5 轮仍有 🔴），停下来按第 8 步格式向用户汇报"卡在审查循环"，列出当前未解决的 🔴，让用户决策——**不要无限循环**。
- 每一轮的修复要基于上一轮的审查结果精准定位，不要盲目大改。

**为什么是循环而不是一次**：代码与 change 设计的偏差往往是相互关联的——修了 A 偏差可能暴露 B 偏差，改了 B 又影响 C。只有循环审查到收敛，才能确认实现真正符合设计意图。**这个收敛过程是 apply 的责任，不是用户的事**——不能交付一个"还残留 🔴、等用户发现再修"的状态。

### 8. 汇报并完全停止

自我审查通过后，向用户汇报本次 apply 的完整结果，然后**完全停止**。

**完全停止的含义**：
- 不主动调用 `/shw-archive`
- 不询问"是否归档"
- 不建议"接下来可以归档"
- 归档完全是用户的决定，由用户在验收后显式触发

**完成时的输出格式：**

```
## ✅ Apply 完成 — 等待验收

**Change：** <change-name>
**Schema：** <schema-name>
**进度：** 7/7 任务完成

### 本次完成的任务
- [x] Task 1：<描述>
- [x] Task 2：<描述>
- [x] Task 3：<描述>（与 Task 4 并行）
- [x] Task 4：<描述>（与 Task 3 并行）
...

### 验证
<完整测试套件输出或摘要>

### 自我审查结果
<shw-change-review-code 审查摘要，含 🔴 项的修复记录>

🟡 待你决定的改进项（若有）：
- <改进项 1>
- <改进项 2>

---
**实现已交付，等你验收。** 验收通过后由你决定是否 `/shw-archive`，发现问题告诉我即可。
```

**执行中因阻塞暂停时**（见步骤 6.6 的暂停条件），按下面格式停下等用户决策：

```
## ⏸ 执行中遇到阻塞

**Change：** <change-name>
**进度：** 4/7 任务完成

### 阻塞描述
<描述>

**选项：**
1. <选项 1>
2. <选项 2>
3. 其他方案

你想怎么做？
```

## 约束

- **完成后完全停止，绝不主动归档。** apply 的终点是"自我审查通过 + 向用户汇报"，不是归档。归档是用户的决定，由用户在验收后显式触发 `/shw-archive`。绝不在 apply 流程内连续调用 archive，也不要在汇报里建议归档。
- **自我审查是 apply 的责任。** 不能把 🔴 问题留给用户发现。交付前必须自己审查并修复完所有 🔴 项。
- **你是协调者。** 不要自己写生产代码——那是子智能体的事。（读文件、改 tasks.md 的 checkbox、做小的协调修复是 OK 的。）
- **派发前必须读 context 文件。** 子智能体只知道你告诉它的内容。
- **派发 prompt 必须包含全部 6 段。** 模糊的 prompt 只会产出模糊的结果。
- **默认并行，只有命名的依赖才串行。** 这是 shw-change-parallel skill 的核心原则。
- **声称前必须验证。** 用 `shw-verify` 的纪律——不要没证据就相信子智能体的"成功"。
- **每个 task 完成后立即更新 checkbox。**
- **任务执行阶段连续，完成后停止。** 执行过程中遇到真正的阻塞才暂停（见步骤 6.6），不要为了汇报而暂停；但所有任务完成 + 自我审查通过后，必须完全停止向用户汇报，等用户验收。

---

## 流式集成

此命令支持"对 change 的动作"模型：
- **可随时调用**：在所有 artifact 完成前（若有 task）、部分实现后、与其他动作穿插
- **允许更新 artifact**：若实现暴露了设计问题，建议通过 `/shw-propose` 流程更新 artifact——不锁阶段，灵活工作
