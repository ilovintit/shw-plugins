# 完成前验证

## 模式前置

本 Skill 不是所有项目的默认约束。先读取仓库根 `.shw/project.yaml` 的模式：无标识时不主动应用；`issue-main` 只保留 Issue 分支→main 的轻量闭环；`issue-dev` 只保留 Issue 分支→dev→main 的轻量闭环；只有 `managed` 才应用本 Skill 中的业务项目目录、分支、测试、发布、部署或公司规范要求。模式定义见 `shw-issue-gate/project-mode.md`。

## 概述

声称工作完成而没验证是不诚实，不是高效。

**核心原则**：声称之前先有证据，永远如此。

**违反规则的字面意义就是违反规则的精神。**

## 铁律

```
没有新鲜的验证证据，不声称完成
```

若你这次响应没运行过验证命令，你不能声称它通过。

## 门禁函数

```
声称任何状态或表达满意之前：

1. 识别：什么命令能证明这个声称？
2. 运行：执行完整命令（新鲜的、完整的）
3. 阅读：完整输出，检查退出码，数失败
4. 验证：输出是否支持声称？
   - 否：附带证据陈述实际状态
   - 是：附带证据陈述声称
5. 仅在此时：做出声称

证明级别匹配声称级别：
- 编译级声称（build/typecheck）用本地命令输出证明
- 合并与发布证据按真实目的区分：Issue→dev必须有当前 HEAD 的适用工程检查；dev→main必须有当前候选的工程、来源与发布检查，纯历史同步只按 `shw-test-spec/references/history-sync.md` 复用工程证据。API/E2E/VRT 回归报告不作为合并或发布通过证据，失败/缺失也不是例外合并债务。开发中必要本地单测不能替代 CI。
- 声称基线有效必须同时验证最终人工验收引用、不可变 accepted source、manifest、生成与同目标复跑证据；只跑一次回归、只发布成功或只比较 dev 都不够。

跳过任何步骤 = 在撒谎，不是在验证
```

## 常见失败

| 声称 | 需要 | 不够 |
|-------|----------|----------------|
| 合并所需测试通过 | 当前 HEAD 的 PR CI run 链接 + required job 绿 | 本地结果、之前跑过、"应该通过" |
| Linter 干净 | Linter 输出：0 错误 | 部分检查、推测 |
| 构建成功 | 构建命令：exit 0 | Linter 通过、日志看起来好 |
| Bug 已修 | 测原始症状：通过 | 代码改了、假设修好了 |
| 回归基线有效 | 最终验收来源 + accepted source + manifest + 生成/复跑 | 测试通过一次、发布成功 |
| 子智能体完成 | VCS diff 显示改动 | 子智能体报告"成功" |
| 需求满足 | 逐项清单 | 测试通过 |

## 红旗 - 停下

- 用"应该"、"大概"、"似乎"
- 验证前表达满意（"好了！"、"完美！"、"搞定！"等）
- 准备 commit/push/PR 但没验证
- 信任子智能体的成功报告
- 依赖部分验证
- 想"就这次"
- 累了想收工
- **任何措辞暗示成功但没跑验证**

## 防止合理化

| 借口 | 现实 |
|--------|---------|
| "现在应该可以了" | 运行验证 |
| "我有信心" | 信心 ≠ 证据 |
| "就这次" | 无例外 |
| "Linter 通过了" | Linter ≠ 编译器 |
| "子智能体说成功" | 独立验证 |
| "我累了" | 疲劳 ≠ 借口 |
| "部分检查够了" | 部分证明不了什么 |
| "措辞不同所以规则不适用" | 精神高于字面 |

## 关键模式

**工程检查：**
```
✅ 提交推送 → PR CI run 链接 + 对应 required 工程 job 绿
❌ 用本地结果替代 required CI / "现在应该通过"/"看起来对"
```

**适用工程 TDD（判定在 CI）：**
```
✅ 写最小工程断言 → 推送（CI 红）→ 修复 → 再推（CI 绿）——红绿两截记录可查
❌ 用 API/E2E/VRT 或截图基线给功能开发制造 RED
```

**回归基线：**
```
✅ 最终人工验收证据 + 不可变 accepted source + 候选审查 + 同目标复跑 + manifest/PR
❌ dev 测试通过、main 已合并、发布健康或一次比较通过
```

**构建：**
```
✅ [运行构建] [看到：exit 0] "构建通过"
❌ "Linter 通过"（linter 不检查编译）
```

**需求：**
```
✅ 重读计划 → 建清单 → 逐项验证 → 报告缺口或完成
❌ "测试通过，阶段完成"
```

**子智能体委派：**
```
✅ 子智能体报告成功 → 检查 VCS diff → 验证改动 → 报告实际状态
❌ 信任子智能体报告
```

## 为什么重要

来自真实失败案例：
- 用户说"我不信你"——信任破裂
- 未定义函数被发布——会崩
- 漏掉的需求被发布——功能不完整
- 假完成上浪费的时间 → 返工 → 重做
- 诚实是核心价值。虚假声称摧毁信任。

## 何时应用

**总是在以下之前：**
- 任何变体的成功/完成声称
- 任何满意表达
- 任何关于工作状态的正面陈述
- commit、创建 PR、标记任务完成
- 进入下一任务
- 委派给子智能体

**规则适用于：**
- 精确短语
- 转述和同义词
- 暗示成功
- 任何暗示完成/正确的沟通

## 底线

**验证没有捷径。**

运行命令。读输出。然后声称结果。

这是不可协商的。
