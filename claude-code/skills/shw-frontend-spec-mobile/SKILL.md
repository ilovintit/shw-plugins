# 移动端视觉与操作规范

先确定真实目标端和项目现有实现。通用的详情接口、表单提交防重、列表竞态、错误反馈见 `shw-frontend-spec-common`；技术栈与目录见 `shw-frontend-stack`。同一业务可以跨端保持数据/API 和用户目标一致，不要求相同的页面结构、控件、导航、手势或代码。

## H5 与小程序：分端组件

`shw-ui` 计划在其独立 monorepo 中分别维护移动 H5 和各类小程序组件。每次接入先核对该**具体端**的正式发布包名、版本、组件文档、设计 token、平台支持与构建条件。不能把旧 `@shwkj/taro-ui` 的 `Shw*` API、CSS 变量、物理 px、pxtransform exclude 或示例目录视为新包既有契约；不能把某个小程序包直接用于另一平台。未发布或未覆盖时，记录缺口并按该端既有基座实现，不引用虚构的包，也不复制公共库源码到业务仓库。

- H5 按其浏览器框架、路由、请求、样式和安全区能力落地；企微内嵌只在产品明确时接入企微授权。
- 每种小程序按该平台原生语言/组件、页面注册、请求、尺寸单位、导航与包体限制落地。微信小程序的 `navigateTo`、`redirectTo`、`switchTab` 和开发者工具约束不外推给其他小程序。
- 列表、表单、上传、弹层、反馈优先使用**当前端已发布并验证**的库组件；组件行为以该端文档为准。没有组件时允许端内实现并记录未来迁移点，不把“页面不造轮子”解释为必须使用尚不存在的组件。
- 主题、颜色、间距、字体和安全区使用当前端实际可用的 token/平台机制。图标以 `shw-frontend-spec-common/references/icon-management.md` 的已验证端内方案为依据，不把微信 TabBar PNG 或 H5 字体实现强加给其他端。

## iOS、Android、鸿蒙：原生 App

前期 `shw-ui` 不覆盖这三个端的可运行组件。分别按其原生平台规范、语言与工程实现；详情加载、错误语义和提交防重等业务契约可共享，但返回栈、导航、弹窗、手势、系统控件、安全区和无障碍行为各端单独设计与验收。不能直接使用 H5 CSS token、Shw 标签、微信小程序组件或统一交互截图作为原生 App 的实现要求或验收证据。

将来 `shw-ui` 仅提供三端各自规范，还是另建 App 专用公共库，待实际 App 开发时由用户决定；当前不选包名、组件 API 或强制技术栈。

## 微信小程序开发与发布边界

微信项目单独登记源码、编译目录、开发者工具 `miniprogramRoot`、上传器路径与 CI 产物；不得默认为 Taro 的 `dist/weapp` 或与 H5 共用构建输出。旧 Taro 项目在迁移前可继续按既有 `dist/h5`、`dist/weapp` 约定运行，改产物路径时同时核对所有消费者，不因规范升级自动清理旧目录。

项目正常调试时保持微信开发者工具打开，复用现有自动化连接与 watch；断连先重连，卡死再恢复。打开开发者工具后，页面导航、交互、断言、日志与调试控制全程使用微信 `automate-ci` 工具。Computer Use 可直接打开工具和截图；卡死时可直接关闭并触发重新编译。其他 Computer Use 操作须先说明并逐次获得用户明确确认。

小程序上传只证明相应平台的代码上传，不证明审核、发布、H5 等价或真机验收。原型优先复用可运行的该端 H5 资产；纯 HTML 模拟要标明组件映射和未联调范围，不替代任何小程序或原生 App 端验收。

## 审计

按真实端逐页核对：详情/编辑是否重新获取详情、请求竞态、提交防重、错误与空态、端内已发布组件的实际使用、平台导航和产物路径。旧 Taro 工程只记录迁移计划与现有兼容条件，不以新规范直接判定其全部页面违规；未经过该端构建和设备验证的能力标为未实测。
