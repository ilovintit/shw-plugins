# 四层职责定义

### Domain 层 — "核心业务规则"

纯业务，不依赖任何框架、不依赖 DB、不依赖基础设施。这一层的代码可以被任何框架复用。

| 放什么 | 不放什么 |
|--------|---------|
| 领域实体 / 聚合根（有唯一标识，含业务行为方法） | ORM 模型 / 数据表映射 |
| 值对象（无标识，不可变，如金额、地址、状态码） | 可变状态、DB 字段映射 |
| 领域服务（跨实体的业务逻辑，不属于单个实体） | 直接访问 DB（必须通过 Repository 接口） |
| Repository **接口**（数据访问契约，只定义不实现） | 实现细节（归 Infrastructure） |
| 其他领域契约/防腐层接口（对接外部系统的抽象） | 外部系统的具体实现 |
| 领域事件（业务意义上发生的事，如"用户已注册"） | 事件监听器（归 Application） |
| 编码生成规则（如订单号、合同号的生成逻辑） | 与 DB 交互 |
| 领域异常（业务规则被违反，如"库存不足"） | 技术异常 |

### Application 层 — "业务编排"

不含业务规则，只负责编排一个业务操作的流程。

| 放什么 | 不放什么 |
|--------|---------|
| 请求/响应 DTO（出入参数据结构） | 业务校验规则（归 Domain） |
| 用例 UseCase（编排多个领域对象完成一个业务操作） | 业务规则（归 Domain Service / Entity） |
| 事件监听器（监听领域事件，执行副作用如发通知） | 业务规则（只编排，不写规则） |
| 应用层异常（业务流程异常，如"资源不存在"、"操作无权限"） | 技术异常（归 Infrastructure） |

**用例的职责边界**：用例编排流程（"先查、再校验、再改、再发事件"），但**业务规则由领域服务/实体承载**。用例调用它们，不自己写规则。

### Interfaces 层 — "系统入口"

外部交互层，系统的入口。按"端"分组（同一模块服务多个端时，每端一个子目录，如 admin/client/tenant）。

| 放什么 | 不放什么 |
|--------|---------|
| 请求处理器/控制器（接收请求、提取参数、调用用例、返回响应） | 业务逻辑、直接查 DB |
| CLI 命令（如数据修复、批处理） | 业务逻辑（应调用用例） |
| 常驻进程入口（消费 MQ、定时任务、长连接） | 业务逻辑（应调用用例） |
| 全局异常处理器（统一捕获各层异常，映射 HTTP，装配响应） | — |

### Infrastructure 层 — "技术实现"

技术实现细节，一切与框架、DB、外部系统打交道的代码。

| 放什么 | 不放什么 |
|--------|---------|
| ORM 模型 / 数据表映射（定义字段、关系） | 业务逻辑 |
| Repository 接口的实现（查 DB 模型，转换为领域实体） | 业务规则（只做数据格式转换） |
| 外部服务客户端（第三方 API 调用、消息推送） | 业务判断 |
| 基础设施异常（DB 连接失败、第三方 API 超时、网络错误） | 业务异常 |

**仓储实现的职责**：实现 Domain 层定义的 Repository 接口。从 DB 查出模型，转成领域实体返回。这里做数据格式转换（DB 行 ↔ 实体），**不做业务判断**。
