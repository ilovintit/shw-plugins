# Module 模式

每个业务模块是一个独立、完整的四层结构。模块内自治，模块间通过应用层或共享服务协作。

```
{module}/                         ← 一个业务模块（物理根路径由各框架约定）
│
├── interfaces/                   ← 系统入口
│   ├── {end}/                    ←   按端分组（admin / client / tenant 等）
│   │   ├── http/                 ←     请求处理器/控制器（取参 + 调用用例）
│   │   └── command/              ←     该端的 CLI 命令
│   ├── process/                  ←   常驻进程（队列消费者、定时任务、长连接）
│   └── exception/                ←   全局异常处理器（统一捕获分发）
│
├── application/                  ← 业务编排
│   ├── dto/                      ←   请求/响应 DTO
│   ├── usecase/                  ←   用例（编排领域对象完成一个业务操作）
│   ├── listener/                 ←   事件监听器（监听领域事件，做副作用）
│   └── exception/                ←   应用层异常（"资源不存在"、"权限不足"）
│
├── domain/                       ← 核心业务规则（纯业务，不依赖任何框架/DB）
│   ├── entity/                   ←   聚合根 + 实体（含业务行为方法）
│   ├── valueobject/              ←   值对象（无标识，不可变）
│   ├── service/                  ←   领域服务（跨实体的业务逻辑）
│   ├── repository/               ←   仓储接口（契约，只定义不实现）
│   ├── contract/                 ←   其他领域契约/防腐层接口
│   ├── event/                    ←   领域事件
│   ├── coderule/                 ←   编码生成规则（如订单号生成）
│   └── exception/                ←   领域异常（"库存不足"、"状态不允许此操作"）
│
├── infrastructure/               ← 技术实现细节
│   ├── model/                    ←   ORM 模型 / 数据表映射（不进 domain）
│   ├── persistence/              ←   仓储接口的实现（查 DB，转实体）
│   └── exception/                ←   基础设施异常（连接失败、超时）
│
└── {module_entry}                ← 模块入口：集中做路由注册 + 依赖注入装配
```

### 模块入口的职责

每个模块有一个入口（具体形态由各框架定：可能是模块注册文件、服务提供者、路由注册函数等），集中做两件事：

1. **路由注册**：把本模块的请求处理器/CLI 命令挂到框架路由上
2. **依赖注入装配**：集中声明各层依赖绑定，把仓储实现注入用例，再注入控制器；Go 手工构造，Hyperf 使用框架容器，具体语法由语言规范规定。

```
✅ 模块入口一处装配全部依赖，依赖关系显式可见
❌ 依赖关系靠全局单例/运行时查找隐式散落各处（Service Locator 反模式）
```

依赖倒置靠模块入口接线实现：domain 定义接口，infrastructure 实现，application 依赖接口，模块入口负责把实现塞进接口。具体注入方式（构造函数注入、结构体字段、setter）由各语言 conventions 决定。
