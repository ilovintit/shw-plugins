执行前读取 [cloud-runtime.md](cloud-runtime.md)，按实际工具与工作区提供者执行。

执行前必须读取 `shw-issue-gate`；修改前读取 `shw-workspace` 并确认项目、目录、Issue 与所有权。项目外只读，未知修改不覆盖；能力缺失不扩大授权。

# 单 Issue 交付

先读项目模式、`shw-gitea-flow`、`shw-acceptance` 和 `shw-verify`。一个 Issue 对应一个交付分支与 PR；已有匹配 Issue/占用/PR 优先复用，不重复派工。

1. 读取 Issue、评论、依赖、相关实现和当前规格。确认范围、非目标、人工可判定 AC，以及依赖已进入来源分支。
2. 通过 `shw-workspace` 确认工作区所有权；列出实现与体验计划。初版只需够用 PRD/技术方案，直接做可体验版本，无独立原型阶段。
3. 实现并在同一变更同步文档：业务逻辑、权限、状态流转更新 PRD；接口、数据、架构更新技术文档。当前已实现规格与待实现方案明确分开，Issue 摘要不能代替规格。
4. 读取 `shw-pr-review`，检查 diff、AC、安全、兼容与文档。开发阶段必须执行类型检查、适用 lint/静态检查及本次改动涉及的单元与单模块 API 快速测试；全量 E2E、VRT、全量 API 等长周期回归集中到 dev→main 集成。必要构建、部署正常执行，tag 不新增测试阶段；检查通过不能代替人工验收。
5. 执行体验所需构建、打包和部署，核对实际脚本依赖。现有类型检查和模块快速 CI 正常运行，不因包含测试而询问是否沿用；不得跳过 required checks、force 合并或伪造通过。真正需要修改门禁时按项目授权处理。
6. 更新同一 PR，按真实授权与路由合入 dev，记录快速检查、构建、部署与变更审查证据；全量长周期回归按 `shw-integration` 执行。
7. 提供真实入口、角色/数据、体验步骤、源码 SHA、制品 digest、部署 revision、已知限制。待用户反馈，不能将工程交付当作人工验收。反馈修正依然同步代码文档；已合入时使用关联修正 Issue/PR。
8. 回写事实，按工作区提供者安全释放/清理。未知修改、他人占用或分叉现场保留，不自动删除。

范围或契约发生需用户裁决的变化时提出具体方案；在已有授权内继续无关独立工作。roadmap 复用此内核；并行仅按 `shw-issue-parallel` 的所有权约束。
