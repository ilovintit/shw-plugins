# 设计评审：数据库与 API 路由的确认（PRD 对照优先）

## 触发场景

在 explore 模式或 propose 阶段，当出现以下任一情况时自动加载本 skill：

- 设计新的数据库表 / 修改现有表结构
- 设计数据库迁移
- 设计后端 API 路由（新增端点、修改现有端点的请求/响应格式）
- 设计数据模型关系（外键、关联表、索引）

**核心原则**：PRD 规格是真相源——有规格对照规格，无规格问用户。这些设计决策影响深远（DB 结构难改、API 是契约），不能由 agent 默默决定后埋在 artifact 里。项目有 PRD 时先对照规格做一致性检查（agent 自主完成）；PRD 未覆盖的设计点才逐项展示给用户确认，不要等用户主动问。

## 第一步：查 PRD

涉及数据库或 API 设计时，**先检查项目 `docs/prd/` 是否存在 PRD**。业务项目用 PRD 工具链时，PRD 的**数据库设计节与 WebUI 要求节是规格真相源**——用户裁决权前置集中在 PRD 起草/审查期，执行期 agent 照规格自主推进。按设计点的 PRD 覆盖情况分流到以下分支：

### PRD 已覆盖的设计点：对照检查（agent 自主，不打扰用户）

该表 / 字段 / 端点在 PRD 数据库设计节或相关规格节有记载时：

- **逐项对照 PRD 做一致性检查**：表结构逐项比对字段 / 类型 / 约束 / 默认值 / 索引 / 表间关系；API 逐项比对请求参数 / 响应结构 / 错误码规格
- 对照检查 agent 自主完成，**不逐项打扰用户**。design 与 PRD 一致、或差异已说明理由，即通过
- 发现 design 与 PRD 规格冲突时**必须摆出差异**：
  - 属**实现偏差**的：修正 design 并说明理由
  - 属 **PRD 错漏**的：走 `/shw-prd-revise` 修正规格，然后照新规格实现。**禁止在 design 内静默偏离规格**

### PRD 未覆盖的设计点：逐项展示确认（原有模式）

规格节空缺（如留空占位待 review 补齐）或该设计点在 PRD 中无记载时，走本 skill 下文的完整确认流程：逐表逐字段 / 逐端点展示设计逻辑与确认点，用户确认后才写入 design.md。

### 无 PRD 的项目：全部逐项确认（行为不变）

`docs/prd/` 不存在任何 PRD 时，全部设计点走原有逐项展示确认模式，不因对照优先模式引入而跳过任何确认。

### 规格之下的实现自由度：design 自主决策（即使有 PRD 也不问用户）

迁移脚本组织、代码分层、技术选型落地等规格之下的实现细节，归 change design 自主决策，**不要求用户确认**——即使项目有 PRD，也不就这些问用户。

## 工作方式：PRD 未覆盖时的逐项确认流程

> 以下为 PRD 未覆盖的设计点（或项目无 PRD）时的完整确认流程，即上文"逐项展示确认"模式的具体展开。

### 1. 数据库结构设计

当需要设计表结构或字段时，**不要直接写进 design.md**，先按下面的格式逐表逐字段展示给用户：

```
## 数据库设计 - 请逐项确认

### 表：<table_name>
用途：<这个表存什么，解决什么问题>

| 字段 | 类型 | 可空 | 默认 | 索引 | 设计逻辑 |
|------|------|------|------|------|---------|
| id | bigint unsigned | 否 | - | PK, AI | 主键 |
| user_id | bigint unsigned | 否 | - | FK→users.id | 关联用户，必填 |
| status | tinyint | 否 | 0 | 普通 | 0=待审 1=通过 2=拒，用 tinyint 而非 enum 减少 JOIN 成本 |
| created_at | datetime | 否 | CURRENT_TIMESTAMP | - | 创建时间 |
| ... | ... | ... | ... | ... | ... |

### 索引设计
| 索引名 | 字段 | 类型 | 理由 |
|--------|------|------|------|
| idx_user_status | (user_id, status) | 联合 | 高频查询：按用户筛状态 |
| ... | ... | ... | ... |

### 关系设计
- <table_name>.user_id -> users.id（一对多，用户有多条记录）
- ...

### 需要你确认的点
1. <字段名>：是否真的需要可空？我倾向 NOT NULL，因为...
2. <字段名>：用 tinyint 还是 enum？我推荐 tinyint 因为...
3. <索引>：是否需要加 (user_id, status) 联合索引？查询模式是...
4. <表名>：是否需要加软删除 deleted_at？项目其他表有用吗？
5. ...
```

**关键要求**：
- 每个字段都要有「设计逻辑」列，不能只列类型不解释为什么
- 索引设计要说明对应的查询模式
- 关系设计要画清楚（用文字或简单 ASCII）
- **末尾列出"需要确认的点"**--把你认为有争议或需要用户拍板的设计决策主动提出来

### 2. API 路由设计

当需要设计 API 端点时，**逐个端点展示**：

```
## API 路由设计 - 请逐项确认

### 端点 1：<METHOD> <path>
用途：<这个端点做什么>

**请求**：
| 参数 | 位置 | 类型 | 必填 | 校验规则 | 设计逻辑 |
|------|------|------|------|---------|---------|
| user_id | path | int | 是 | >0 | 标识用户 |
| status | query | string | 否 | enum:active,inactive | 筛选状态，默认全部 |
| ... | ... | ... | ... | ... | ... |

**响应**：
```json
{
  "code": 0,
  "data": {
    "id": 1,
    "name": "..."
  }
}
```

| 字段 | 类型 | 设计逻辑 |
|------|------|---------|
| code | int | 0=成功，非0=错误码 |
| data.id | int | 资源 ID |
| ... | ... | ... |

**错误码**：
| code | 含义 | 触发场景 |
|------|------|---------|
| 40001 | 用户不存在 | user_id 找不到 |
| ... | ... | ... |

**需要你确认的点**：
1. 路径用 /users/{id}/orders 还是 /orders?user_id={id}？我倾向前者因为...
2. status 参数用 enum 字符串还是 int？项目其他接口怎么用的？
3. 响应包装用 {code, data, message} 还是直接返回 data？项目约定是...
4. ...
```

**关键要求**：
- 每个端点都要有：用途、请求参数表、响应结构、错误码、确认点
- 请求参数要说明「位置 + 校验规则」
- 响应结构要画出 JSON 示例 + 字段说明
- **末尾列出"需要确认的点"**--主动提出有争议的设计决策

### 3. 确认流程

展示完设计后：

1. **等用户逐项确认**--不要默认用户同意，不要在用户没回应时就写进 artifact
2. 用户可能：
   - 全部同意 -> 把确认后的设计固化到 design.md
   - 部分修改 -> 按用户意见调整后再次展示修改的部分
   - 提出新问题 -> 讨论后更新设计
3. **只有用户明确确认后**，才把设计写入 design.md 或 proposal.md

## 与 explore 模式的关系

explore 强调"姿态不是工作流"，但本 skill 定义的是**硬性行为要求**：

- explore 允许自由探索、不强加结构
- 但**一旦触及数据库或 API 设计**，本 skill 的"逐项展示确认"就是强制的
- 这不矛盾--探索可以自由，但涉及 DB/API 这种影响深远的设计时必须停下来确认
- 有 PRD 时，"停下来"的动作是对照规格检查（agent 自主，不打扰用户）；规格未覆盖的设计点才停下问用户

## 与 propose 命令的关系

propose 阶段创建 design.md 时，如果 design.md 涉及数据库或 API 设计：

- 加载本 skill，先走"第一步：查 PRD"分流，再对 PRD 未覆盖的设计点按上述格式逐项展示确认
- 用户确认后，把确认结果写入 design.md
- 不要在 design.md 里偷偷写未确认的设计（PRD 已覆盖且对照通过的设计不算"未确认"——规格即裁决）

## 不要做的事

- ❌ 直接把表结构/API 设计写进 design.md 不给用户看
- ❌ 只列字段名和类型，不解释设计逻辑
- ❌ 不列"需要确认的点"，让用户自己找问题
- ❌ 用户没确认就假设同意
- ❌ 一次展示太多内容（多张表/多个端点混在一起），让用户难以逐项确认
- ❌ PRD 已有规格还逐字段问用户（浪费用户时间，对照检查是 agent 的活）
- ❌ design 偏离 PRD 规格却不摆差异、静默改（PRD 错漏走 /shw-prd-revise，不静默偏离）

## 约束

- 涉及 DB/API 设计时**必须**加载本 skill，不能跳过
- 每个字段/每个端点都要有设计逻辑说明
- 末尾必须列出"需要确认的点"（逐项确认模式下）
- 用户确认前不写入 artifact（PRD 已覆盖且对照通过的除外）
- design 不得静默偏离 PRD 规格——冲突必须摆差异，属 PRD 错漏的走 `/shw-prd-revise` 修正规格后照新规格实现
- 遵循项目现有约定（命名风格、响应格式、错误码体系）--先读项目代码确认约定
