# AES 加密跨语言设计范式

## 概述

敏感数据加密的本质问题不是"挑个算法调个 API"，而是"怎么让两端用各自语言的标准库，产出彼此都能解开、且字节级一致的密文"。

**核心原则**：算法统一 AES-256-GCM，字节布局统一 `nonce + tag + ciphertext`，密钥派生统一 PBKDF2-SHA256，盐两端一致。一端写入数据库的加密数据，另一端原样读出来能解密；写回去的密文，下次读也能解。**两端密文格式是同一套，不是两套各玩各的。**

**违反这个原则就是把加解密做成"单向锁"**：A 端加密的 B 端解不开、换语言迁移历史数据全成乱码、跨服务共享加密字段直接对不上。这些问题的根因都是"两端没有字节级对齐同一套格式"。

## 铁律

```
算法固定 AES-256-GCM，不选别的
密文格式固定 base64( nonce[12] + tag[16] + ciphertext )，两端字节级一致
密钥派生固定 PBKDF2-SHA256，600000 次迭代
盐从配置读，两端必须一字节不差地一致（生产环境必须配置，禁用默认占位盐）
配置值满 32 字节直接用作 key，否则走 PBKDF2 派生
Go 标准库默认布局与本约定不符（tag 在末尾），必须手动重排字节
```

凭"Go 标准库默认 tag 在末尾，顺手用默认就行"、"盐随便填一个，反正都是加密"、"迭代次数 10 万够了，600000 太慢"的直觉做事——全部是在亲手切断两端互通。

## 算法选型：AES-256-GCM

固定用 **AES-256-GCM**，不要换成 CBC、ECB、CTR 或其他。

**为什么是 GCM**：GCM 是 AEAD（Authenticated Encryption with Associated Data），**同时**保证两条性质：

| 性质 | 含义 | CBC 有没有 |
|------|------|-----------|
| 机密性 | 没密钥看不到明文 | 有 |
| 完整性 | 密文被篡改一个比特，解密时 tag 校验直接失败 | **没有**（需另配 HMAC，容易漏） |

CBC 模式只保证机密性，不防篡改。攻击者翻转密文字节，明文对应位置就被篡改，且解密不报错——这叫"密文注入"。GCM 用认证 tag 把这问题一次性解决，不用再自己拼一层 HMAC。

**为什么是 256**：密钥 32 字节（256 位），抗暴力破解强度顶格。配合 PBKDF2 高迭代次数，即便配置里的密码是弱口令，派生出的 key 也极难被穷举。

## 跨语言字节布局（核心硬约定）

这是整个范式的命门。两端标准库的默认布局**不一样**，必须统一到一套格式上。

### 统一格式（规范约定）

```
最终密文 = base64( nonce[12] + tag[16] + ciphertext )

字节偏移：
  [0 .. 12)    nonce      （12 字节，GCM 标准 96 位 IV）
  [12 .. 28)   tag        （16 字节，GCM 认证标签 128 位）
  [28 .. end)  ciphertext （变长，与明文等长）
```

**tag 在中间（紧跟 nonce 之后）**，这是本范式的硬约定，两端必须凑齐这个格式。

### 两端标准库的默认差异

| 语言 | 标准库 GCM 布局 | tag 位置 | 是否符合本约定 |
|------|----------------|---------|---------------|
| **PHP**（openssl） | `openssl_encrypt` 返回 ciphertext，tag 经引用参数 `&$tag` 单独返回，由调用方组装 | 自由拼，**拼成 `nonce + tag + ciphertext` 即符合** | 是 |
| **Go**（crypto/cipher） | `gcm.Seal` 返回 `ciphertext + tag` 一坨 | **末尾**（tag 拼在 ciphertext 后） | **否，需手动重排** |

```
本约定格式：       nonce + tag + ciphertext     ← tag 在中间
Go gcm.Seal 默认： nonce + ciphertext + tag     ← tag 在末尾（偏离约定）
```

PHP 端组装时直接按约定格式拼装，无需重排。Go 标准库的 tag 位置写死在末尾改不了，所以必须由 Go 端动手重排。如果不处理，PHP 加密的密文 Go 的 `gcm.Open` 解不开（tag 位置对不上），反之亦然。

### PHP 端实现（直接按约定格式组装）

PHP 的 `openssl_encrypt` 原生分离 ciphertext 和 tag，直接按约定格式拼装，无需重排：

```
function encrypt(plaintext, key):
    nonce = random_bytes(12)                      // 12 字节随机 IV
    tag = null
    ciphertext = openssl_encrypt(                 // PHP openssl，'aes-256-gcm'
        plaintext, 'aes-256-gcm', key, OPENSSL_RAW_DATA,
        nonce, tag                                // tag 通过引用参数单独返回
    )
    blob = nonce + tag + ciphertext               // 约定格式：nonce + tag + ciphertext
    return base64_encode(blob)

function decrypt(blob64, key):
    blob = base64_decode(blob64)
    nonce      = blob[0:12]
    tag        = blob[12:28]
    ciphertext = blob[28:]
    plaintext = openssl_decrypt(                  // PHP openssl 验证 tag
        ciphertext, 'aes-256-gcm', key, OPENSSL_RAW_DATA,
        nonce, tag                                // tag 传回，校验失败返回 false
    )
    return plaintext                              // false = 篡改或 key 错
```

### Go 端实现（手动重排对齐约定格式）

Go 标准库的 tag 位置改不了（`gcm.Seal/Open` 写死末尾），所以 **Go 端在调用标准库前后手动重排字节**，强行产出 / 解析约定的标准格式：

```
Go 加密（产出的密文必须长得像约定格式）：
  raw = gcm.Seal(nil, nonce, plaintext, nil)     // Go 标准库输出 ciphertext + tag（tag 在末尾）
  ciphertext = raw[0 : len(raw)-16]              // 切出 ciphertext
  tag        = raw[len(raw)-16 :]                // 切出 tag
  blob = nonce + tag + ciphertext                // 重排成约定格式（tag 在中间）
  return base64(blob)

Go 解密（收到约定格式的密文）：
  blob = base64decode(input)
  nonce      = blob[0:12]
  tag        = blob[12:28]
  ciphertext = blob[28:]
  raw = ciphertext + tag                         // 重排回 Go 标准库期望的格式（tag 在末尾）
  plaintext, err = gcm.Open(nil, nonce, raw, nil)
```

**两端必须字节级对齐同一套格式**。改了字节顺序、改了 tag 位置、改了 nonce 长度，对端立刻解不开，历史数据全废。

> Go 标准库默认布局与本约定不符，是技术事实（不是 Go 的缺陷，只是 Go 标准库的选择不同）。照本约定实现时，Go 端手动重排是必须的步骤。

## 密钥派生：PBKDF2-SHA256

固定用 **PBKDF2-SHA256**，**600000 次迭代**，派生到 **32 字节**（AES-256 key）。

### 迭代次数

600000 次是 **OWASP 2023 推荐值**（PBKDF2-SHA256）。低于这个数，配置里的密码若是弱口令，派生出的 key 会被离线穷举攻破。慢一点是对的——加密本来就不是高频操作，字段级加密每个请求也就解几次。

### 盐配置

```
盐从配置读：app.aes_salt
两端盐必须一致：一字节都不能差
生产环境必须配置自己的盐，禁用默认占位盐
```

**盐不一致 = 密钥不一致 = 互通断裂**。一端用盐 A 派生出 key A，另一端用盐 B 派生出 key B，两把钥匙开不了同一把锁。部署时两端的 `app.aes_salt` 必须核对成同一个值，这是运维 checklist 的必检项。

**默认盐仅是占位符**（开发/测试环境用），生产环境必须配置自己的盐。把默认盐带上生产 = 加密形同虚设。

### 密钥处理两条路

配置里给的东西有两种情况，库要都支持：

| 配置内容 | 处理方式 |
|---------|---------|
| **已是 32 字节的原始密钥** | 直接用作 AES-256 key，**不走 PBKDF2** |
| **密码 / 短字符串（不足 32 字节或非二进制）** | 用 PBKDF2-SHA256 + 盐 + 600000 次迭代派生到 32 字节 |

```
function deriveKey(configValue, salt):
    if len(configValue) == 32:
        return configValue                       // 满 32 字节直接用
    return pbkdf2Sha256(configValue, salt, 600000, 32)   // 否则派生

# 各语言的 PBKDF2 实现：
# PHP: hash_pbkdf2('sha256', configValue, salt, 600000, 32, true)
# Go:  crypto/pbkdf2 包或对应实现
# 两端派生算法和参数（哈希算法、迭代数、输出长度）必须完全一致
```

**为什么留"直接用 raw key"这条路**：对安全性要求高的部署，会用密钥管理服务（KMS）下发 32 字节随机 key。这种 key 已经足够强，再过 PBKDF2 是脱裤子放屁。两条路并存，让库既能配密码（易用），也能配 raw key（最安全）。

## IsEncrypted 长度探测

实际系统里常有"明文/密文混合字段"：同一个字段，历史数据是明文（老数据没加密），新数据是密文（约定格式产出的）。读取时需要**自动判断**要不要解密。

```
function isEncrypted(value):
    raw = base64decode(value)     // 先尝试 base64 解码
    if base64decode 失败:
        return false              // 连 base64 都不是，肯定是明文
    return len(raw) >= 29         // ≥ 29 字节视为可能是密文
```

**29 字节的来历**：`nonce[12] + tag[16] + 至少 1 字节 ciphertext = 29`。真实密文（加密身份证、手机号等）解码后必然 ≥ 29 字节；而正常明文（18 位身份证号解码回来 18 字节、11 位手机号 11 字节）都 < 29。

```
长度探测 + 解密兜底：
  if isEncrypted(value):
      plaintext, ok = decrypt(value)
      if ok:  return plaintext    // 确实是密文，解出来了
  return value                    // 探测错了或解密失败，原样当明文返回
```

**探测只是启发式，不是结论**。长度 ≥ 29 不一定真是密文（巧合的明文也可能解码到 29 字节），但配合"解密失败就当明文"的兜底，安全且无损：是密文就能解开，不是密文解密失败原样返回，不会丢数据。

## 跨语言互通场景

本范式的全部价值就在于：**两端密文双向流通，谁加的密谁都能解**。

| 场景 | 写入端 | 读取端 | 互通点 |
|------|--------|--------|--------|
| A 端写入加密身份证到 DB | A 端（约定格式） | B 端新服务读 | B 端按约定格式解析（Go 需重排字节） |
| B 端服务写回更新后的加密字段 | B 端（约定格式） | A 端老逻辑读 | B 端按约定格式产出，A 端直接解 |
| 语言迁移 | 历史数据（旧端加密） | 新系统 | 历史 DB 数据无需重新加密，新端对齐约定格式后直接读 |

**互通的前提三件套全部对齐**：

```
1. 算法：两端都是 AES-256-GCM              （少一个都不通）
2. 布局：两端都是 nonce[12] + tag[16] + ciphertext（约定格式）
3. 密钥：两端盐一致 → 派生出同一把 32 字节 key
```

任一项不对齐，互通立刻断裂。最常见的踩坑：Go 偷懒用了标准库默认布局（tag 在末尾），既读不懂另一端写的历史数据，写回去的密文对端也解不开。

## Good / Bad

| Good | Bad |
|------|-----|
| 固定 AES-256-GCM | 用 CBC（不防篡改）或 ECB（同等明文出同等密文） |
| 密文格式 `nonce + tag + ciphertext` 两端字节级统一 | 各端用各自标准库默认布局，各玩各的 |
| Go 手动重排字节对齐约定格式 | Go 直接用 `gcm.Seal` 默认输出（tag 在末尾） |
| PBKDF2-SHA256 600000 次迭代 | 迭代 1 万次图快，或干脆不派生直接用密码当 key |
| 盐两端配置一致（app.aes_salt），生产必配 | 两端盐不同，或用默认占位盐上生产 |
| 32 字节 raw key 直接用、否则派生 | 所有情况都派生（raw key 也过 PBKDF2，多此一举） |
| IsEncrypted 探测 + 解密失败兜底 | 只看长度就断定是密文，解密失败直接抛错丢数据 |
| 配 raw key 走 KMS 下发 | 把密码硬编码在代码里 |

## 红旗 - 停下重新评估

- 准备用 CBC / CTR / ECB 替代 GCM（丢了完整性保护或暴露明文模式）
- Go 端不重排字节，直接用 `gcm.Seal` 默认输出（tag 位置和约定格式对不上）
- 改 nonce 长度（不是 12）或 tag 长度（不是 16）（破坏互通格式）
- 修改字节布局顺序（如 tag 放末尾、nonce 放最后）（历史密文全废）
- 迭代次数低于 600000（OWASP 2023 红线）
- 两端配了不同的 `app.aes_salt`（派生出不同 key）
- 用默认占位盐上生产环境
- 把盐或密码硬编码、提交进 git
- IsEncrypted 探测失败就抛异常（明文历史数据会被误杀）

## 防止合理化

| 借口 | 现实 |
|--------|---------|
| "Go 标准库默认 tag 在末尾，顺手用默认多省事" | 省事一次，对端的历史密文全部解不开，迁移项目直接卡死 |
| "两端各用各的标准库默认布局，反正都是加密" | 两端布局不一致 = 互通断裂，跨服务/跨语言共享加密字段全废 |
| "CBC 也够安全，项目里一直用的" | CBC 不防篡改，密文注入攻击不报错，出了事查都查不出来 |
| "600000 次太慢，改成 10 万" | 10 万次抗离线穷举强度差一个数量级，弱口令密码会被秒破 |
| "盐随便填一个，反正加密了就行" | 两端盐不同 = 两把钥匙，互通直接断；盐要刻意核对成同一个值 |
| "用默认盐上生产也能跑" | 默认盐是公开占位符，等于没加密；生产必须配自己的盐 |
| "nonce 自己随便生成就行" | nonce 长度必须是 12 字节（GCM 标准），且同 key 下不能重复，重复=密钥泄漏 |
| "IsEncrypted 看长度就够了，解密失败直接报错" | 明文历史数据长度也可能 ≥29，报错会把正常数据当损坏，得加解密失败兜底 |
| "历史数据重新加密一遍不就行了" | 重新加密 = 停服迁移 + 全表读写，风险巨大；两端对齐约定格式本可零迁移互通 |
| "raw key 也过一遍 PBKDF2 更安全" | 32 字节随机 key 已经够强，再派生只是浪费 CPU，不增加安全性 |

## 何时触发

**以下场景必须按本范式设计：**

- 设计或实现敏感数据加密（身份证、手机号、银行卡等字段级加密）
- 跨语言系统需要加密数据互通（一端写、另一端读）
- 从一种语言迁移加密数据到另一种语言（历史 DB 密文无需重加密）
- 实现字段"明文/密文混合"的自动探测与兼容读取
- 选型 AES 加解密方案、密钥派生方式、密文存储格式
- 排查"对端解不开我方密文"、"跨语言密文对不上"等互通问题

**不触发：**

- 传输层加密（HTTPS / TLS，那是通道加密，不是字段加密）
- 密码哈希存储（bcrypt / argon2，那是单向哈希，不是可逆加解密）
- 只读现有加密代码、查资料（没在设计/实现）
- JWT 签名验证（那是签名，不是对称加密）

## 底线

**算法锁死 AES-256-GCM，布局锁死 nonce+tag+ciphertext（约定格式），密钥锁死 PBKDF2 同盐派生。**

两端字节级对齐同一套格式不是可选优化，是互通的前提。Go 标准库默认布局与本约定不符，Go 端手动重排字节是必须步骤。盐两端一字节都不能差，迭代次数一步都不能少，字节顺序一个位都不能动。生产环境必须配置自己的盐，禁用默认占位盐。

改了任一条——要么对端解不开，要么安全性塌方，要么历史数据全废。跨语言加密的互通性，是字节级精确对齐出来的，不是调通了一端就万事大吉。

这是不可协商的。
