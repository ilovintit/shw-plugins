# 前端通用设计与操作逻辑规范

## 概述

本 skill 是前端页面**操作逻辑与交互行为的通用规范**，跨 PC 端与移动端。视觉规范与端内差异见 **shw-frontend-spec-pc** 与 **shw-frontend-spec-mobile**；技术栈选型见 **shw-frontend-stack**。

**核心原则**：操作逻辑规范是强约束。违反 = 设计缺陷，不是风格差异。

---

## 数据获取铁律（最严重级别）

### 编辑/详情弹窗或页面必须调详情接口

```
✅ 打开编辑/详情 → 用行 ID 调详情接口 → 接口返回填充表单/展示
❌ 打开编辑/详情 → 把列表行数据直接塞进表单/展示
```

**为什么严重违法**：

1. 列表接口的字段往往是裁剪版（摘要字段），详情里需要的完整字段列表里没有，直接带入 = 空值/旧值假象
2. 列表数据可能已过期（他人已修改），带入的是**过期快照**，编辑保存会覆盖他人修改
3. 列表的展示值常经过格式化（日期格式化、字典翻译、金额格式化），带入表单后回传给后端的是**格式化后的脏数据**
4. 详情接口的字段演进与页面解耦；带列表数据则列表接口一动字段，编辑页跟着坏

**判定法**：编辑/详情弹窗或页面打开时，看它的数据来源——

```
数据来源是 xxxDetail(id) 之类的详情接口调用 → ✅
数据来源是列表 row / record / item 直接透传  → ❌ 严重违法，必须改
```

**唯一例外**：纯展示型快捷预览（不编辑、不回传）且产品明确接受摘要级内容时，可用列表数据做轻量预览，但正式详情入口仍必须走详情接口。拿不准就不豁免。

### 新建与编辑共用弹窗

新建/编辑通常共用一个表单弹窗组件：打开时以 `id` 区分——有 `id` 先调详情接口回填，无 `id` 空表单。共用的前提是编辑路径**必须**有详情回填这一步。

## 弹窗操作逻辑

### 打开与关闭

- 弹窗打开时机：数据请求在**打开时发起**（而非父页面预加载），loading 态显示在弹窗内容区
- 关闭拦截：表单有未保存修改时，关闭（点遮罩/×/ESC）必须二次确认（"修改尚未保存，确定离开？"），无修改直接关
- **提交中禁止关闭**：接口在途时禁用关闭入口，防重复提交与脏关闭
- 关闭必重置：弹窗关闭时重置内部状态（表单、校验、loading），下次打开是干净状态

### 保存与提交

- **提交按钮 loading + 防重**：提交中按钮进入 loading/禁用，接口返回前不可二次点击
- 校验前置：先前端校验，过了才发请求；校验失败定位到第一个错误字段并聚焦/滚动
- 成功后：toast 反馈 → 关弹窗 → **刷新列表**（列表数据已变，不刷新 = 展示过期）
- 失败后：弹窗不关，错误信息展示在弹窗内（表单内字段错误标红，非字段错误展示在弹窗顶部或 toast），已填数据必须保留
- 编辑保存后若父页面也展示该数据摘要，同步刷新父页面

### 删除

- 删除必须二次确认，确认文案带**对象标识**（"确定删除用户「张三」？"，不是干巴巴的"确定删除？"）
- 删除成功 → toast → 刷新列表；若删除的是当前页最后一条且不在第一页，回退一页再查
- 批量删除确认文案带数量

## 表单操作逻辑

- **校验时机**：失焦校验单字段，提交时校验全表单；不在每次键入时全表单校验（抖动）
- 错误展示：字段下方红字 + 输入框标红，错误信息说**具体原因**（"手机号格式不正确"），不是"输入有误"
- 默认值显式声明，不靠组件隐式行为
- 数字/金额输入：受控输入 + 明确精度约束；金额展示与传输的精度口径与后端约定一致（后端金额规范的传输格式，见后端相关规范）
- 联动：上级变化清空并重置下级选项（如省变了清空市），不留悬空的脏值
- 提交前序列化做 trim，避免首尾空格入库

---

## 列表操作逻辑

- **查询条件与分页状态联动**：改查询条件发起查询时**重置到第一页**（否则可能请求超出范围的空页）
- 刷新：条件不变时刷新保持当前页；条件变化回到第一页
- 空态：无数据展示空态提示（区分"无数据"与"加载中"与"查询无结果"），不是空白
- 加载态：首屏骨架屏/loading；翻页/筛选时列表 loading 或局部遮罩，不清空已有内容闪白
- 操作列：低频危险操作（删除）不放第一位；批量操作需在选中态下才可用，翻页/刷新清空选中时给出提示
- 分页参数越界（删完最后一页数据）自动修正页码重查

---

## 请求与错误反馈通用约定

- 请求层统一封装：loading 管理、错误码分发、登录态失效跳转、无权限提示，页面不各自手写
- 401（登录失效）→ 清登录态跳登录页（带回跳地址）；403 → toast 无权限提示；业务错误码 → toast 或表单内展示
- 网络错误/超时 → toast 可重试的错误提示，不静默吞掉
- **反馈三原则**：任何写操作必须有成功反馈；任何失败必须让用户知道原因；任何在途操作必须有 loading 态
- 禁止空 catch：catch 了就必须处理（提示或降级），不允许无声失败

---

## 状态与渲染

- 展示与数据分离：格式化（字典翻译、日期、金额）在渲染层做，不污染源数据
- 字典/枚举翻译统一走字典映射函数，不散落三元表达式
- 时间展示统一时区与格式口径，全项目一个格式化入口
- 竞态防护：快速切换查询条件/快速打开不同行的详情，旧请求的响应不得覆盖新请求的结果（带请求序号或取消旧请求）

---

## 红旗 — 停下

- 编辑/详情弹窗把列表 `row` 直接当数据源（**最严重**）
- 提交无 loading/防重，可连点
- 删除确认不带对象标识
- 改查询条件不重置页码
- 弹窗关闭不重置表单，二次打开残留上次数据
- catch 里什么都不做
- 快速切行详情出现"张冠李戴"的数据（竞态）

## 审计应用

对存量前端项目做全面审查时，逐页核对上述规则，优先扫"编辑/详情弹窗数据来源"这一项（violationPattern：编辑/详情组件的 props 含整个列表行对象、或打开弹窗时无详情接口调用）。发现即标记为**严重级别**，逐页产出违规清单后统一修复。
