# 审查源代码与 Issue 设计的一致性

## 概述

apply 实现了 Issue 验收 checklist 对应的功能，但实现是否真的满足了设计和需求？本 skill 强制做逐字符审查，确保代码与设计意图完全一致。

**核心原则**：测试通过 ≠ 满足需求。测试可能漏覆盖、实现可能偏离设计、边界场景可能没处理。只有逐字符审查代码与设计文档的对应关系，才能确认交付质量。（测试用例自身的基准对齐由 /shw-test-review 前置把关——本 skill 聚焦**实现**与基准的一致性，不重复用例对账。）

## 触发时机

| 时机 | 审查范围 | 说明 |
|------|---------|------|
| **自我审查阶段**（/shw-apply 内，提 PR 前，强制） | 本次 apply 涉及的全部代码变更 | 第一次审查，循环到红黄清零（🔴 修复 + 🟡 处置） |
| **PR 合并前**（CI 全绿后，强制） | 该 PR 的全部代码变更 | 第二次审查（完整复审） |

双次审查的理由：
- 第一次（提 PR 前）：趁记忆新鲜，快速发现偏离，不让 🔴 进 PR
- 第二次（合并前）：CI 绿只证明测试过，不证明设计对；整体视角发现集成问题和遗漏

## 审查方法：逐字符代码审计

### 审查输入

1. **Issue 与文档**（设计基准）：
   - Issue 正文 + 验收 checklist — 需求与范围（每条 AC = 验收标准）
   - `docs/architecture/<功能>.md` — 技术决策和架构（"备选与风险"章节是决策依据）
   - `docs/prd/<模块>.md` 对应章节 — 业务规则（验收标准原文）
   - `docs/design/` 原型 — 前端活的交互与字段基准
2. **需求讨论上下文**（如果存在）：Issue 评论时间线中讨论的需求和约束
3. **源代码变更**：本次 PR 修改/创建的所有文件
4. **项目 AGENTS.md**（如果存在）：项目约定和反模式

### 审查维度

#### 1. 需求覆盖：验收 checklist / AC → 代码

逐个检查验收 checklist 的每条 AC（及 PRD 中更细的业务规则）：

```
对每条 AC：
  1. 找到对应的代码实现位置
  2. 逐行阅读，确认：
     - WHEN 条件是否被正确处理
     - THEN 预期是否被实现
  3. 如果找不到对应实现 → 🔴 遗漏
  4. 如果实现与 AC 描述不符 → 🔴 偏离
```

**常见问题**：
- AC 描述了错误处理路径，但代码没有 try/catch
- AC 声明了权限检查，但代码没有鉴权逻辑
- AC/PRD 定义了数据格式约束，但代码没有校验

#### 2. 设计符合：技术方案决策 → 代码

逐个检查技术方案中的每个技术决策：

```
对每个设计决策：
  1. 找到代码中体现该决策的地方
  2. 确认实现方式与决策一致
  3. 如果代码采用了不同方案 → 🔴 违背设计
```

**常见问题**：
- 方案说用事件驱动，代码用了直接调用
- 方案说分四层，代码全部堆在一个文件
- 方案说用事务，代码没有事务包裹

#### 3. 项目约定：AGENTS.md → 代码

检查代码是否遵守项目级 AGENTS.md 的约定：

```
对 AGENTS.md 中的每条规则：
  1. 检查变更的代码是否遵守
  2. 如果违反 → 🟡 违反约定
```

**常见问题**：
- AGENTS.md 禁止 any 类型，代码用了 any
- AGENTS.md 要求文件头声明，代码没有
- AGENTS.md 禁止跨模块直接调用，代码违反了

#### 4. 反模式检查

逐段阅读代码，检查常见反模式：

| 反模式 | 检查方法 |
|--------|---------|
| 硬编码 | 代码中是否有写死的 URL/端口/路径/密钥 |
| 魔数 | 代码中是否有未命名常量 |
| 无限循环/递归 | 是否有终止条件缺失 |
| 资源泄漏 | 文件/连接/定时器是否正确释放 |
| 错误吞没 | catch 块是否真的处理了错误还是默默忽略 |
| 安全漏洞 | 是否有 SQL 注入/XSS/路径穿越风险 |

#### 5. 边界完整性

针对需求讨论和技术方案中提到的边界场景：

```
对每个边界场景：
  1. 空值/null/undefined 处理
  2. 空列表/空字符串/零值处理
  3. 最大值/溢出处理
  4. 并发/竞态处理
  5. 权限边界处理
```

## 审查报告格式

```
## 代码审查报告：Issue #<N>

### 审查范围
- 代码变更：<N> 个文件，<M> 行变更
- 审查基准：验收 checklist + 技术方案 + PRD + 原型
- 审查时机：提 PR 前第一次 / 合并前第二次

### 🔴 必须修复（<N> 项）
1. [需求遗漏] 验收 checklist AC2 "手机号已注册返回 409" 没有代码实现
   - AC 原文：WHEN 用户用已注册手机号注册 THEN 返回 409
   - 代码位置：src/api/user/controller.ts:45 — 缺少重复检查
   - 建议：在注册逻辑中添加手机号唯一性校验

2. [设计违背] 技术方案说用 Repository 模式，但代码在 Controller 直接操作数据库
   - 方案原文："数据访问通过 Repository 接口隔离"
   - 代码位置：src/api/user/controller.ts:23 — 直接调用了 db.query()
   - 建议：提取 UserRepository，Controller 通过 Repository 访问

### 🟡 建议修复（<N> 项）
1. [反模式] src/api/user/service.ts:18 — 超时时间硬编码为 5000
   - 建议：提取为常量或配置项

### ✅ 通过项
- 需求覆盖：X/Y 条 AC 有对应实现
- 设计符合：X/Y 个设计决策被正确落地
- 项目约定：代码遵守 AGENTS.md 的全部规则
- 无反模式：硬编码/魔数/资源泄漏/安全漏洞检查通过
- 边界完整：X/Y 个边界场景已处理
```

## 审查后的行动

- **有 🔴 项**：
  - 第一次审查：必须修复后才能提 PR。列出修复建议，可委派子智能体修复（shw-apply 的审查循环）。
  - 第二次审查：必须修复后才能合并，CI 全绿不豁免。
- **只有 🟡 项**：同样不放过——逐条经用户裁决处置（修复，或豁免并记录理由），处置结果列入 PR 描述的 🟡 区段；未经处置的 🟡 不得视为审查通过。
- **全部 ✅**：宣布审查通过。

## 双次审查的差异

| 维度 | 提 PR 前第一次 | 合并前第二次 |
|------|---------------|-------------|
| 范围 | 本次 apply 涉及的代码 | 该 PR 的全部代码变更（可能多轮修复累积） |
| 重点 | 单次实现的正确性 | 全部变更的集成一致性 |
| 视角 | 逐 AC 检查 | 跨 AC 整体检查 |
| 发现的问题类型 | 遗漏、偏离、设计违背 | 集成断裂、累积偏移、边界遗漏 |

## 约束

- **逐字符审查，不是粗略浏览**。每个变更文件都要从头到尾读完。
- **必须对比 AC/方案原文和代码实现**。不能只看代码"差不多对"就放过。
- **审查报告必须包含具体引用**（PRD/方案原文 + 代码位置:行号），不能只说"有问题"。
- **不修改代码**——只报告问题，修复由 apply 审查循环执行。
- **第二次审查（合并前）必须独立于第一次**。即使第一次全通过，第二次也要完整重审，因为修复迭代可能破坏之前的实现。
