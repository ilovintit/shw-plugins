# DDD 四层架构设计规范

## 概述

本 skill 是后端 DDD 四层架构的**单一权威定义**，跨语言、跨框架。四层划分（domain/application/interfaces/infrastructure）是通用设计范式，与具体语言无关。

所有后端文件必须按此规范归位，跨层依赖必须遵循此规范的方向约束。

**核心原则**：架构分层是强约束，不是建议。放错层 = 技术债。

**层名只是语义标签**：本规范用 `domain/application/interfaces/infrastructure` 表达层语义。目录命名风格（大小写、下划线、复数）和模块的物理根路径，由各语言/框架的编码约定决定。具体框架如何落地分层（依赖注入方式、路由注册、模型映射），参见各自的 conventions skill。

---

## 依赖方向（不可违反）

```
Interfaces ──→ Application ──→ Domain ←─── Infrastructure
   (入口)         (编排)        (核心)        (实现)
                                   ↑
                          Infrastructure 实现 Domain 的 Repository 接口
                          （依赖倒置：Domain 定义契约，Infrastructure 实现）
```

**铁律**：
- Domain 层**不依赖**任何外层（不引用 Infrastructure、不引用 Application、不依赖 ORM 模型）
- Infrastructure **依赖** Domain（实现 Domain 定义的 Repository 接口）
- Application 编排 Domain（调用 Domain Service / Repository 接口）
- Interfaces 只调用 Application（不直接碰 Domain 或 DB）
- 所有箭头指向 Domain，Domain 是最内层

```
没有新鲜的依赖倒置，不声称分层正确
```

若 Domain 里出现了对框架、DB、外部服务的直接引用，分层已经被破坏，无论目录摆得多整齐。

## 四层职责定义

### Domain 层 — "核心业务规则"

纯业务，不依赖任何框架、不依赖 DB、不依赖基础设施。这一层的代码可以被任何框架复用。

| 放什么 | 不放什么 |
|--------|---------|
| 领域实体 / 聚合根（有唯一标识，含业务行为方法） | ORM 模型 / 数据表映射 |
| 值对象（无标识，不可变，如金额、地址、状态码） | 可变状态、DB 字段映射 |
| 领域服务（跨实体的业务逻辑，不属于单个实体） | 直接访问 DB（必须通过 Repository 接口） |
| Repository **接口**（数据访问契约，只定义不实现） | 实现细节（归 Infrastructure） |
| 其他领域契约/防腐层接口（对接外部系统的抽象） | 外部系统的具体实现 |
| 领域事件（业务意义上发生的事，如"用户已注册"） | 事件监听器（归 Application） |
| 编码生成规则（如订单号、合同号的生成逻辑） | 与 DB 交互 |
| 领域异常（业务规则被违反，如"库存不足"） | 技术异常 |

### Application 层 — "业务编排"

不含业务规则，只负责编排一个业务操作的流程。

| 放什么 | 不放什么 |
|--------|---------|
| 请求/响应 DTO（出入参数据结构） | 业务校验规则（归 Domain） |
| 用例 UseCase（编排多个领域对象完成一个业务操作） | 业务规则（归 Domain Service / Entity） |
| 事件监听器（监听领域事件，执行副作用如发通知） | 业务规则（只编排，不写规则） |
| 应用层异常（业务流程异常，如"资源不存在"、"操作无权限"） | 技术异常（归 Infrastructure） |

**用例的职责边界**：用例编排流程（"先查、再校验、再改、再发事件"），但**业务规则由领域服务/实体承载**。用例调用它们，不自己写规则。

### Interfaces 层 — "系统入口"

外部交互层，系统的入口。按"端"分组（同一模块服务多个端时，每端一个子目录，如 admin/client/tenant）。

| 放什么 | 不放什么 |
|--------|---------|
| 请求处理器/控制器（接收请求、提取参数、调用用例、返回响应） | 业务逻辑、直接查 DB |
| CLI 命令（如数据修复、批处理） | 业务逻辑（应调用用例） |
| 常驻进程入口（消费 MQ、定时任务、长连接） | 业务逻辑（应调用用例） |
| 接口层异常处理（如参数校验异常的转换） | — |

### Infrastructure 层 — "技术实现"

技术实现细节，一切与框架、DB、外部系统打交道的代码。

| 放什么 | 不放什么 |
|--------|---------|
| ORM 模型 / 数据表映射（定义字段、关系） | 业务逻辑 |
| Repository 接口的实现（查 DB 模型，转换为领域实体） | 业务规则（只做数据格式转换） |
| 外部服务客户端（第三方 API 调用、消息推送） | 业务判断 |
| 基础设施异常（DB 连接失败、第三方 API 超时、网络错误） | 业务异常 |

**仓储实现的职责**：实现 Domain 层定义的 Repository 接口。从 DB 查出模型，转成领域实体返回。这里做数据格式转换（DB 行 ↔ 实体），**不做业务判断**。

## Module 模式

每个业务模块是一个独立、完整的四层结构。模块内自治，模块间通过应用层或共享服务协作。

```
{module}/                         ← 一个业务模块（物理根路径由各框架约定）
│
├── interfaces/                   ← 系统入口
│   ├── {end}/                    ←   按端分组（admin / client / tenant 等）
│   │   ├── http/                 ←     请求处理器/控制器（取参 + 调用用例）
│   │   └── command/              ←     该端的 CLI 命令
│   ├── process/                  ←   常驻进程（队列消费者、定时任务、长连接）
│   └── exception/                ←   接口层异常处理
│
├── application/                  ← 业务编排
│   ├── dto/                      ←   请求/响应 DTO
│   ├── usecase/                  ←   用例（编排领域对象完成一个业务操作）
│   ├── listener/                 ←   事件监听器（监听领域事件，做副作用）
│   └── exception/                ←   应用层异常（"资源不存在"、"权限不足"）
│
├── domain/                       ← 核心业务规则（纯业务，不依赖任何框架/DB）
│   ├── entity/                   ←   聚合根 + 实体（含业务行为方法）
│   ├── valueobject/              ←   值对象（无标识，不可变）
│   ├── service/                  ←   领域服务（跨实体的业务逻辑）
│   ├── repository/               ←   仓储接口（契约，只定义不实现）
│   ├── contract/                 ←   其他领域契约/防腐层接口
│   ├── event/                    ←   领域事件
│   ├── coderule/                 ←   编码生成规则（如订单号生成）
│   └── exception/                ←   领域异常（"库存不足"、"状态不允许此操作"）
│
├── infrastructure/               ← 技术实现细节
│   ├── model/                    ←   ORM 模型 / 数据表映射（不进 domain）
│   ├── persistence/              ←   仓储接口的实现（查 DB，转实体）
│   └── exception/                ←   基础设施异常（连接失败、超时）
│
└── {module_entry}                ← 模块入口：集中做路由注册 + 依赖注入装配
```

### 模块入口的职责

每个模块有一个入口（具体形态由各框架定：可能是模块注册文件、服务提供者、路由注册函数等），集中做两件事：

1. **路由注册**：把本模块的请求处理器/CLI 命令挂到框架路由上
2. **依赖注入装配**：手工构造各层对象，把仓储实现注入到用例，把用例注入到控制器

```
✅ 模块入口一处装配全部依赖，依赖关系显式可见
❌ 依赖关系靠全局单例/运行时查找隐式散落各处（Service Locator 反模式）
```

依赖倒置靠模块入口接线实现：domain 定义接口，infrastructure 实现，application 依赖接口，模块入口负责把实现塞进接口。具体注入方式（构造函数注入、结构体字段、setter）由各语言 conventions 决定。

## Shared 模式

Shared 放**跨模块共享**的代码，同样遵循四层结构。

```
shared/                           ← 跨模块共享（物理根路径由各框架约定）
│
├── interfaces/                   ← 全局入口（跨模块共享）
│   ├── http/                     ←   全局请求处理器（如健康检查）
│   ├── middleware/               ←   全局请求管道装配（把基础设施中间件挂到链上）
│   └── command/                  ←   全局 CLI 命令（数据填充、缓存清理等）
│
├── application/                  ← 跨模块共享的应用层
│   └── enum/                     ←   共享应用枚举（如全局错误码）
│
├── domain/                       ← 跨模块共享的领域层
│   ├── enum/                     ←   共享领域枚举（通用业务状态码）
│   └── service/                  ←   共享领域服务（如密码生成器）
│
└── infrastructure/               ← 跨模块共享的基础设施
    ├── service/                  ←   共享基础设施服务（会话、短信、存储等组件接入）
    └── enum/                     ←   基础设施枚举（如基础设施错误码）
```

### Shared 的使用原则

- **只有真正被多个模块共享的代码才放这里**。单模块使用的代码留在自己模块内。
- **Shared 不是垃圾桶**。如果不确定，先放模块内。等第二个模块需要时再提取。
- **提取时机**：第二处复用发生时再下沉到 Shared，不要提前抽象。

| Good | Bad |
|------|-----|
| 第二个模块需要时才下沉到 Shared | 为了"复用"提前抽到 Shared |
| 单模块代码留在模块内 | 把可能复用的代码都堆进 Shared |

## 组件库组件归层约定

项目引入组件库（如会话、短信、加密、序列号、分布式锁、存储等）时，组件按性质归层。这是跨语言的通用约定：

| 组件类型 | 归层 | 理由 |
|---------|------|------|
| 会话/认证服务（session） | infrastructure | 技术基础设施，与业务无关 |
| 认证/权限中间件 | infrastructure | 横切关注点的技术实现 |
| 短信/企微/通知通道 | infrastructure | 外部通道，技术实现 |
| 加密/序列号/分布式锁 | infrastructure | 技术工具服务 |
| 存储驱动/地区数据源 | infrastructure | 基础设施适配 |
| 请求/响应 DTO | application | 应用层数据契约 |
| 仓储接口 | domain | 数据访问契约属于领域 |
| 业务枚举/业务错误码 | domain | 承载业务语义 |
| 全局错误码/通用状态码 | shared | 跨模块共享 |

**中间件归层的边界**：中间件的**代码实现**归 infrastructure（它是认证机制的技术实现）；interfaces 层负责把它**装配**到请求管道。interfaces 不含技术实现细节，只负责组装。

**组件库与业务解耦**：组件库本身是独立的项目，不依赖任何业务模块。业务项目在 infrastructure 层接入组件库（实例化、配置、包装成领域需要的接口），domain 层只依赖自己定义的抽象接口，不直接依赖组件库。

## 依赖倒置原则

```
高层不依赖低层细节，二者都依赖抽象。
抽象（接口）属于 Domain，细节（实现）属于 Infrastructure。
```

具体表现：

- Domain 定义 Repository 接口（"我需要按 ID 查用户"），不关心数据来自 MySQL、Redis 还是第三方
- Infrastructure 实现 Repository 接口（"我用 ORM 查 MySQL 转成实体"）
- Application 依赖 Domain 的接口编程，由模块入口在运行时注入具体实现

```
✅ Domain 定义接口，Infrastructure 实现，模块入口接线
❌ Domain 直接 import ORM / DB 客户端 / 第三方 SDK
```

这是四层架构能"换框架不换业务"的根本——Domain 是稳定的业务核心，Infrastructure 是可替换的技术细节。

## 异常分层规则

每层有自己的异常目录，异常**不跨层抛**：

| 层 | 异常类型 | 语义 | 谁处理 |
|----|---------|------|--------|
| Domain | 业务规则被违反 | "库存不足"、"状态不允许此操作" | Application 捕获，转业务错误响应 |
| Application | 业务流程异常 | "资源不存在"、"操作无权限" | Interfaces 捕获，转响应 |
| Infrastructure | 技术故障 | "DB 连接失败"、"第三方超时" | Application 捕获或全局处理 |

**规则**：底层抛的异常由上层捕获并转换，不让技术异常泄漏到业务层，也不让业务异常泄漏到框架层。异常类型的具体命名（后缀、错误码体系）由各语言 conventions 决定。

## 常见错误（禁止）

- ❌ **请求处理器直接查 DB** → 必须通过用例 → 仓储
- ❌ **Domain 层引用 ORM 模型/DB 客户端** → Domain 不依赖框架
- ❌ **Repository 接口放 Infrastructure** → 接口属于 Domain，实现属于 Infrastructure
- ❌ **跨模块直接访问数据模型** → 通过应用层或共享服务协作
- ❌ **业务规则写在用例里** → 业务规则属于领域服务/实体
- ❌ **单模块代码放 Shared** → 先放模块，等共享时再提取
- ❌ **异常跨层泄漏** → 每层捕获并转换为本层异常类型
- ❌ **中间件实现塞进 interfaces** → 实现归 infrastructure，interfaces 只装配
- ❌ **DTO 里写业务校验规则** → DTO 只描述数据结构，校验归 Domain

## 红旗 — 停下

- Domain 目录里出现对框架/DB/外部 SDK 的引用
- 用例里出现 if-else 分支的业务判断（应是领域对象的职责）
- 控制器里出现事务开启、DB 查询
- 仓储接口和实现放在同一个目录
- 为了"以后可能复用"把代码提前放进 Shared
- 一个模块直接 new 另一个模块的数据模型

## 判定法：文件该放哪层？

```
问：这个文件包含业务规则吗？
├─ 是 → Domain（entity / valueobject / service / coderule / event）
└─ 否 → 它做什么？
   ├─ 接收 HTTP/CLI/MQ 请求 → Interfaces（控制器 / 命令 / 进程入口）
   ├─ 编排一个业务操作 → Application（usecase / dto / listener）
   ├─ 访问 DB / 外部系统 / 技术工具 → Infrastructure（persistence / model / 外部客户端）
   ├─ 是组件库接入点 → Infrastructure（service / 中间件实现）
   └─ 跨模块共享 → Shared（按上述规则选层）
```

**快速判断**：
- 换掉框架/DB 这段代码还成立吗？成立 → Domain
- 它描述了一次业务操作的流程吗？是 → Application
- 它是系统的外部入口吗？是 → Interfaces
- 它跟具体技术（DB/HTTP 客户端/SDK）绑死吗？是 → Infrastructure
