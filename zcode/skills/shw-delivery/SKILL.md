执行前必须读取 `shw-issue-gate`；修改前读取 `shw-workspace` 并确认项目、目录、Issue 与所有权。项目外只读，未知修改不覆盖；能力缺失不扩大授权。

# 单 Issue 交付

先读项目模式、`shw-gitea-flow`、`shw-acceptance` 和 `shw-verify`。每轮 Issue 交付对应一个分支与 PR；核对已有匹配 Issue/占用，优先复用当前范围匹配且未合并的 PR，不重复派工。重开已交付 Issue 后，从当前模式来源分支进入新一轮修正，使用新的编号分支和 PR，不复用已合并 PR；仍须通过工作区提供者确认所有权。

## 主动使用子智能体

开发开始、任务拆分、进入审查及出现新的独立工作时，必须读取 `shw-subagent-dispatch`，主动评估并优先使用子智能体（子代理）。有输入充分、边界明确且能独立推进的调查、实现、文档或审查任务，宿主允许时应实际派发，不等待用户点名，不以主代理也能完成为由默认全部单干。本开发入口明确要求在已授权的当前 Issue 范围内委派，无需用户逐次再次授权；用户禁止或宿主限制仍优先。

简单、局部且拆分没有实际收益的任务直接完成，不为数量制造子任务。依赖输出、共享契约或同文件修改先串行确定，再派发独立部分；写入文件所有权必须互斥，只读审查使用明确的固定候选或在写入结束后进行。按 `shw-issue-parallel` 核对占用、目录和权限，不增加跨 Issue 调度、测试、合并、部署或发布授权。主代理持续推进独立工作，负责整合与审查结果。进度中简述派发目标与边界；无合适任务或能力受限时说明具体原因，不反复请求已获得的委派授权。

## 交付步骤

1. 读取 Issue、评论、依赖、相关实现和当前规格。确认范围、非目标、人工可判定 AC，以及依赖已进入来源分支。
2. 通过 `shw-workspace` 确认工作区所有权；列出实现与体验计划。初版只需够用 PRD/技术方案，直接做可体验版本，无独立原型阶段。
3. 实现并在同一变更同步文档：业务逻辑、权限、状态流转更新 PRD；接口、数据、架构更新技术文档。当前已实现规格与待实现方案明确分开，Issue 摘要不能代替规格。
4. 读取 `shw-pr-review`，检查 diff、AC、安全、兼容与文档。测试与开发、集成、发布、部署解耦：单元、API、E2E、VRT、回归及冒烟均仅在用户明确要求后，在专用 Mac mini 的本地隔离工作区固定提交执行。普通 push/PR/tag/部署不触发测试，线上 test 分支测试入口退役；未测试不阻挡已授权发布。必要构建/编译、静态与配置检查、来源核对正常执行，不得借“检查”名义运行测试；构建成功不代表测试或人工验收通过。
5. 执行体验所需构建、打包和部署，核对实际脚本依赖。审查脚本依赖中是否夹带测试；测试链按项目授权迁移到 Mac mini 本地入口，不以发布请求自动授权测试。不得force合并或伪造检查；服务端旧测试保护尚未迁移时报告确切阻塞。
6. 更新同一 PR，按真实授权与路由合入目标分支：`issue-dev` / `managed` 为 `dev`，`issue-main` 为 `main`。回读确认 PR 实际 merged、目标分支和 merge commit 后，立即按 `shw-gitea-flow` 关闭已完成交付范围的 Issue 并回读验证。不能只写 `Closes #N` 等待默认分支自动关闭，也不等待后续部署、dev→main 集成、正式发布、测试或人工验收。记录必要静态检查、构建与变更审查证据；没有明确测试请求则记录未测试。
7. 继续完成已授权的构建/部署跟进，提供真实入口、角色/数据、体验步骤、源码 SHA、制品 digest、部署 revision、已知限制。未体验/未验收如实记录，与 Issue 已关闭并存；交接后结束本工单开发，不因等待用户反馈持续挂单。后续反馈优先新建关联修正 Issue，也可根据实际反馈重新打开原 Issue，再以新的修正 PR 交付并同步代码文档；不能在已合并 PR 上继续追加修正。
8. 回写合并、Issue 关闭及部署/体验的各自事实，按工作区提供者安全释放/清理。关闭失败报告实际错误和待办，不冒称已关闭；未知修改、他人占用或分叉现场保留，不自动删除。

范围或契约发生需用户裁决的变化时提出具体方案；在已有授权内继续无关独立工作。roadmap 复用此内核；并行仅按 `shw-issue-parallel` 的所有权约束。

## 持续推进与开发部署

测试阶段调整不撤销已有 dev 合并、自动部署或数据库迁移授权。核对项目现有触发链和目标，按原授权运行；既有自动迁移不擅自改为手动，原本由用户执行的迁移也不擅自接管。集群与命名空间是不同字段，使用当前项目确认值，不把某项目示例固化为公司全局目标。

用户已授权多个独立项目持续推进时，一个项目的具体阻塞只停止其依赖工作；其余项目由各自获授权工作区/任务继续。不得因“持续推进”跨项目写入、自动派工或扩大合并/部署权限。

## 合并后部署跟进与体验交接

存在已授权的开发部署、正式发布或制品发布任务时，PR merged、Issue closed、CI 构建绿和 T3 settled 都不是会话交付终点。合并后继续跟进该候选的实际部署链；Issue 按规则及时关闭，部署任务仍保留在当前计划/交付记录中，不能因此结束或清理工作区。

1. 回读 merge SHA，找到对应构建/上传/部署任务；保存候选 SHA、制品 digest、部署 revision、目标环境和日志链接。共享开发环境只有一个时，按既有 dev 部署链交付，不为每个 PR 擅切分支。
2. 用项目已授权的只读来源核对部署结果：GitOps/Fleet 声明同步及实际工作负载 Ready/运行镜像与候选对应；其他部署平台按其实际运行版本/发布状态核对。构建成功、镜像已推送或声明已更新均不能单独称为已部署。平台不提供某层证据时明确缺失，不编造通过，不扩大集群权限。
3. 多个提交共享部署时，确认实际运行版本包含本次 merge SHA；若被更新候选取代，记录最终版本及包含关系，不把他人部署或旧版本证据套在本次修改上。无法证明包含关系时停止“可体验”结论。
4. 部署运行中继续通过宿主可用的持续任务/事件机制跟进。T3 watch_pull_request 只观察开放 PR 的检查/审阅，合并后会停止，不能作为部署观察器；不用已合并 PR 的 watch 或虚构任务维持会话；遵守当前宿主的等待限制。没有事件订阅本身不是停止理由，当前轮仍可只读推进时继续查询准确候选的部署状态、分析日志和处理授权内问题，不能第一次读到 running 就交回。仅宿主实际中断或确认能力限制无法继续时，保留明确待办、运行链接与恢复步骤，报告“部署未确认”，不称完成或邀请体验。
5. 部署失败时读取真实日志，在授权内修复并跟进；确切权限或外部阻塞才交接具体动作。只有上述实际部署证据齐全后，才通知用户“开发环境已部署，可体验”，附环境入口、实际运行版本、体验步骤与已知限制。插件无应用环境时以市场/tag/附件及来源完整性作为制品交付证据，说明用户仍需自行安装，不称已替用户安装。

T3 在 PR 合并时可能自动收起线程。识别仍有部署任务时，在交付计划和 PR/Issue 记录明确合并后步骤；建议用户在本线程菜单 Auto-settle behavior 选择 Disabled，或关闭合并自动收起。不得擅改用户配置。若 T3 已中断运行，恢复后先查询部署状态继续原任务，不重复合并/部署，也不把中断当成功。技能不能保证宿主一定持续调度，能力限制必须如实说明。

以上为部署状态与来源取证，不新增测试/API 请求、页面点击、冒烟或人工验收门禁；未体验和未测试仍分别如实记录。
