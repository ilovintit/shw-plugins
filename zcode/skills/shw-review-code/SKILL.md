# 审查源代码与 change 设计的一致性

## 概述

apply 实现了 change 的 tasks，但实现是否真的满足了设计和需求？本 skill 强制做逐字符审查，确保代码与 change 的设计意图完全一致。

**核心原则**：测试通过 ≠ 满足需求。测试可能漏覆盖、实现可能偏离设计、边界场景可能没处理。只有逐字符审查代码与设计文档的对应关系，才能确认交付质量。

## 触发时机

| 时机 | 审查范围 | 说明 |
|------|---------|------|
| **apply 完成后**（强制） | 本次 apply 涉及的全部代码变更 | 第一次审查 |
| **归档前**（强制） | change 的全部代码变更 | 第二次审查（完整复审） |

双次审查的理由：
- 第一次（apply 后）：趁记忆新鲜，快速发现偏离
- 第二次（归档前）：全部变更累积后的整体视角，发现集成问题和遗漏

## 审查方法：逐字符代码审计

### 审查输入

1. **change artifact**（设计基准）：
   - `proposal.md` — 变更动机和范围
   - `specs/` — 需求规格（scenario = 验收标准）
   - `design.md` — 技术决策和架构
   - `tasks.md` — 实现清单
2. **explore 上下文**（如果存在）：对话历史中讨论的需求和约束
3. **源代码变更**：本次 apply 修改/创建的所有文件
4. **项目 AGENTS.md**（如果存在）：项目约定和反模式

### 审查维度

#### 1. 需求覆盖：specs scenario → 代码

逐个检查 specs 中的每个 scenario：

```
对每个 scenario：
  1. 找到对应的代码实现位置
  2. 逐行阅读，确认：
     - WHEN 条件是否被正确处理
     - THEN 预期是否被实现
  3. 如果找不到对应实现 → 🔴 遗漏
  4. 如果实现与 scenario 描述不符 → 🔴 偏离
```

**常见问题**：
- scenario 描述了错误处理路径，但代码没有 try/catch
- scenario 声明了权限检查，但代码没有鉴权逻辑
- scenario 定义了数据格式约束，但代码没有校验

#### 2. 设计符合：design 决策 → 代码

逐个检查 design 中的每个技术决策：

```
对每个 design decision：
  1. 找到代码中体现该决策的地方
  2. 确认实现方式与决策一致
  3. 如果代码采用了不同方案 → 🔴 违背设计
```

**常见问题**：
- design 说用事件驱动，代码用了直接调用
- design 说分三层，代码全部堆在一个文件
- design 说用事务，代码没有事务包裹

#### 3. 项目约定：AGENTS.md → 代码

检查代码是否遵守项目级 AGENTS.md 的约定：

```
对 AGENTS.md 中的每条规则：
  1. 检查变更的代码是否遵守
  2. 如果违反 → 🟡 违反约定
```

**常见问题**：
- AGENTS.md 禁止 any 类型，代码用了 any
- AGENTS.md 要求文件头声明，代码没有
- AGENTS.md 禁止跨模块直接调用，代码违反了

#### 4. 反模式检查

逐段阅读代码，检查常见反模式：

| 反模式 | 检查方法 |
|--------|---------|
| 硬编码 | 代码中是否有写死的 URL/端口/路径/密钥 |
| 魔数 | 代码中是否有未命名常量 |
| 无限循环/递归 | 是否有终止条件缺失 |
| 资源泄漏 | 文件/连接/定时器是否正确释放 |
| 错误吞没 | catch 块是否真的处理了错误还是默默忽略 |
| 安全漏洞 | 是否有 SQL 注入/XSS/路径穿越风险 |

#### 5. 边界完整性

针对 explore 上下文和 specs 中提到的边界场景：

```
对每个边界场景：
  1. 空值/null/undefined 处理
  2. 空列表/空字符串/零值处理
  3. 最大值/溢出处理
  4. 并发/竞态处理
  5. 权限边界处理
```

## 审查报告格式

```
## 代码审查报告：<change-name>

### 审查范围
- 代码变更：<N> 个文件，<M> 行变更
- 审查基准：proposal + specs + design + tasks
- 审查时机：apply 后第一次 / 归档前第二次

### 🔴 必须修复（<N> 项）
1. [需求遗漏] specs/user-module.md 的 Scenario "手机号已注册" 没有代码实现
   - spec 原文：WHEN 用户用已注册手机号注册 THEN 返回 409
   - 代码位置：src/api/user/controller.ts:45 — 缺少重复检查
   - 建议：在注册逻辑中添加手机号唯一性校验

2. [设计违背] design 说用 Repository 模式，但代码在 Controller 直接操作数据库
   - design 原文："数据访问通过 Repository 接口隔离"
   - 代码位置：src/api/user/controller.ts:23 — 直接调用了 db.query()
   - 建议：提取 UserRepository，Controller 通过 Repository 访问

### 🟡 建议修复（<N> 项）
1. [反模式] src/api/user/service.ts:18 — 超时时间硬编码为 5000
   - 建议：提取为常量或配置项

### ✅ 通过项
- 需求覆盖：X/Y 个 scenario 有对应实现
- 设计符合：X/Y 个 design decision 被正确落地
- 项目约定：代码遵守 AGENTS.md 的全部规则
- 无反模式：硬编码/魔数/资源泄漏/安全漏洞检查通过
- 边界完整：X/Y 个边界场景已处理
```

## 审查后的行动

- **有 🔴 项**：
  - apply 后第一次审查：必须修复后才能继续。列出修复建议，可委派子智能体修复。
  - 归档前第二次审查：必须修复后才能归档。阻断 `/shw-archive`。
- **只有 🟡 项**：提示用户，建议修复但不阻塞。
- **全部 ✅**：宣布审查通过。

## 双次审查的差异

| 维度 | apply 后第一次 | 归档前第二次 |
|------|---------------|-------------|
| 范围 | 本次 apply 涉及的代码 | change 的全部代码变更（可能多次 apply 累积） |
| 重点 | 单次实现的正确性 | 多次实现的集成一致性 |
| 视角 | 逐 task 检查 | 跨 task 整体检查 |
| 发现的问题类型 | 遗漏、偏离、设计违背 | 集成断裂、累积偏移、边界遗漏 |

## 约束

- **逐字符审查，不是粗略浏览**。每个变更文件都要从头到尾读完。
- **必须对比 spec 原文和代码实现**。不能只看代码"差不多对"就放过。
- **审查报告必须包含具体引用**（spec/design 原文 + 代码位置:行号），不能只说"有问题"。
- **不修改代码**——只报告问题，修改由 apply 流程或用户决定。
- **第二次审查（归档前）必须独立于第一次**。即使第一次全通过，第二次也要完整重审，因为后续变更可能破坏之前的实现。
