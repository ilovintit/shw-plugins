# 用原生 goal 执行 roadmap（差距驱动编排打法）

## 0. 前置（第一节必执行：先判定双文件是否就绪，再往下）

本 skill 是"编排打法手册"，组合三样东西：**roadmap.md**（`.roadmaps/<name>/roadmap.md`，四节结构：北极星 / 方向解法 / 终态描述原料 / 执行轨迹）、**verify.md**（`.roadmaps/<name>/verify.md`，终态句集 = 完成判据）、**原生 goal**（所用 agent 工具的 goal/任务循环能力，任务循环驱动）。

背景先明示一句：**探索期清单不可预信**——探索时对问题的认知是初步的，按探索期预拆的清单顺序执行会吃掉后续轮次该有的判断。所以 change 拆解移到执行期：每轮用当前认知把差距切成 change。roadmap.md 给的是意图（北极星 + 方向解法），不是待办清单；verify.md 的终态句集才是完成判据。

**加载本 skill 后第一件事就是确认双文件就绪**——不许跳过、不许凭记忆假设"roadmap 应该已经生成"：

```bash
# <name> 为 roadmap 名（.roadmaps/ 下的目录名），未知时列出后问用户
ls .roadmaps/ 2>/dev/null
test -f .roadmaps/<name>/roadmap.md && echo "roadmap 就绪" || echo "roadmap 缺失"
test -f .roadmaps/<name>/verify.md && echo "verify 就绪" || echo "verify 缺失"
```

| 判定结果 | 动作 |
|---|---|
| 双文件都在 | 按下方模板设定 goal objective，进入第 1 节编排循环 |
| roadmap.md 缺失（还没做探索） | 先走 `/shw-roadmap-explore` 生成 roadmap，完成后再回本节 |
| verify.md 缺失（终态句集还没定稿） | 先走 `/shw-roadmap-verify` 定稿 verify.md，完成后再回本节 |

**goal objective 写法 = 一句话模板**（照抄替换 `<name>`，不要自行改写措辞、不要省略完成判据）：

```
以 .roadmaps/<name>/verify.md 的终态描述为完成判据，执行 .roadmaps/<name>/roadmap.md 的意图：每轮调查现状与终态的差距，把差距切出下一个 change（propose→apply→archive），归档后回写 .roadmaps/<name>/roadmap.md 执行轨迹并重新判断；终态句全部达成且每句附取证（目检项除外）才算完成
```

把这段文本填入所用 agent 工具的 goal 功能的目标设定处（各工具入口不同，按你所用工具的 goal 设置方式粘贴）。

## 1. 差距驱动循环：四步纪律

主 agent（goal 会话中的编排者）按固定循环推进。**分层铁律：主 agent 持方向判断与整体验证，子 agent 一个 change 一个——只有主 agent 有跨 change 的全局视野。**

每轮的形状：判终态句集与现状的差距 → 把差距切出下一个 change → 走完 change 小循环 → 记轨迹 → 重新判差距。四步纪律如下，编号即执行顺序：

```
┌→ 1.判差距 ─→ 2.拆 change ─→ 3.小循环（propose→apply→archive）─→ 4.记轨迹 ─┐
└←──────────────────── 回到第 1 步重新判差距 ←─────────────────────────────┘
```

1. **判差距**：读 verify.md 终态句集，调查现状，找出未达成句——主 agent 亲自独立取证（跑命令 / 发请求 / 读代码），**不凭上轮记忆、不采信子 agent 汇报**直接判断
2. **拆 change**：把当前差距切出**下一个自包含 change**（能独立走完 propose → apply → archive 的粒度）——用当前认知拆，**不假设存在预拆清单**；差距大时一个 change 只切差距的一部分（先切被依赖的部分）
3. **小循环**：该 change 走完整 propose → apply → archive；实现工作可派子 agent——**一个子 agent 负责一个 change 的完整交付**（交付责任整体归一个子 agent，不按 propose/apply 拆段派发）；主 agent 保留差距判断与整体验证。归档步骤中 delta spec 的同步评估**默认选择同步**——goal 会话无用户逐次确认，同步是安全默认值：知识资产即时落盘，不堆积到 roadmap 收尾（roadmap 归档的 spec 同步核验是兜底而非主力）
4. **记轨迹**：change 归档后立即回写 roadmap.md 执行轨迹（追加了什么 change / 学到什么 / 方向解法是否修正）——然后回到第 1 步重新判差距

**完成判定（单判据）**：全部终态句判定为真且每句附取证（需目检项除外，汇总移交用户）才算完成。不以"change 做完了"或"轨迹够长了"为判据——即使某个已归档 change 的任务清单有未尽事项，只要不构成终态句差距，不阻碍完成判定；存在未达成句不得停止循环。goal 完成、目检项汇总移交用户后，提示用户运行 `/shw-roadmap-archive <name>` 逐条确认目检结果并归档收尾——skill 不自动归档，目检最终结论与生命周期终结是用户确认域。

示例：第 1 轮判差距发现"订单写入口"与"订单查询"两个差距 → 拆一个针对订单写入口的 change（被依赖的在前）→ 交付归档、记轨迹 → 重新判差距决定下一个——而非按任何预拆清单顺序执行。

### 方向修正门：双层纪律

执行中发现路线或意图有问题，先分清是哪一层再动作：

- **路径层**（方向解法的路线调整：换实现路线 / 调先后顺序 / 放弃某条路线）：agent 可自主决定，但必须把修正内容与理由记入执行轨迹（如"修正：放弃独立查询服务路线，理由 X，改为扩展现有入口"），继续循环
- **意图层**（北极星本身要动 / 终态句集合的语义要改）：必须停下向用户陈述发现与理由，由用户裁决——agent 不得单方面改写北极星或终态句语义

## 2. 验证纪律

判差距与完成判定的取证是整个打法可信度的来源（这是替代预拆清单的防放水手段），四条硬纪律：

1. **独立取证，不采信转述**：verifier（每轮差距判断者，即主 agent）判断每句自己取证——自动类自己执行命令比对结果，请求类自己发请求看响应，代码类读到检查点；子 agent 汇报只能当线索，不能当结论——子 agent 说"CRUD 全部完成，测试全绿"不算数，自己验过才算
2. **宣布必须出示证据**：宣布任何终态句达成必须附取证（命令输出 / 请求响应 / 代码位置），**禁止裸判**；无证据的宣布无效，不构成完成判定依据
3. **目检不越界**：需目检项（视觉 / 体验类）到代码级检查点确认后列入移交清单，**不得自行宣布通过**——这类结论只有用户能下；goal 完成时把移交清单汇总交给用户逐条确认
4. **轨迹可追溯**：每轮差距判断（哪些句未达成、为什么）与证据记入执行轨迹，保持可回溯

verify.md 是文档判据，不是脚本——终态句判定是 agent 取证判断，不要试图把它转成自动化验证程序。

## 3. 边界与退化

**分层边界**：roadmap/goal 编排是**外层**，change 流程（propose/apply/archive）是**内层小循环**且对 roadmap 零感知——change 命令文件不含 roadmap 读写逻辑，在无 roadmap 的项目里跑 change 流程与本体系存在前完全一致。外层与内层唯一的耦合点是主 agent 的第 4 步记轨迹（读 roadmap、写 roadmap 都发生在编排层，change 小循环内部不碰这两个文件）。

**无原生 goal 循环时的退化**：所用 agent 工具若无原生 goal 循环，退化为**手动多轮对话 + 每轮结束时按 verify.md 自验**——用户每轮说"继续"，agent 每轮按四步纪律走一遍并汇报差距判断结果与证据。纪律不变，只是驱动从自动变手动；objective 模板同样有效，作为整个会话的任务书贴在对话里即可。
