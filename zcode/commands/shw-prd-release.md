外包/合同项目的交付边界冻结：对指定模块 PRD 做一次 fresh audit——逐条重验验收标准、只认当下事实——全绿或经用户裁决后，在 PRD 的交付边界章节写入冻结标记，配合 git tag 作为验收基线。冻结的是**交付边界章节**（签合同时写死的交付范围清单），不是整个 PRD——PRD 其余部分仍是活文档，照常增改。

**只对外包/合同项目有意义**：内部产品的 PRD 是活文档，没有"交付即冻结"的概念——对内部产品 PRD 执行本命令时明确提示不适用并停止。

本命令由用户手动执行，执行即冻结意图——全绿时展示证据摘要后直接写入标记，不需二次确认（有差距时除外，见裁决分支）。

---

**输入**：`/shw-prd-release` 后的参数是模块名（如 `订单`），对应 PRD 文件 `docs/prd/<模块名>.md`；未提供参数时向用户确认冻结范围（单模块或全部交付模块）。

**步骤**

1. **前置校验一：适用性判定**

   确认这是外包/合同交付场景（用户执行本命令本身即是声明；拿不准时向用户确认一句）。**内部产品 PRD → 明确提示不适用并停止**："内部产品 PRD 是活文档，无交付边界冻结概念；需求变更走 /shw-prd-draft 追加模式即可。"

2. **前置校验二：定位 PRD 与冻结范围**

   - **参数有模块名**：定位 `docs/prd/<模块名>.md`，不存在 → 提示该模块 PRD 不存在，停止
   - **参数未提供**：列出 `docs/prd/` 下全部模块，向用户确认冻结范围——单模块还是全部交付模块（多模块时逐个走下述流程），不猜
   - 已含冻结标记的模块跳过：

     ```bash
     grep -m1 '^> 交付边界冻结：' docs/prd/<PRD文件>
     ```

     有输出 → 该模块已冻结过、无需重复，跳过

3. **fresh audit：逐条重验验收标准**

   复用 /shw-prd-audit 的取证逻辑（取证来源与纪律全套照搬）：通读 PRD 需求清单，逐条读验收标准，每条对照代码/测试现实独立取证判定——读代码、查 `git log`、经 gitea-mcp 查 `TC:` 对齐测试的 PR CI run 记录与 Issue/PR（全程只读；agent 本地不跑测试、不起服务）。

   判定纪律重申：

   - **不采信任何历史盘点报告**——上次盘点后状态可能已变（新提交合入 / 某处被改坏），判据必须是当下事实，历史结论只能当线索
   - 宣布达成必须附证据（命令输出 / 响应 / 代码位置 / 用例红绿），禁止裸判
   - 目检类标准只走到代码级检查点，标注"待用户目检"，不自行宣布通过

4. **裁决**

   - **全绿**（可判定的验收标准全部达成，目检类均已到代码级检查点）→ 向用户展示每条证据摘要（待目检项单独列出供用户过目），然后直接进入第 5 步写入冻结标记——写入动作以用户执行本命令为确认意图
   - **有差距**（存在未达成 / 部分达成）→ 逐条摆出差距事实（每条标注达成 / 部分达成 / 未动 + 证据），然后**显式询问用户是否仍要冻结**——带差距冻结是业务/合同决策，只摆事实不替用户决定：
     - 用户答"冻结" → 进入第 5 步（承诺与交付的差异如实记入 docs PR 描述，交付边界范围不改写）
     - 用户答"不冻结" → 退出，不写标记，提示去补差距（差距的善后属于后续需求与修复工作，本命令不管）

5. **写入冻结标记**

   定位 PRD 的**交付边界**章节：有则用之；无则在文末创建（内容 = 本合同覆盖的需求清单与验收标准范围，逐条列明）。在该章节标题正下方紧邻一行写入（YYYY-MM-DD 为当天日期）：

   ```markdown
   > 交付边界冻结：YYYY-MM-DD（合同基线）
   ```

   **冻结语义收窄**：只有这一章节就此固定——标记写入后交付边界章节不可再改（后续增改走 /shw-prd-draft 追加模式，冻结章节跳过）；PRD 其余章节仍是活文档，照常修订。

6. **提交并打验收基线 tag**

   冻结变更按 `shw-gitea-flow` skill 的关联纪律提 docs PR：从 dev 建分支、commit、经 gitea-mcp 建 PR（目标 dev），描述写明冻结背景与裁决结论（有关联 Issue 写 `Refs #N`；走了差距裁决的附差距清单）。PR 合入 dev 后，在合并 commit 上打 git tag 作为验收基线（命名经用户确认，如 `delivery-baseline-YYYYMMDD`）并推送。

   然后向用户输出冻结完成摘要：冻结文件与章节、冻结日期、基线 tag 名、逐条判定结果；若走了差距裁决，摘要中附差距清单。

**约束**

- **内部产品 PRD 必劝阻**：适用性判定不过即停止并说明原因，不做半截
- fresh audit 不采信任何历史盘点报告——判据必须是当下事实，历史结论只能当线索
- 有差距必须显式询问用户是否仍要冻结，不替用户决定；全绿也不跳过任何前置校验，按步骤走完
- 冻结标记的格式与位置固定：`> 交付边界冻结：YYYY-MM-DD（合同基线）`，交付边界章节标题正下方紧邻一行——不写别处、不改格式
- 冻结只圈定交付边界章节：标记写入后该章节不改写、无移除流程（改交付范围是合同变更，走用户与甲方的流程）；PRD 其余章节不受影响
- 多模块冻结范围必须向用户确认，不猜
- audit 阶段全程只读；写动作仅限冻结标记与交付边界章节（写入 PRD 本身）、其 docs PR、验收基线 tag
