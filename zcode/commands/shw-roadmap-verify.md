把 roadmap 的终态描述原料逐句转写为终态描述句集 - 产出 verify.md 判据文档与一句话 goal 文本。

原生 goal 的验证是模型自判，目标含糊时容易放水；把终态写成可观察的句子后，verifier 每轮有明确对照物——读代码、发请求取证，对照句子判真伪，judgment 对象从"感觉"变成"可判真伪的句子"。每句满足**可观察性判据**：能从系统外部判真伪的表述（行为 / 输出 / 结构），有明确的真伪边界。

分层：verify.md 是 **roadmap 级**判据（goal 每轮校验的对象）；change 级验证是各 change 流程内的任务验证命令与 apply 后代码审查，两层互不接管。verify.md 本身是**判据不是记分板**——定稿后语义稳定，不随执行轮次变动；每轮的验证状态记在 roadmap.md 执行轨迹，不在 verify.md 维护勾选表、不标 change 归属（这是清单驱动的旧口径，已废弃）。终态句不预绑 change——change 是执行期手段，verify 只锚定终态。

---

**输入**：`/shw-roadmap-verify` 后的参数是 roadmap 名（对应 `.roadmaps/<name>/`）。

**步骤**

1. **读 roadmap**

   读 `.roadmaps/<name>/roadmap.md`，取出北极星与终态描述原料（「终态描述原料」节）。文件不存在时停下提示：
   > "未找到 .roadmaps/<name>/roadmap.md，先运行 /shw-roadmap-explore 生成 roadmap。"

2. **逐句转写为终态描述句**

   每句必须**可观察**——能从系统外部判真伪（行为 / 输出 / 结构），有明确的真伪边界。反例对照：

   - "用户模块支持增删改查"**不是**终态句——"支持"没有真伪边界，做到什么程度算"支持"无从判断
   - "编辑已存在的用户后再次读取，返回修改后的值且其余字段不变"**是**终态句——操作 + 预期结果，verifier 实际执行操作即可对照判真伪

   每句可附**取证手段参考**（句子级参考，帮助 verifier 取证；不是探索期必须预写的验证条目，不强求每句归入某一类）：

   | 取证手段 | 适用 | 形态 |
   | --- | --- | --- |
   | 命令取证 | 能命令化的断言（编译 / 测试 / 结构检查） | 可执行命令 + 期望结果 |
   | 请求取证 | API 行为 | 操作序列 + 预期响应（verifier 可实际发请求对照） |
   | 代码取证 | UI / 难以外部观察的行为 | 代码级检查点；视觉部分标注"最终需用户目检" |

   转写纪律：

   - **空洞原料不编造**：原料是「把 X 做好」这类无法导出可观察判据的表述时，停下向用户追问具体成功标准，用户说清前不写句
   - **不为凑取证手段而降级**：能外部观察验证的（接口可达）不硬降级成代码取证
   - **业务行为不硬写成脚本**：CRUD 的「编辑回显」这类交互行为禁止写成 shell 断言脚本——用请求序列表达，交互行为脚本化只会得到假信心

   **"最终需用户目检"的语义**：agent 负责到代码级确认，最终视觉/体验验收留给用户——agent 不得自行宣布 UI 类验证通过。它是句子上的目检标注与移交说明，不是任何状态值。

3. **写 verify.md**

   写 `.roadmaps/<name>/verify.md`：终态句集结构——标题 + 逐句（句子 + 取证手段 + 目检标注）。不维护勾选表、不标 change 归属、不预写验证状态——每轮验证状态由 goal 执行期记在 roadmap.md 执行轨迹。

   文件结构模板（简短示例：编辑回显句 + 请求取证 curl 序列）：

   ````markdown
   # <name> 终态描述句集

   ## 编辑回显

   - **终态句**：编辑已存在的用户后再次读取，返回修改后的值且其余字段不变
   - **取证手段**：请求取证——GET 单条 → PUT 改字段 → 再 GET 对照：

     ```bash
     curl -s http://localhost:<port>/api/users/1
     curl -s -X PUT http://localhost:<port>/api/users/1 -H 'Content-Type: application/json' -d '{"name":"新值"}'
     curl -s http://localhost:<port>/api/users/1
     ```

   ## 列表分页

   - **终态句**：列表接口按页返回不重复、不丢失的数据
   - **取证手段**：请求取证——请求第 1、2 页，对照两次响应无重复、合并无丢失

   ## 分页控件视觉

   - **终态句**：分页控件在各页码间切换时表现正常
   - **取证手段**：代码取证——翻页 offset / key 计算正确，page/pageSize 参数透传到后端查询
   - **最终需用户目检**：分页控件的视觉表现与交互流畅度
   ````

4. **逐句展示给用户审查**

   把终态句集展示给用户，逐句核对三问：

   - **句子可观察吗**——有真伪判据，还是仍是「支持 X / 做好 X」式含糊表述
   - **取证手段现实吗**——命令存在、接口可达、检查点可查
   - **有没有漏**——roadmap 的终态描述原料全覆盖

   用户有异议 → 修对应句子（含补漏）→ 重新展示。**定稿前不输出 goal 文本**——goal 文本只在全部句子被用户确认后出现。

5. **定稿后输出一句话 goal 文本**

   按下方模板生成 goal 文本（`<name>` 替换为实际 roadmap 名）输出给用户：

   ````text
   以 .roadmaps/<name>/verify.md 的终态描述为完成判据，执行 .roadmaps/<name>/roadmap.md 的意图：每轮调查现状与终态的差距，把差距切出下一个 change（propose→apply→archive），归档后回写 .roadmaps/<name>/roadmap.md 执行轨迹并重新判断；终态句全部达成且每句附取证（目检项除外）才算完成
   ````

   附粘贴指引：到所用 agent 工具的 goal/目标设置处粘贴这段文本（各工具入口不同，在工具的目标或任务设定处粘贴即可）。之后每轮由 goal 驱动：对照 verify.md 逐句取证判真伪，验证结果回写 roadmap.md 执行轨迹。
