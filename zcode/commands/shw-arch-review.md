细化审查功能技术方案的完备性：审查对象是**即将提交 docs PR 的方案变更**（工作区改动）或**指定方案全量**，多视角无锚定审查逼出方案该记而未记的内容，问题清单经用户裁决后写回方案并提 docs PR，最后给出就绪度软结论。审的是**方案 vs 需求空间**——表结构、API 契约、异常分支、非功能性有没有漏。

与 `shw-design-review` skill 的边界：skill 是起草时的对照检查（agent 自主，随 /shw-arch-draft 加载）；本命令是成型后的多视角无锚定找洞（独立审查代理，用户裁决驱动）。**审查即修正**：审出的问题经用户裁决后直接写回（无独立修正命令）；用户的主动增改走 /shw-arch-draft 追加模式。可**多轮重跑**（含新会话）：跨轮收敛靠方案单一真相源 + 关联 Issue 时间线上的否决记录，不靠外部报告。

---

**输入**：`/shw-arch-review` 后的参数是 Issue 编号或功能名（对应 `docs/architecture/<功能名>.md`）；参数未提供时先识别审查范围（见步骤 1）。

**步骤**

1. **定位审查对象与范围**

   - **参数未提供**：先看工作区有无未提交的方案变更（`git status docs/architecture/` 与 `git diff docs/architecture/`）：

     - 有 → 本次审查对象即这批待提交变更，列出涉及方案向用户确认
     - 无 → 列出 `docs/architecture/` 下的方案文件（目录不存在或为空 → 提示尚无任何技术方案、起草走 /shw-arch-draft），问用户审哪个，不猜

   - **参数有值**：定位对应方案（文件不存在 → 提示不存在、起草走 /shw-arch-draft，停止）。恰有未提交变更时默认只审变更面 + 波及一致性，向用户说明；用户要全量则全量。

2. **识别变更面（变更审查时）**

   ```bash
   git diff docs/architecture/<文件>
   ```

   变更审查聚焦两件事：新增/改动内容自身的完备性，以及变更与既有章节、关联 PRD/原型的咬合（改了表结构却没同步 API 出参、改了流程却没更新兼容迁移，是高频洞）。全量审查跳过本步。

3. **多视角无锚定审查**

   **并行委派多个独立审查视角**：每个视角由一个**不携带本对话上下文的独立审查代理**承担（所用工具的委派机制自行映射）；不支持委派时退化为串行自查各维度，并**向用户声明该局限**。每个视角只拿方案全文、关联 PRD/原型与本维度审查指令，不拿本对话历史。

   视角维度（至少六个）：

   | 视角 | 审什么 |
   | --- | --- |
   | 表结构完备 | 每张表字段类型/约束/索引齐全；有需求没落表、有表没需求来源；表间关系覆盖业务规则；状态机有字段承载 |
   | API 契约一致 | 请求/响应字段与原型界面字段咬合；错误码、分页、幂等、并发有约定；同一资源在 CRUD 间口径一致 |
   | 流程异常分支 | 每个核心流程问超时/失败/降级三分支；事务边界、重试与补偿、数据一致性有交代 |
   | 非功能性 | 性能量级、安全（鉴权/越权/敏感数据）、兼容迁移（存量数据/灰度/回滚）覆盖 |
   | 三方一致性 | PRD ↔ 原型 ↔ 方案同一套状态机与字段口径；测试策略覆盖 PRD 验收标准（`TC:` 对齐） |
   | 离场可执行性 | 总判据：把方案交给无上下文 agent，实现到 E2E 全绿全程无需问人；任何必须问人的点即洞 |

   审查实证姿势（与 /shw-prd-review 同款）：数值参数问默认值与可配置性、每个实体问状态机、横切关注点矩阵化、每个流程问超时/失败/降级三分支、"明确不处理"经用户裁决写进非目标节。

   视角纪律：各视角开审前先读方案全文与关联 PRD/原型（真相源）。会话内多轮重跑靠对话中的裁决记忆；新会话重跑时先经 gitea-mcp 读关联 Issue 时间线，**读到否决裁决的问题不再重提**。每条发现含：问题描述 / 判定依据 / 建议落点（补进哪个章节）。

4. **问题清单展示与用户裁决**

   汇总各视角产出，去重合并后按三级分级，**只在对话展示，不落盘任何独立报告文件**：

   - **P0**：开发执行必然阻塞——agent 必须瞎猜才能继续的点
   - **P1**：高概率分叉——存在两种以上合理理解、会导出不同实现的点
   - **P2**：建议——不影响可执行性的改进建议

   请用户逐条裁决：**采纳**（进写回）或**不采纳**（进否决留痕）；可分批裁决，裁决完成后进下一步。

5. **写回并提 docs PR（审查即修正，直接写回）**

   - **采纳的问题**：起草变更摘要——改哪些章节、为什么、影响哪些需求/用例规划，向用户展示；**审核门是硬门**，用户确认前方案文件保持原样；确认后修改方案。测试策略章节新增的用例规划同样保持 `TC:` 命名对齐
   - **不采纳的问题**：随 docs PR 描述的"否决清单"段留痕（经 `Refs #N` 反向出现在 Issue 时间线），格式与 `/shw-prd-review` 相同

   变更就绪后按 `shw-gitea-flow` skill 的关联纪律提交：从 dev 建分支、commit、经 gitea-mcp 建 docs PR（目标 dev），描述写 `Refs #N`（含否决清单段）；该 Issue 已有未合并的 docs PR 时 commit 追加到同一分支，不另开 PR。完成后向用户输出：改了哪些章节、PR 链接。

6. **就绪度结论**

   写回完成后给出就绪度结论，三档：

   - **可进 Sprint**：P0 清零、P1 已消解或已有明确裁决、占位注释清零
   - **建议先补 X**：X 为未消解的关键问题（指向具体章节）
   - **未就绪**：P0 大面积存在或章节大面积空缺，先补方案再排期

   给出"可进 Sprint"前**必须**确认 draft 留下的占位注释已全部清除：

   ```bash
   grep -n '<!-- 待 /shw-arch-review 补齐' docs/architecture/<文件>
   ```

   有输出 = 占位未清零，不得给"可进 Sprint"。就绪度结论是**纯软建议**：不做成 /shw-propose 或任何下游的硬门，排不排期由用户决定。

**约束**

- **问题清单只在对话展示**：不落盘任何独立报告文件；唯一的写动作是写回方案本身与其 docs PR
- **用户未确认不改文档**：审核门是硬门，变更摘要未获用户确认前方案文件保持原样
- **变更必走 docs PR**：确认后的修改经分支 commit + docs PR 合入（描述写 `Refs #N`，目标 dev），不直接 commit 到 dev/main
- **否决留痕不重提**：不采纳的裁决随 PR 描述留痕（反出 Issue 时间线），后续轮次（含新会话重跑）读到即不再重提
- **除写回方案与其 docs PR 外零写副作用**：不写任何其他本地文件；gitea-mcp 操作限建 PR 与读 Issue 时间线
