change 族的第一步，**不可跳过**：任何 change 在固化（/shw-propose）之前必须先经过本命令。探索对象是**代码现状与需求之间的差距**——需求已由 Issue 承载明确（大活的设计已由 docs 三件套承载），本命令不重复它们；本命令回答的是：**要做的任务与现在的代码之间差多少、缺口在哪、执行路径是什么**。

**产出**：差距清单 + 具体执行方案（动哪些模块/文件、什么顺序、有什么风险）。产出**只在会话上下文，不落盘任何文件**——探索结论必须紧接着同会话运行 `/shw-propose` 固化成三件套；新会话没有探索结论，就重新探索（差距调查很快），不凭任何残留记忆猜。

**explorer 不写生产代码。** 思考、读代码、画图、对比选项都可以。

---

## 工作区（绑定 Issue 即强制 worktree）

- 输入是 **Issue 编号**（或 change 名）→ 探索一律在 issue worktree 内进行：优先使用宿主原生 Worktree，否则 fallback 建 `git worktree add ../<repo>-issue-N -b feat/N-slug origin/dev`；已在则进入使用；进 worktree 后**立即创建/切换到 `feat/<N>-<slug>` 分支**再开始探索（detached HEAD / base 分支上不开发，见 shw-worktree「进 worktree 后第一步 = 固化 issue 分支」）。同会话后续 `/shw-propose`（`.changes/` 三件套）与实现复用同一 worktree。roadmap / goal-drive 驱动的探索进里程碑常驻/permanent worktree（见 `shw-worktree`），不另开
- 输入是**要探索的主题**（未挂 Issue）→ 属纯读调研（与 `/shw-research` 同性），任意目录可做；探索中决定挂 Issue 动手时，先过 `shw-issue-gate` 建单、再建 worktree
- 探索本身纯读，worktree 内读代码与主目录无差；需跑构建/测试级探针时按 `shw-worktree` 使用纪律先装依赖

## 探索方法

### 1. 读需求侧

- 输入是 Issue 编号：读 Issue 正文 + 验收 checklist + 评论时间线（**已有裁决不重提**），有否决记录的问题不再碰
- 大活（含 milestone 拆出的子 Issue）：通读 `docs/architecture/<功能>.md` 对应章节——方案已定的表结构/API 契约是差距核对的基准，不重新发明
- 小活：Issue 初步整理（三五句话）就是全部需求侧，缺口靠代码侧调查补

### 2. 读代码侧（差距调查的主体）

- 读相关模块的现状：已有实现、已有表、已有接口、现有约定（AGENTS.md）
- 对照出**差距清单**：需求要什么 × 现在有什么 → 缺什么、要改什么、哪里是硬骨头
- 大活子 Issue 的差距核对典型如：方案里的表哪张已存在（要不要迁移）、模块边界落在哪、与现有代码的接缝在哪

### 3. 形成执行方案

把差距翻译成**具体的执行路径**：

- 改动落点（哪些模块/文件，新增还是修改）
- 顺序与依赖（先打通什么、什么可以并行）
- 风险点（方案假设与现实不符的地方、可能返工的点）——**方案与代码现实冲突时停下问用户，不自行调和**

**结束判据**：能清楚回答"差距是什么、执行路径是什么"才结束；说不清就继续调查。Issue 本身写不清晰（不是代码侧问题）→ 提示回 `/shw-issue` 补澄清，不在本命令里替用户想需求。

### 探索姿态

- **好奇，不强加** - 自然涌现的问题就问，不照本宣科
- **抛出线索，不是审讯** - 提出方向让用户跟有共鸣的走
- **可视化** - 有助于澄清时大量用 ASCII 图（系统图、状态机、依赖图）
- **接地气** - 一切结论建立在读过的代码上，不空谈
- **耐心** - 不急于结论，让方案形状自然浮现

需要对比选项时（如"这个缓存用 Valkey 还是靠 PG 直接扛"）：头脑风暴、做对比表、（若被问）给推荐路径。

## 与下一步的衔接

探索结束、执行方案成型时：

- 提议固化："探索完毕，差距与执行路径已清楚。运行 `/shw-propose` 固化成三件套吗？"（同会话立即执行，探索结论在上下文里）
- 用户想继续探索也可以——没有强制形式化的压力，但**固化前不许进入实现**

## 约束

- **不可跳过**——propose 固化的方案必须产自本命令的调查，跳过 explore 直接 propose 是流程违规
- **不落盘**——探索结论只活在会话上下文；`.changes/` 三件套是唯一持久交接物，由 propose 写
- **不写生产代码、不写 docs 文件**——产出是探索结论本身
- **不重复需求探索与设计探索**——需求归 /shw-issue，设计归 docs 三件套；本命令探索的是执行方案
- 方案（docs/architecture/）与代码现实冲突时停下问用户，不静默调和
