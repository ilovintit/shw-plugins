细化审查模块 PRD 的完备性：审查对象是**即将提交 docs PR 的 PRD 变更**（工作区改动）或**指定模块全量**，多视角无锚定审查逼出 PRD 该记而未记的内容，问题清单经用户裁决后更新文档并提 docs PR，最后给出就绪度软结论。审的是**文档 vs 需求空间**——业务逻辑、操作习惯、领域事实、数据库结构有没有漏。

与 /shw-prd-audit 的边界：audit 审**文档 vs 实现**（完成度对账），发生在实现后的任何时候；本命令审**文档 vs 需求空间**，发生在文档成型后、docs PR 合入前（也可对已合入模块做全量复审）。**审查即修正**：审出的问题经用户裁决后直接写回（无独立修正命令）；用户的主动增改走 /shw-prd-draft 追加模式。可**多轮重跑**（含新会话）：跨轮收敛靠 PRD 单一真相源 + 关联 Issue 时间线上的否决记录，不靠外部报告。

---

**输入**：`/shw-prd-review` 后的参数是模块名（如 `订单`），对应 `docs/prd/<模块名>.md`；参数未提供时先识别审查范围（见步骤 1）。

**步骤**

1. **定位审查对象与范围**

   - **参数未提供**：先看工作区有无未提交的 PRD 变更（`git status docs/prd/` 与 `git diff docs/prd/`）：

     - 有 → 本次审查对象即这批待提交变更，列出涉及模块向用户确认
     - 无 → 列出 `docs/prd/` 下的模块文件（目录不存在则提示尚无任何 PRD、起草走 /shw-prd-draft），问用户审哪个模块的全量，不猜

   - **参数有模块名**：定位 `docs/prd/<模块名>.md`（文件不存在 → 提示该模块 PRD 不存在、起草走 /shw-prd-draft，停止）。该模块恰有未提交变更时默认只审变更面 + 波及一致性，向用户说明；用户要全量则全量。

2. **识别变更面（变更审查时）**

   ```bash
   git diff docs/prd/<文件>
   ```

   变更审查聚焦两件事：新增/改动内容自身的完备性，以及变更与既有章节的咬合（改了需求却没同步动状态枚举、配置项、表结构、非目标是高频洞）。全量审查跳过本步。

3. **多视角无锚定审查**

   **并行委派多个独立审查视角**：每个视角由一个**不携带本对话上下文的独立审查代理**承担（所用工具的委派机制自行映射，子代理天然不继承对话历史即满足无锚定要求）；所用工具不支持委派时，退化为串行自查各维度，并**向用户声明该局限**。每个视角只拿 PRD 全文与本维度审查指令，不拿本对话历史。

   视角维度（至少五个）：

   | 视角 | 审什么 |
   | --- | --- |
   | 业务逻辑完备 | 主流程 / 异常流 / 边界条件 / 业务规则（计算、校验、状态联动） |
   | 用户操作流 | 角色 / 入口 / 步骤 / 状态反馈 / 误操作与恢复路径 |
   | 数据库结构 | 每张表字段类型约束索引是否齐全；有需求没落表、有表没需求来源；表间关系是否覆盖业务规则 |
   | 三方一致性 | 需求 ↔ 数据库设计 ↔ WebUI 流程互相咬合（同一状态机在表字段与界面流转上是同一套） |
   | 离场可执行性 | 总判据：把任一需求交给无上下文 agent，从技术方案（docs/architecture/）到实现全程无需问人；任何必须问人的点即洞 |

   各视角的**审查实证姿势**（找洞方法）：

   - **数值参数**逐个问默认值与可配置性——可配置项进横切资产·全局配置项清单
   - **每个实体**问状态机——状态定义进横切资产·状态枚举
   - **横切关注点**（通知 / 权限 / 配置）强制矩阵化——进横切资产对应矩阵
   - **每个流程**问超时 / 失败 / 降级三分支——缺哪个分支即洞
   - **"明确不处理"也是裁决**：审出的异常路径经用户裁决不处理的，必须写进非目标节

   视角纪律：各视角开审前先读 PRD 全文（真相源）。会话内多轮重跑靠对话中的裁决记忆；新会话重跑时先经 gitea-mcp 读关联 Issue 时间线（docs PR 描述中的否决记录经 `Refs #N` 反出到时间线），**读到否决裁决的问题不再重提**。每条发现含：问题描述 / 判定依据 / 建议落点（应补进哪个要素节）。

4. **问题清单展示与用户裁决**

   汇总各视角产出，去重合并后按三级分级，**只在对话展示，不落盘任何独立报告文件**：

   - **P0**：开发执行必然阻塞——agent 必须瞎猜才能继续的点
   - **P1**：高概率分叉——存在两种以上合理理解、会导出不同实现的点
   - **P2**：建议——不影响可执行性的改进建议

   请用户逐条裁决：**采纳**（进写回）或**不采纳**（进否决留痕）；可分批裁决，裁决完成后进下一步。

5. **写回并提 docs PR（审查即修正，直接写回）**

   - **采纳的问题**：起草变更摘要——改哪些要素节 / 为什么 / 影响哪些需求与验收标准，向用户展示；**审核门是硬门**，用户确认前 PRD 文件保持原样；确认后修改 PRD 对应节。新写入的验收标准同样执行可取证纪律 + `TC:` 用例名对齐。
   - **不采纳的问题**：随 docs PR 描述的"否决清单"段留痕（经 `Refs #N` 反向出现在 Issue 时间线），格式：

     ````markdown
     ### 否决：<一句话问题>

     - 提出：<问题描述与来源视角>
     - 不采纳理由：<为什么不做>
     - 经用户确认
     ````

   变更就绪后按 `shw-gitea-flow` skill 的关联纪律提交：从 dev 建分支、commit、经 gitea-mcp 建 docs PR（目标 dev），描述写 `Refs #N`（含否决清单段）；该 Issue 已有未合并的 docs PR 时 commit 追加到同一分支，不另开 PR。PRD 内不追加变更记录章节（留痕由 git 历史 + PR 描述承担）。完成后向用户输出：改了哪些节、PR 链接。

6. **就绪度结论**

   写回完成后给出就绪度结论，三档：

   - **可进 Sprint**：P0 清零、P1 已消解或已有明确裁决、空节占位清零
   - **建议先补 X**：X 为未消解的关键问题（指向具体要素节）
   - **未就绪**：P0 大面积存在或要素节大面积空缺，先补 PRD 再排期

   给出"可进 Sprint"前**必须**确认 draft 留下的空节占位注释已全部清除（占位未清零即要素未补齐）：

   ```bash
   grep -n '<!-- 待 /shw-prd-review 补齐' docs/prd/<文件>
   ```

   有输出 = 占位未清零，不得给"可进 Sprint"。

   就绪度结论是**纯软建议**：不做成 /shw-milestone（Sprint 计划）或任何下游的硬门，排不排期由用户决定。

**约束**

- **问题清单只在对话展示**：不落盘任何独立报告文件；唯一的写动作是写回 PRD 本身与其 docs PR
- **用户未确认不改文档**：审核门是硬门，变更摘要未获用户确认前 PRD 文件保持原样
- **变更必走 docs PR**：确认后的修改经分支 commit + docs PR 合入（描述写 `Refs #N`，目标 dev），不直接 commit 到 dev/main；PRD 内不手写变更记录章节
- **否决留痕不重提**：不采纳的裁决随 PR 描述留痕（反出 Issue 时间线），后续轮次（含新会话重跑）读到即不再重提
- **就绪度纯软建议**：结论只是建议，任何下游（含 /shw-propose）不强制检查
- **除写回 PRD 与其 docs PR 外零写副作用**：不写任何其他本地文件；gitea-mcp 操作限建 PR 与读 Issue 时间线
