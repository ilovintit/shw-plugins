# shw-prd-draft

这是共享源码中同名 slash command 的 Codex skill-backed prompt，不是 Codex 原生 commands。用户明确点名 `shw-prd-draft`、`/shw-prd-draft` 或要求执行该工作流时按下方原文执行。

**参数**：[模块名]

起草新模块 PRD 或向已有模块追加新需求章节：通过开放性访谈收集需求，按八要素模板起草全文（全新模块）或增改对应章节（已有模块），对每条验收标准做可取证自查，逐节展示并经用户确认后落盘到 `docs/prd/<模块>.md`，最后提 docs PR。

PRD 是**模块粒度的活文档**——一个功能模块一个文件（如 `docs/prd/订单.md`、`docs/prd/会员.md`），持续增改，不按里程碑拆文件（拆分把同一模块需求撕碎到 N 份文档，真相源没了）。PRD 不只是产品需求，还包含数据库设计与 WebUI 要求：用户裁决层的技术规格属于 PRD，agent 执行期照规格实现。历史管理由 git 天然承担：PRD 内不手写变更记录章节，每次变更的留痕靠 docs PR 描述（`Refs #N`）。

---

**输入**：`/shw-prd-draft` 后的参数是模块名（如 `订单`）。

**步骤**

1. **前置校验**

   - **模块参数未提供**：用向用户提问（开放性问题，不要预设选项）问用户：
     > "你想为哪个功能模块起草或补充 PRD？这个模块要解决什么问题？"

     **重要**：拿到模块名之前不要继续；问出模块名后，同样执行下述存在性检查。

   - **模块参数已提供**：检查该模块 PRD 是否已存在——`ls docs/prd/<模块名>.md`：

     - **不存在** → 全新起草模式，走下述完整流程
     - **已存在** → **追加模式**，不是停止：先通读现有 PRD 全文，再只访谈新需求（见步骤 2），增改对应章节后落盘，不重排未受影响的节。访谈中识别出**重大新增**（跨多天 / 动表结构 / 定新契约的大活）时，建议先经 `/shw-issue` 建 Issue（需求入口），本次变更的 docs PR 描述写 `Refs #N` 关联；用户选择不建 Issue 的小增补照常进行，PR 描述写清背景即可，不拦

   - **领单流转**：本次起草关联 Issue 且该 Issue 仍带 `backlog` label → 经 gitea-mcp 打 `status/方案中` 摘 `backlog`（文档三件套领单）；已在 `status/方案中` 则不动

2. **访谈需求**

   以开放性问题访谈（不预设选项），问清需求空间。追加模式先通读现有 PRD 再聚焦新需求——已裁决的内容以文档为准，不重复提问、不推翻既有裁决（用户主动要改的除外，同样走本命令追加模式收集变更）：

   > - "这个模块要交付什么？"（全新模块）/ "这次要新增什么需求？"（追加模式）（逐条收集）
   > - "各需求的验收标准是什么？"（怎么算做完）
   > - "这个模块明确不做什么？"（非目标，含"明确不处理"的裁决）
   > - "有哪些用户角色、权限怎么划、核心业务流程怎么走？"
   > - "表结构、WebUI 界面有什么想法？"（有则记录，无则跳过）

   用户说多少就是多少——不替用户补需求、不硬拆需求边界。**访谈不逼齐**：八要素中用户未覆盖的节（典型如数据库设计、WebUI 要求——起草时往往还没想清）落空占位待 review 补齐，把没想到的逼出来是 `/shw-prd-review` 的职责，不是本命令的。访谈信息不足以起草时继续追问，理解到位前不进入起草。

3. **起草全文 / 增改章节**

   文件名即 `docs/prd/<模块名>.md`（模块名与参数一致，不做 slug 改写）。

   **全新起草**按下方模板出全文：

   ````markdown
   # PRD: <模块名>

   ## 目标

   <一句话：这个模块达成时产品是什么样>

   ## 用户角色与权限

   - **角色清单**：<角色名与一句话职责>
   - **权限边界**：<各角色能做什么、不能做什么>
   - **数据可见范围**：<各角色能看到哪些数据>

   ## 核心业务流程

   <主流程与关键分支：自然语言步骤或流程图，覆盖正常路径与关键分支、异常路径>

   ## 功能需求清单

   ### 需求 1：<名称>

   - **描述**：<做什么>
   - **操作流**：<角色与入口、步骤、每步的状态反馈>
   - **业务规则**：<计算、校验、状态联动、异常流>
   - **验收标准**：
     - [ ] TC: <E2E 用例名>——<可取证表述>
     - [ ] TC: <…>——<…>
   - **优先级**：<P0/P1/P2>

   ## 数据库设计

   ### 表：<表名>

   | 字段 | 类型 | 约束 | 默认值 | 说明 |
   | ---- | ---- | ---- | ------ | ---- |
   | <…> | <…> | <…> | <…> | <…> |

   <索引与表间关系：索引列组合、关联表与关联方式>

   ## WebUI 要求

   - **页面与入口**：<页面清单、各页面从哪进入>
   - **操作流**：<各页面的操作步骤>
   - **状态反馈**：<操作成功 / 处理中 / 失败的反馈形态>
   - **异常提示**：<错误场景与提示文案>

   ## 横切资产

   ### 状态枚举

   <每实体状态机：状态名 / 值 / 含义。编码约定：流转类按 10/20/30 步进（如待支付 10 → 已支付 20 → 已取消 30），分类类按 11/12/13 步进>

   ### 通知矩阵

   | 场景 | 通知对象 | 渠道 |
   | ---- | -------- | ---- |
   | <…> | <…> | <…> |

   ### 全局配置项清单

   | 参数 | 默认值 | 可配置范围 | 谁配置 |
   | ---- | -------- | ---------- | ------ |
   | <…> | <…> | <…> | <…> |

   ## 非目标

   - <本模块明确不做的事，逐条——含"明确不处理"的裁决（如某异常路径不自动处理）>
   ````

   模板八节固定，节名与节序如上。**定位边界**：用户裁决层的技术规格（表结构、WebUI 要求、横切资产）属于 PRD；规格之下的实现细节（代码组织、迁移脚本写法、技术选型落地）走技术方案（`docs/architecture/`），不进 PRD。

   **追加模式**不重排全文：新需求按模板中对应要素的格式增补需求条目，波及的既有节（状态枚举、配置项、表结构、非目标等）同步增改，未波及的节一字不动。

   **验收标准锚定**：验收标准只挂在功能需求清单的需求条目下——数据库设计 / WebUI 要求 / 横切资产节是规格内容，不另设验收标准（audit / release 只遍历需求条目下的验收标准，锚定不因模板扩展而变化）。

   **空节占位**：访谈未覆盖的节保留节标题，节内只放一行占位注释：

   `<!-- 待 /shw-prd-review 补齐：本节内容由审查循环逼出 -->`

   不用"暂无""TBD"等正文文字占位（避免被误当正式内容）。不替用户编造规格——编造的规格会被后续流程当作用户裁决的事实，比空着危害更大。

4. **可取证自查（硬纪律，不可跳过）**

   对每条验收标准逐条自查两件事：

   - **可取证吗？**——能跑命令比对结果 / 能发请求看响应 / 能指到界面检查点，三者居其一即可取证。不可取证的表述（如"优化用户体验""提升性能"）必须改造为可取证表述。例：
     > "优化下单体验" → "用户从进入商品页到下单成功不超过 3 步操作，可在小程序中按步骤核验"
   - **对得上 E2E 用例吗？**——每条标准以 `TC: <用例名>` 标注，用例名对齐将来的 E2E 测试用例，一条标准对一个用例；实现期与 `/shw-prd-audit` 取证都按这个名字对号入座。

   无法改造为可取证的，向用户指出该条不可取证，由用户改写或确认保留原表述——agent 不擅自删除或保留。

5. **确认门**

   向用户展示变更结果，并说明完整文件名（`docs/prd/<模块名>.md`）：全新起草按八节节序逐节展示（空占位节如实标注待 review 补齐）；追加模式逐处展示增改（原文表述 → 改后表述 / 新增条目全文）。用户确认后才落盘；有异议先调整再确认，调整后重新展示。

6. **落盘并提 docs PR**

   `docs/prd/` 目录由本命令首次落盘时按需创建（`mkdir -p docs/prd`），不预建。确认后写入文件。随后按 `shw-gitea-flow` skill 的关联纪律提交变更：从 dev 建分支、commit、经 gitea-mcp 建 docs PR（目标 dev），描述写 `Refs #N`（有关联 Issue 时）或变更背景说明；该 Issue 已有未合并的 docs PR 时 commit 追加到同一分支，不另开 PR。变更留痕由 git 历史 + PR 描述承担，PRD 内不追加变更记录章节。

7. **提示下一步**

   落盘后向用户输出（入口指引，供用户导航）：

   ```
   PRD 已更新：docs/prd/<模块名>.md（docs PR 待合并）
   后续：需求细化审查走 /shw-prd-review <模块名>（审出问题经你裁决直接修正）；后续增改需求走 /shw-prd-draft 追加模式；完成度盘点走 /shw-prd-audit <模块名>
   ```

**约束**

- 不硬拆需求边界：用户说多少需求就写多少，不替用户合并、拆分或增补需求
- 访谈不逼齐：不要求访谈覆盖全部八要素，用户未覆盖的节落空占位（标注待 /shw-prd-review 补齐），不替用户编造规格（表结构、页面设计等）——编造的规格会被后续流程当作用户裁决的事实，比空着危害更大
- 追加模式不推翻既有裁决：通读现有 PRD 在先，只增改本次访谈波及的节，未波及的节不动
- 可取证自查不可跳过：每条验收标准都必须过自查（可取证 + `TC:` 用例名对齐），不可取证且未改造/未确认的不得落盘
- 验收标准只挂功能需求清单的需求条目下：数据库设计 / WebUI 要求 / 横切资产节是规格内容，不另设验收标准，audit / release 的遍历锚定不受影响
- 落盘前必须经用户确认门：未经用户逐节确认，不得写文件
- 目录按需创建不预建：`docs/prd/` 只在首次落盘时创建，访谈/起草阶段不预建目录
- 变更必走 docs PR：落盘后经分支 commit + docs PR 合入（描述写 `Refs #N` 关联 Issue，目标 dev），不直接 commit 到 dev/main；PRD 内不手写变更记录章节（留痕由 git 历史 + PR 描述承担）
