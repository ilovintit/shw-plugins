# 小版本规划与反馈

## 载体

Version 使用一个 Gitea Milestone，不另建版本范围文件。描述记录当前 PRD/技术文档引用及 commit、用户目标、范围/非目标、依赖/风险、必要迁移/回滚与发布条件，以及开发环境、逐功能反馈、候选确认、发布和最终验收 checklist。

## 切片与准备

- 一个小版本围绕一个可完整体验目标；一个 Issue 是贯通必要前端/API/数据的可观察结果，不按技术层拆孤岛。
- 当前 Issue 具备范围、非目标、依赖、人工 AC 与必要工程检查即可开工，首项前先打通最小运行环境。纯维护项使用对应构建/调用结果，不伪造页面。
- 当前及紧接着的工作补齐入口、角色/数据、步骤和预期，后续细节随迭代完善；不等待全版本详细拆分或测试计划完成。
- 依赖按拓扑顺序串行。用户决定范围、优先级与重要边界；已有明确授权直接复用，Agent 维护载体和步骤，不要求用户逐个调用命令。

## 逐功能检查点

每个可体验功能合入 dev 且对应入口就绪后，提供源码/制品/部署标识、体验说明与限制，在 Milestone/Issue 标记待反馈，并等待用户回复。

反馈修正优先于下一项：未合并时用原 Issue/PR，已合并时用关联修正 Issue/PR；纯体验修改直接改实现，业务/技术契约变动同步 PRD/技术文档。用户确认满意或明确要求继续后再推进，“继续”不等于验收通过。明确授权连续开发时可跳过等待，记录未体验范围，不外推发布确认。

## 验收映射与收敛

AC 反向引用 PRD 和实际入口，记录步骤、预期、角色、数据、环境与反馈。`test-plan` 是增量维护工具，不是单独开工闸门；API/E2E/VRT 候选不阻止开发，最终验收后才以独立 chore Issue/PR 固化基线。

Issue closed 只证明其工程交付完成，Milestone 分别记录已交付、待反馈、修正中、已确认及未确认范围。版本范围全部交付后复核候选跨功能流程和受后续改动影响的已确认范围，汇总真实反馈供用户确认发布候选。生产验证与最终确认后才关闭 Version。
