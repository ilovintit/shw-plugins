# 动手前先挂 Issue（入口闸门）

## 概述

任务开工不是起点——**改动没有 Issue 关联就动手，等于在流程外裸奔**。事后补单、状态事后追认、分支和 PR 无处挂靠，1:1:1 体系（Issue : 分支 : PR）从根上就断了。

**核心原则**：产生 git 变更的任务，开工前必须有已声明的关联 Issue。用户直接发任务没提 Issue，不是跳过 gate 的理由，是 agent 当场建单的信号。

**这是主 Agent 的入口自律行为，不是用户该催的事。** 命令 `/issue` 是用户侧显式入口（带澄清对话的完整流程），本 skill 是 agent 侧自动闸门，两者建单语义同源。

## 铁律

```
会产生 git 变更的任务 + 无关联 Issue + 用户未豁免 → 先建单，声明编号后才开工
有单 ≠ 可在主目录开工：issue 开发一律在 issue worktree 内进行（形态见 shw-worktree），主目录只做 dev 基座
纯读侧任务 → 跳过，不误建单
```

## 门禁函数

```
接到任务（无论大小：改代码、改文档、修 bug、新建文件、配置调整）准备动手前：

1. 判断：这个任务会产生 git 变更吗？
   - 纯读侧（调研、答疑、读码、跑只读命令）→ 跳过 gate，直接干活
   - 会产生变更（改码/改文档/新建文件）→ 继续

2. 查关联 Issue：
   - 用户给了编号？→ 读取确认存在，关联，开工
   - 用户没给编号？→ 按任务关键词搜 open Issue（标题/正文匹配）
   - 命中 → 关联该 Issue，开工

3. 无关联 → 当场建单（语义与 /issue 步骤 1 同源）：
   - 标题一句话概括任务
   - 正文写背景 / 目标 / 约束
   - 打 backlog label
   - 向用户声明 Issue 编号后，才允许开工

4. 工作区检查（有单后、动手前）：
   - 当前在合规 issue worktree 内（宿主原生 Worktree、fallback `../<repo>-issue-N` 或里程碑常驻/permanent worktree）？→ 开工
   - 在主目录（或任意非 worktree 路径）？→ 先建/进 worktree 再动手：宿主有原生入口用原生；否则 `git worktree add ../<repo>-issue-N -b <分支> origin/dev`（形态判定见 shw-worktree）
   - 主目录已有本任务的未提交改动 → 停手，迁移进 worktree（stash / patch 搬运）再继续，不在主目录扩大现场
   - 用户明示"就在主目录干" → 记录豁免，最终汇报注明
   4b. 分支检查：当前分支是否 = issue 对应分支？
       - `git branch --show-current` 输出 `feat/<N>-<slug>`（或 bug/hotfix 对应前缀）→ 通过
       - 输出为空（detached HEAD）或 `dev`/`main` → 立即 `git checkout -b feat/<N>-<slug>` 固化（见 shw-worktree「进 worktree 后第一步 = 固化 issue 分支」）
       - 分支名与 Issue 编号不一致 → 停下核对

5. 建单通道：
   - gitea-mcp 优先
   - 不可用（未挂载 / 调用失败）时，经 Gitea REST API 兜底——
     host 与 token 来自当前 agent 工具的 gitea 凭证配置
     （具体工具的凭证存放路径一律见本 skill 的 config.md，按需加载）

6. 豁免：用户明确说"不用建单" / "先随便看看" →
   - 记录豁免，不擅自建单，也不反复纠缠
   - 在最终汇报里注明"本次无 Issue"
```

跳过任何检查步骤 = 失职。无单开工 = 事后补单 = 流程倒置；有单在主目录开工 = worktree 纪律形同虚设。

## 常见情况

| 场景 | 行为 |
|------|------|
| 纯读任务（调研 / 答疑 / 读码 / 只读命令） | ⏭️ 跳过 gate |
| 用户给了 Issue 编号 | ✅ 直接关联，开工 |
| 关键词搜到匹配的 open Issue | ✅ 关联并确认，开工 |
| 用户发任务没提 Issue | ✅ 当场建单，声明编号后开工 |
| 有单但在主目录（含主目录已有未提交改动） | ✅ 先建/进 worktree（脏改动迁移进去），再开工 |
| 探索中发现要动手改 | ✅ 先过 gate 建单，再转执行（衔接 /research 的转交语义） |
| 紧急线上修复 | ✅ 无例外——先建单，再开 hotfix 分支 |
| 用户明确拒绝建单 | ⏭️ 豁免，记录"本次无 Issue" |

## 红旗 - 停下重新评估

- 准备跳过 gate 直接写码（"任务很小"不是理由）
- 拿"就改一行"当借口绕过建单
- 挂了单就跳过工作区检查、直接在主目录开写（"活很小"同样不豁免 worktree）
- 任务做完了才想起补 Issue（事后补单 = 状态事后追认）
- 把纯读任务误建了单（gate 是入口闸门，不是建单强迫症）

## 与工作流命令的关系

`/issue` 是用户侧显式入口：带澄清对话、初步整理回写、小活/大活规格判定。本 skill 是 agent 侧自动闸门，只做"挂上单"这一件事：

- 用户用 `/issue` 发起 → 走命令完整流程，本 skill 自然无事
- 用户直接发任务 → 本 skill 兜住入口，建单语义取自 `/issue` 步骤 1（标题一句话 + 正文背景/目标/约束 + backlog label）
- 任务收尾由 shw-commit 兜底 commit——入口 gate、出口 commit，两端对称

探索类任务（/research 等）以纯读为主，gate 跳过；一旦探索结论指向动手实现，转交执行前先过本 gate。

## 例外：何时不触发

**用户拥有最终决定权。** 以下情况不建单：
- 用户明确说"不用建单" / "先随便看看" / "试一下"
- 纯读侧任务（调研、答疑、读码）
- 用户已给出编号、任务正在某个已有 Issue 的执行链中

**判断不清时**，问一句："这个任务建个 Issue 挂上吗？"——而不是默默开工。

## 底线

**动手的标志是"已声明关联 Issue + 已在合规 worktree"，不是"我开始改了"。**

无单开工 = 事后补单 = 1:1:1 从根上断掉；有单在主目录开工 = 共享现场互毁。先挂单、进 worktree，再动手。

这是主 Agent 的默认行为，不是可选项。
