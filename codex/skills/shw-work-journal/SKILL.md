# 工作记忆两层结构（Session Log + 提炼索引）

Agent 没有部落知识，跨会话的记忆只有仓库里的文档。代码只记录 What 和 How，**Why 必须落盘**——"当初为什么不用 X"、"试过什么不行"、"修复日后被证明是错的，你最想看当初为什么这么做"。本 skill 定义工作记忆的两层结构，两层缺一不可：只留索引丢细节，只存原始记录没法检索。

## 第一层：Session Log（原始过程记录）

**位置**：`docs/journal/issue-N.md`（一个 Issue 一个文件；无 Issue 的探索活动用 `docs/journal/date-主题.md`）

**记录内容**（追加式，带日期）：

- **被否方案**：考虑过什么、为什么放弃（配技术方案"备选与风险"章节的详版）
- **试错记录**：尝试路径 → 失败现象 → 原因 → 转向
- **踩坑**：环境、依赖、工具的坑与解法（下次直接绕开）
- **偏差**：实现与技术方案/PRD 的出入、原因、用户裁决结果
- **用户裁决**：过程中用户拍板的决策原话与背景

**写法纪律**：

- 追加不重写——log 是编年体，历史条目不改（错的分析也是历史）
- 一事一条，日期开头，三五句说清；贴关键报错原文，不贴大段日志
- 不记进度流水账（"完成了 A"这种 Issue/checklist 已表达的不重复）

**触发时机**：任务收尾必写；探索产出重要决策时即时写；实现出现方案外偏差时当场写。

## 第二层：提炼索引（定期收敛）

Session Log 是给"翻历史"用的；给"日常加载"用的是提炼层：

**AGENTS.md（索引层）**：每完成一个 Issue / 每次重要探索后，把值得跨会话记住的东西提炼成一行，追加进 AGENTS.md 的工作流区段或专门"经验索引"区段：

```markdown
- #12 支付回调：幂等键用 业务单号+状态机 而非回调 id（回调 id 会重发，见 docs/journal/issue-12.md）
- 部署：worker 只受 ENABLE_WORKERS 控制，勿再加进程级开关
```

一行一个主题：结论 + 一句理由 + 指向 Session Log/架构文档的链接。旧条目被更好结论取代时更新该行，不堆叠。

**docs/architecture/（决策层）**：设计决策的正式归宿随写随更——"为什么不用 X"、业务约束、回滚方式写进对应功能的技术方案（写决策不抄代码）；Session Log 里的过程细节不搬，链接过去即可。

## 提炼判据

写进提炼层的标准：**三个月后的新会话不知道它会不会重蹈覆辙或重复调研**。会 → 提炼；只是本次任务的过程细节 → 留在 Session Log。

## 与其他机制的关系

- `shw-commit`：journal 落盘后随手本地 commit
- `shw-docs-audit`：审计时 AGENTS.md 索引行的断言也要对账代码现实
- 技术方案"备选方案与风险"章节：决策的正式详版；Session Log 是过程草稿层
