# 合并执行人和拒绝后的推进

合并前先读取当前用户约定、项目规则和 `.shw/project.yaml` 的实际合并责任，再核对 PR 的仓库、base、head、来源范围与当前 SHA。创建 PR、集成范围、生产发布和代用户合并是不同动作；工具可见、CI 绿或有写权限都不授予合并权。

## dev→main：交用户手动合并

`issue-dev` / `managed` 的 dev→main 集成默认由用户手动合并。来源是冻结 dev 的集成分支时也属于这一类，不能只因 head 名称不叫 dev 就当作普通 PR。已有“必须用户手动合并”约定持续有效；“发布 dev 全部修改到生产”“继续”“全部完成”和 `/integrate` 不撤销该约定。

Agent 在交接前完成可独立推进的工作：冻结 dev SHA/main 基点/PR HEAD/预合并 tree、创建或复用 PR、审查差异、跟进必要构建与当前 HEAD 的门禁、处理授权内失败。准备就绪后提供 PR 链接、范围、检查状态和后续发布动作，明确请用户手动合并及所依据的规则；不是只交一个未核对的空 PR。

不调用 merge 或开启 auto-merge，不通过网页按钮、其他 MCP/REST、CLI、直接 push main、修改保护或换身份代做此步。若已经收到合并拒绝，先回读 PR：仍未 merged 时按人工边界反馈；尚未完成的检查继续跟进，不能换入口试合。单独的 403/405 不能证明拒绝原因；可只读查看日志/页面提示，但读到按钮可用也不是代点授权。

用户手动合并后回读 `merged`、base、实际 merge commit、父提交及 tree，核对冻结范围。用户说“合了”是回读触发，不代替证据；范围漂移先重新核对。确认一致后继续已有授权的 tag、发布和部署，无需重复索取同一发布授权；若原请求只有集成，不自动发布。尚未 merged 时不得提前打生产 tag、用 dev 制品冒充 main 或声称发布完成。跨回合继续时先恢复该边界和 PR 事实，不把恢复任务视为新的合并授权。

项目配置 `integration.mergeAuthority` 缺省或 `user` 按人工处理。兼容值 `explicit-project-authorization` 仅保留项目声明，不自动开启 Agent 合并；改变人工约定必须有用户明确变更合并执行人并指定适用项目/范围的独立授权。核实确有该授权时按新约定执行；配置值本身、历史泛化授权和普通发布/继续请求不能覆盖当前人工约定。集成、发布、候选和模板中的“交用户手动合并”均按本契约默认及当前人工约定解释，不主动要求用户放开权限。

## 其他 PR：拒绝后继续排查和推进

普通 Issue→dev，以及 issue-main 的 Issue→main，按各自实际合并授权处理；不能只因 base=main 就误归为 dev→main。已有项目人工审批或手动合并约定仍须遵守。已授权由 Agent 合并的 PR 被拒绝时，不以一次拒绝或“CI 还没跑完”结束交付：

1. **先回读**：PR 是否已 merged、当前 head/base、冲突/可合并状态、审批及当前 HEAD 的 required checks/run/job。未知响应可能已经合并，先确认，避免重复操作。不用旧 SHA 的成功代替当前候选。
2. **门禁运行中**：queued/pending/in_progress 或状态传播延迟时，继续有间隔地等待和查询，报告有意义的进展；完成后复核当前 SHA 和门禁再尝试正常合并。检查还在运行本身不是需要用户介入的阻塞。
3. **门禁失败、取消、缺失或过期**：读取对应日志、触发条件和必需检查，查明原因；在当前授权范围修复代码/配置、更新 PR，并跟进新候选的构建/静态门禁。需要重新触发时先核对不会夹带未授权测试。旧测试保护与当前按需测试规则冲突时报告真实冲突，不自动跑测试、改保护或伪造成功；skipped 不当 passed。
4. **门禁通过仍被拒**：继续核对审批、冲突、目标漂移、允许的合并方式和可读的保护信息；可安全处理的来源/冲突问题在当前工作区授权内解决，重取证后再正常合并。不盲重试同一请求，也不把 403/405 一律解释成权限不足或一律解释成 CI。
5. **确需用户处理**：确认缺少审批/权限、存在人工限制，或具体失败无法在现有授权内解决时，给出 PR、当前 SHA、门禁/拒绝证据、已尝试措施及所需用户动作；只有受阻的依赖动作暂停，继续其他已授权独立工作。缺少工具能力时说明缺失证据，不改身份、通道或保护绕过。

合并成功后回读真实结果，按交付规则关闭已完成范围的 Issue，继续已有 CI/部署跟进。此处持续推进不增加测试、跨项目写入或正式发布权限。
