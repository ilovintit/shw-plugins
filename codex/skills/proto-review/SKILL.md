# proto-review

这是共享源码中 slash command 的 Codex skill-backed prompt，不是 Codex 原生 commands。用户明确点名 `proto-review`、`/proto-review` 或要求执行该工作流时按下方原文执行。

**参数**：[Issue 编号 或 功能名]

细化审查功能原型的完备性：审查对象是**即将提交 docs PR 的原型变更**（工作区改动）或**指定原型全量**，多视角无锚定审查逼出原型该有而未有的内容，问题清单经用户裁决后写回原型并提 docs PR，最后给出就绪度软结论。审的是**原型 vs 需求空间**——交互逻辑、状态覆盖、权限可见性有没有漏。

与 `/prd-review` 的边界：那边审 PRD（文档 vs 需求空间），本命令审原型（界面 vs PRD 需求）。**审查即修正**：审出的问题经用户裁决后直接写回（无独立修正命令）；用户的主动增改走 /proto-draft 追加模式。可**多轮重跑**（含新会话）：跨轮收敛靠原型单一真相源 + 关联 Issue 时间线上的否决记录，不靠外部报告。

---

**输入**：`/proto-review` 后的参数是 Issue 编号或功能名（对应 `docs/design/<功能名>.html`）；参数未提供时先识别审查范围（见步骤 1）。

**步骤**

1. **定位审查对象与范围**

   - **参数未提供**：先看工作区有无未提交的原型变更（`git status docs/design/` 与 `git diff docs/design/`）：

     - 有 → 本次审查对象即这批待提交变更，列出涉及原型向用户确认
     - 无 → 列出 `docs/design/` 下的原型文件（目录不存在或为空 → 提示尚无任何原型、起草走 /proto-draft），问用户审哪个，不猜

   - **参数有值**：定位对应原型（文件不存在 → 提示不存在、起草走 /proto-draft，停止）。恰有未提交变更时默认只审变更面 + 波及一致性，向用户说明；用户要全量则全量。

2. **识别变更面（变更审查时）**

   ```bash
   git diff docs/design/<文件>
   ```

   变更审查聚焦两件事：新增/改动界面自身的完备性，以及变更与既有界面、关联 PRD 章节的咬合（加了字段却没加对应状态态、改了流程却没同步异常分支，是高频洞）。全量审查跳过本步。

3. **多视角无锚定审查**

   **并行委派多个独立审查视角**：每个视角由一个**不携带本对话上下文的独立审查代理**承担（所用工具的委派机制自行映射）；不支持委派时退化为串行自查各维度，并**向用户声明该局限**。每个视角只拿原型全文、关联 PRD 章节与本维度审查指令，不拿本对话历史。

   视角维度（至少五个）：

   | 视角 | 审什么 |
   | --- | --- |
   | PRD 咬合 | PRD 每条需求/验收标准在原型上有落点（界面/字段/状态反馈）——有需求没界面、有界面没需求来源都是洞 |
   | 状态覆盖 | 每个实体状态机在界面上的四态枚举齐全（正常/空/加载/错误）；界面流转与 PRD 状态机是同一套 |
   | 操作流完备 | 角色/入口/步骤/状态反馈/误操作与恢复路径；边界输入（超长文本、极端数量、必填缺失）有交代 |
   | 权限可见性 | 各角色看到的界面差异（字段级/按钮级/页面级）与 PRD 权限边界一致 |
   | 离场可执行性 | 总判据：把原型交给无上下文 agent 反推表结构与 API 契约（/arch-draft 的姿势），任何必须问人的点即洞 |

   视角纪律：各视角开审前先读原型全文与关联 PRD 章节（真相源）。会话内多轮重跑靠对话中的裁决记忆；新会话重跑时先经 gitea-mcp 读关联 Issue 时间线（docs PR 描述中的否决记录经 `Refs #N` 反出到时间线），**读到否决裁决的问题不再重提**。每条发现含：问题描述 / 判定依据 / 建议落点（改原型的哪部分）。

4. **问题清单展示与用户裁决**

   汇总各视角产出，去重合并后按三级分级，**只在对话展示，不落盘任何独立报告文件**：

   - **P0**：下游必然阻塞——/arch-draft 必须瞎猜才能反推的点
   - **P1**：高概率分叉——存在两种以上合理界面理解、会导出不同实现的点
   - **P2**：建议——不影响可执行性的改进建议

   请用户逐条裁决：**采纳**（进写回）或**不采纳**（进否决留痕）；可分批裁决，裁决完成后进下一步。

5. **写回并提 docs PR（审查即修正，直接写回）**

   - **采纳的问题**：起草变更摘要——改原型的哪些界面/字段/状态、为什么、影响哪些 PRD 需求，向用户展示；**审核门是硬门**，用户确认前原型文件保持原样；确认后修改原型。需求本身要改的（不是界面表达问题）提示走 `/prd-draft`（增改需求），不在原型里私改需求
   - **不采纳的问题**：随 docs PR 描述的"否决清单"段留痕（经 `Refs #N` 反向出现在 Issue 时间线），格式与 `/prd-review` 相同

   变更就绪后按 `shw-gitea-flow` skill 的关联纪律提交：从 dev 建分支、commit、经 gitea-mcp 建 docs PR（目标 dev），描述写 `Refs #N`（含否决清单段）；该 Issue 已有未合并的 docs PR 时 commit 追加到同一分支，不另开 PR。完成后向用户输出：改了哪些部分、PR 链接。

6. **就绪度结论**

   写回完成后给出就绪度结论，三档：

   - **可进 arch-draft**：P0 清零、P1 已消解或已有明确裁决
   - **建议先补 X**：X 为未消解的关键问题（指向原型的具体界面/状态）
   - **未就绪**：P0 大面积存在（界面结构级缺失），先补原型再反推方案

   就绪度结论是**纯软建议**：不做成任何下游的硬门，跳过审查直接 arch-draft 由用户决定。

**约束**

- **问题清单只在对话展示**：不落盘任何独立报告文件；唯一的写动作是写回原型本身与其 docs PR
- **用户未确认不改文档**：审核门是硬门，变更摘要未获用户确认前原型文件保持原样
- **变更必走 docs PR**：确认后的修改经分支 commit + docs PR 合入（描述写 `Refs #N`，目标 dev），不直接 commit 到 dev/main
- **否决留痕不重提**：不采纳的裁决随 PR 描述留痕（反出 Issue 时间线），后续轮次（含新会话重跑）读到即不再重提
- **需求与界面分层**：审出的是需求缺口 → 提示 /prd-draft（增改需求）；是界面表达缺口 → 本命令写回原型
- **除写回原型与其 docs PR 外零写副作用**：不写任何其他本地文件；gitea-mcp 操作限建 PR 与读 Issue 时间线
