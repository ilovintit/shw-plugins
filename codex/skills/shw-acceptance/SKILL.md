# 人工验收与反馈

## 模式前置

本 Skill 不是所有项目的默认约束。先读取仓库根 `.shw/project.yaml` 的模式：无标识时不主动应用；`issue-main` 只保留 Issue 分支→main 的轻量闭环；`issue-dev` 只保留 Issue 分支→dev→main 的轻量闭环；只有 `managed` 才应用本 Skill 中的业务项目目录、分支、测试、发布、部署或公司规范要求。模式定义见 `shw-issue-gate/project-mode.md`。

## 为什么不设 accept 命令

人工测试和真实使用是持续行为，不需要为“开始测试”制造状态命令。工作流只在必须使用结果作决策时收集证据：

- `/release` 使用 dev 整体验收结果决定是否创建 dev→main PR；
- `/version-close` 使用最终人工验收、生产反馈和观察结果决定是否关闭 Milestone；
- `/baseline` 只引用已经明确通过的最终验收，不把发布或健康状态当验收；
- 任何失败随时用 `/bug` 形成可追踪工作。

## dev 验收

针对 dev 上完整版本候选，按测试计划覆盖跨 Issue、跨端、角色权限、迁移和回归。结果记录时间、环境、commit、步骤、结果和证据。失败建 Bug 并挂当前 Milestone，修复后重验受影响范围。

## 最终人工验收与生产验证

发布/部署后由用户对不可变 main commit/tag、制品或 deployment revision 完成最终人工验收，记录时间、范围、步骤、结果和证据。再验证关键路径、真实依赖、日志/错误率/告警、数据一致性和回滚可用性。P0/P1 阻断版本关闭；非阻断项由用户决定是否进入下一 Version。

main 合并、发布成功、部署健康或 dev 人工测试都不是最终验收。最终验收通过后可创建独立基线维护 Issue；基线维护失败或未完成不推翻已经发生的验收，也不回开历史 Version，但必须记录未受保护范围和责任归属。

## 反馈分类

- 与当前 PRD/AC 不符：Bug。
- 要求新增能力或改变规则：产品需求，回产品定义。
- 当前版本承诺范围中的回归：挂当前 Milestone。
- 历史版本关闭后发现：不重开历史 Milestone，进入当前维护 Version 或 Hotfix。

Agent 不替用户宣告体验可接受，也不以“Pod Running”“CI green”代替人工验收。
